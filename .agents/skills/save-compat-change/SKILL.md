# 세이브에 닿는 것을 고칠 때 — 하위호환과 상위호환

사용자 지시(2026-11-12, 11-13): 데이터를 더 고쳐야 할 때 하위호환과 상위호환은 **무조건** 되어야 한다. 상위호환은 "옛 빌드에서도 플레이까지 된다"는 뜻이다. 예외를 두려면 먼저 사용자에게 묻는다.
규칙 원문은 `.claude/rules/data-driven.md` "세이브". 이 스킬은 그 규칙을 지키며 고치는 순서다.

## 두 약속

| 약속 | 뜻 | 깨지면 |
|---|---|---|
| 하위호환 | 옛 프로그램이 쓴 세이브가 새 프로그램에서 **열리고**, 다시 저장해도 **진행이 빠지지 않는다** | 업데이트 뒤 슬롯이 안 열리거나 진행이 조용히 사라진다 |
| 상위호환 | 새 프로그램이 쓴 세이브가 옛 프로그램에서도 **열리고 플레이되고**, 옛 프로그램이 저장한 뒤 새 프로그램으로 돌아와도 **새 진행이 남아 있다** | 옛 빌드로 열 수 없거나, 한 번 열었다고 새 진행이 지워진다 |

## 저장소가 해 주는 것과 못 하는 것

`FileSaveStore`·`MemorySaveSlot`(Data `NewerSaveInAnOlderProgramTests`, Game `NewerSlotIsPlayableTests`):

- 형식 버전이 더 높은 파일도 읽는다. 모양에 없는 필드는 읽을 때 넘기고, **쓸 때 그 파일에 있던 모르는 필드를 그대로 다시 쓴다.** 형식 버전은 낮춰 쓰지 않는다.
- 맨 위 모양과 **모양 안에 필드로 든 모양**(스냅샷의 지갑처럼)까지 지킨다.
- **목록 안 기록과 사전 안의 모르는 필드는 지키지 못한다.** 옛 프로그램이 기록을 더하고 빼고 순서를 바꾸므로 짝을 지을 수 없다.
- 읽기를 거절하는 것은 파일이 `ReadableFrom`(이 형식 버전을 아는 프로그램부터 읽을 수 있다)을 적었고 그 값이 프로그램의 `KnownVersion`보다 높을 때뿐이다. 거절한 파일은 덮어쓰지 않는다.
- 이 장치가 들어간 빌드부터 지켜진다. 그 전 빌드(2026-11-13 이전 개발 빌드)는 높은 버전을 거절한다.

## 먼저: 이 변경이 세이브에 닿는가

하나라도 맞으면 아래를 따른다.

- 세이브 모양 클래스(`*SaveData`, `IVersionedSave`)의 필드를 더하거나 바꾼다.
- 파일에 숫자로 쓰이는 enum을 고친다.
- 새 세이브 파일을 더한다(`SaveFileNames`).
- `data/`·`game/world`에서 세이브가 가리킬 수 있는 id를 지우거나 이름을 바꾼다(아이템, 퀘스트, 체인, 가구, 맵, 도착 지점).
- 저장된 양을 줄이는 수치를 고친다(`maxStack`, 가방 칸 수, 목록 길이 제한).

## 변경 종류마다 할 일

| 변경 | 하위호환 | 상위호환 |
|---|---|---|
| 필드 더하기(맨 위 모양, 모양 안의 모양) | 필드가 없는 옛 파일이 기본값으로 읽히고 그 기본값이 "옛 동작"과 같아야 한다 | 저장소가 지킨다. `KnownVersion`을 올린다(옛 프로그램은 그래도 읽는다). 아래 "옛 프로그램이 다녀간 뒤"를 본다 |
| 목록 기록·사전 값 안에 필드 더하기 | 위와 같다 | **저장소가 못 지킨다.** 잃으면 안 되는 값이면 기록 안에 넣지 않는다: 맨 위에 `기록 id → 새 값` 목록을 새 필드로 두거나 새 파일에 둔다 |
| 필드 이름·형 바꾸기, 지우기 | **하지 않는다.** 옛 필드는 그대로 두고 새 필드를 더한 뒤, 읽을 때 옛 필드에서 새 필드를 채운다 | 옛 필드를 **계속 쓴다**(옛 프로그램이 읽는 값이다). 쓰지 않으면 옛 프로그램은 기본값으로 플레이한다 |
| 뜻이 바뀜(같은 필드, 다른 해석) | 읽을 때 `Version`으로 갈라 옛 값을 새 뜻으로 옮긴다 | **하지 않는다.** 옛 프로그램은 옛 뜻으로 읽는다. 새 뜻은 새 필드에 둔다 |
| 숫자 enum | 있는 값의 숫자를 바꾸지 않는다. 새 값은 끝에, 숫자를 명시한다(Core `SavedEnumValuesTests`) | 옛 프로그램은 모르는 숫자를 만난다. 그 enum을 읽는 코드가 모르는 값에서 예외를 내거나 값을 바꿔 쓰지 않는지 테스트한다 |
| 새 세이브 파일 | 그 파일이 없는 옛 슬롯이 열려야 한다. `GameSession.Load`의 `Require` 목록에는 "그 파일을 쓰기 시작한 뒤의 세이브"를 가릴 근거가 있을 때만 넣는다 | 옛 프로그램은 그 파일을 건드리지 않는다(남는다). 모양을 `IVersionedSave`로 만들고, 진행을 바꾸는 파일은 `GameSession.Save()` 묶음 안에서 쓰고, `SaveShapeCoverage.cs`에 등록한다 |
| data id 지우기·이름 바꾸기, 더하기 | 그 id의 기록을 버리지도, 슬롯을 거절하지도 않는다. 규칙에는 안 보이게 들고 있다가 그대로 다시 쓴다(`ItemInventory._kept`, `QuestLog`·`QuestChainLog`의 `KeepUnknown`, 가구의 풀리지 않은 기록) | 같은 장치가 "새 프로그램에만 있는 id"를 옛 프로그램에서 지킨다. 새 종류의 id를 세이브에 넣으면 같은 방식으로 만든다 |
| 맵·도착 지점 지우기, 더하기 | 저장된 자리가 목록에 없으면 새 게임 자리에서 시작한다(`WorldSlotStart.MovedFrom`). 시작을 거절하지 않는다 | 새 맵에서 저장한 슬롯도 옛 프로그램에서 같은 장치로 열린다 |
| 양 줄이기·늘리기(`maxStack`, 칸 수) | 넘친 만큼을 버리지 않고 보존한다(`ItemInventory.Keep`) | 늘린 프로그램의 세이브를 옛 프로그램이 열 때도 같은 장치가 지킨다 |

`Version` 0은 "Unity 판이 쓴 파일"이다. 저장소는 0인 것만 쓸 때 `KnownVersion`으로 채운다(`FileSaveStore.Serialize`).

## 옛 프로그램이 다녀간 뒤

옛 프로그램은 자기가 아는 필드만 바꾸고 모르는 필드는 **예전 값 그대로** 다시 쓴다. 그래서 새 프로그램은 새 필드가 옛 필드보다 뒤처져 있을 수 있다고 보고 읽는다.

- 새 필드는 옛 필드와 **따로 맞는 값**으로 설계한다(더해지는 것, 따로 세는 것). 옛 필드에서 계산해 낼 수 있는 값은 저장하지 말고 읽을 때 계산한다.
- 옛 필드와 맞아야 하는 새 필드는 읽을 때 어긋남을 검사하고, 어긋나면 옛 필드를 기준으로 다시 맞춘다. 그 경우를 테스트로 고정한다("옛 프로그램이 하루를 보낸 슬롯").
- 새 파일도 같다: 옛 프로그램이 플레이하는 동안 그 파일은 멈춰 있다.
- 받음 기록(요청 id, 받은 보상)은 옛 필드에 있는 것이 기준이어야 한다. 새 필드에만 있는 받음 기록은 옛 프로그램이 모르므로, 옛 프로그램에서 같은 보상을 다시 받을 수 있는지 따진다.

- **요청이 여러 걸음으로 나뉘는 지불(잡기 → 내기 → 쓰기)에서는 "돈을 냈다"를 보낼 목록에만 두지 않는다.** 옛 빌드·옛 방은 모르는 조각의 요청 줄을 `Invalid`로 답하고 지운다. 그러면 새 프로그램으로 돌아와 그 잡기를 "돈 내지 않은 떠도는 잡기"로 풀어 돈만 사라진다. 표시를 새 파일(옛 빌드가 건드리지 않음)에 돈을 내는 바꾸기와 같은 `Save()` 묶음으로 남기고, 다시 켠 판은 보낼 목록이 아니라 표시를 보고 판단한다(있으면 쓰기를 새 id로 다시 보내고, 없으면 푼다). 본보기: `room-house-build-paid-<플레이어>.json`(Core `RoomHouseBuildPaidHolds`), 테스트 Game `RoomHouseBuildCompatTests`.
- **상위호환 테스트는 옛 빌드를 "거친 뒤 새 빌드로 돌아오는" 왕복까지 본다.** 옛 빌드로 열어 플레이한 뒤 저장한 파일을 새 코드로 다시 읽어 돈·진행이 한 번만 남는지 확인한다(`RoomHouseBuildCompatTests`의 `…ThroughAnOlderBuildFirst…`).

## 옛 프로그램이 읽으면 안 되는 변경

위 방법으로 안 되는 변경(옛 프로그램이 플레이하면 진행이 상한다)은 **먼저 사용자에게 묻는다.** 허락받았을 때만 그 모양에 `public int ReadableFrom = <새 KnownVersion>;` 필드를 더해 쓴다. 옛 프로그램은 그 파일을 읽지 않고 덮어쓰지 않으며, 슬롯 화면은 그 칸을 읽을 수 없는 칸으로 보인다.

## 순서

1. **실패 테스트 먼저.**
   - 하위: 옛 모양의 파일(고정 파일이나 테스트가 직접 쓴 JSON)을 새 코드로 읽어 열리는지, 읽고 다시 쓴 뒤 옛 필드와 기록이 남는지.
   - 상위: 새 필드를 넣은 파일을 **그 필드를 모르는 모양**으로 읽고 다시 쓴 뒤 새 필드가 남는지(목록 기록 안이면 남지 않는다 — 자리를 옮긴다). 그리고 "옛 프로그램이 다녀간 뒤"의 파일(새 필드는 예전 값, 옛 필드는 새 값)을 새 코드가 바르게 읽는지.
2. 고친다. **있는 고정 폴더(`game/tests/Rootborn.Data.Tests/Fixtures/saves/*`)는 고치지 않는다.** 그 폴더를 읽는 테스트가 실패하면 고칠 것은 코드다.
3. 새 `GameSession`으로 다시 읽어 같은지 본다(저장 → 새 판 → 읽기).
4. `KnownVersion`을 올렸으면 새 날짜 고정 폴더를 **더한다**:
   ```bash
   ROOTBORN_FIXTURE_OUT=<저장소>/game/tests/Rootborn.Data.Tests/Fixtures/saves/monogame-<날짜> \
     dotnet test game/tests/Rootborn.Game.Tests --filter "Name~WriteCurrentSlotFixture"
   ```
   그리고 그 폴더의 `README.md` 표에 한 줄 더한다.
5. 돌린다: `Rootborn.Core.Tests`, `Rootborn.Data.Tests`(`OldSaveTests`, `SaveShapeRegistrationTests`, `NewerSaveInAnOlderProgramTests`), `Rootborn.Game.Tests`(`SavedFilesAreRegisteredTests`, `DeletedSaveFileTests`, `NewerSlotIsPlayableTests`). 합치기 전에는 전부(`Scripts/remote-test/run.sh`).
6. Unity 판과 달라진 동작이면 `docs/superpowers/specs/2026-11-11-core-rules-extraction-design.md` 9절에 한 줄.

## 하지 않는다

- 읽을 수 없는 파일(깨짐, `ReadableFrom`이 높음)을 "없음"으로 보고 기본값으로 덮어쓰기. 읽기 실패 뒤에는 그 파일을 쓰지 않는다.
- 저장소를 거치지 않고 세이브 JSON을 직접 읽어 고쳐 쓰기(모르는 필드가 사라진다). 원문을 통째로 옮기는 것(`ReadSlotFiles`·`WriteSlotFiles`)은 된다.
- 모르는 id·넘친 양을 조용히 버리기, 또는 그것 때문에 슬롯 전체를 거절하기.
- 옛 세이브가 안 읽힐 때 고정 파일이나 테스트 기대값을 고쳐 통과시키기.
- 테스트에서 사용자 세이브 폴더(`AppData/LocalLow`) 쓰기.
- 두 약속 중 하나를 포기해야만 되는 변경을 묻지 않고 진행하기 — 무엇을 잃는지 적어 사용자에게 묻는다.

## 보고

"하위호환 확인"과 "상위호환 확인"을 나눠 쓰고 각각 테스트 이름을 붙인다. 모두 자동 테스트다(화면 근거 아님). 실제 옛 빌드 실행 파일로 열어 본 것이 아니면 그렇게 쓰지 않는다. 확인하지 못한 쪽은 못 했다고 쓴다.
