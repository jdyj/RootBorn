# 엔진 무관 게임 규칙과 실제 플레이 증거

Claude와 Codex 모두 따른다. 2026-11-07 사용자 결정.

## 1. 게임 규칙은 Unity와 무관한 순수 C#으로 둔다

### 왜
Unity 에디터 테스트는 한 번에 수 분이 걸리고 메모리를 4~10GB 쓴다. 에디터가 열려 있으면 파일 수정이 재컴파일을 일으켜 테스트가 깨진다. 규칙을 엔진과 분리하면 그 부분은 Unity 없이 몇 초 만에 검증할 수 있고, 나중에 엔진을 바꾸더라도 그대로 가져갈 수 있다.

### 원칙
- 진행도, 조건 판정, 보상 계산, 일정, 퀘스트·업적 평가, 저장 데이터 모델처럼 화면과 무관한 규칙은 `UnityEngine`을 참조하지 않는 어셈블리(`noEngineReferences: true`)에 둔다.
- ScriptableObject는 계속 데이터의 원본이다. MonoBehaviour와 SO는 경계에서 순수 데이터로 바꿔 규칙 코드에 넘기고, 규칙 코드는 결과만 돌려준다. 엔티티 데이터 드리븐 원칙(ID 분기 금지)은 그대로 적용된다.
- 순수 규칙의 단위 테스트는 Unity 없이 `dotnet test`로 돌린다. 같은 동작을 Unity EditMode에서 중복 검증하지 않는다.
- 기존 코드는 한꺼번에 옮기지 않는다. 규칙을 고치거나 새로 만들 때 그 부분부터 옮긴다. 옮긴 뒤에도 사용자 흐름은 PlayMode로 검증한다.

## 2. "확인했다"는 실제 플레이로 확인한 것만 쓴다

### 왜
내부 함수 호출, 상태 강제 설정, 입력칸에 값 직접 넣기로 확인한 것을 실제 플레이로 확인한 것처럼 보고한 일이 반복됐다. 사용자는 이것을 플레이하지 않고 한 척한 것으로 받아들였다.

### 보고 규칙
- 완료 보고의 "확인한 것"에는 실제 입력 경로로 확인한 항목만 쓴다. 실제 입력 경로는 다음 넷 중 하나다.
  - 키보드·마우스 장치 입력
  - UI 레이캐스트를 거친 클릭
  - 이동으로 들어간 트리거
  - 직접 본 Game View 스크린샷
- 항목마다 근거를 붙인다: 테스트 이름, 또는 스크린샷 경로.
- 다음으로 확인한 것은 "실제 플레이로는 미확인"에 따로 적고, 무엇을 건너뛰었는지 쓴다.
  - 내부 메서드 호출
  - 씬 강제 로드
  - `ConfigureForTests` 같은 상태 강제 설정
  - 필드나 입력칸에 값 직접 대입
  - `ExecuteEvents.Execute`로 버튼 직접 실행
  - 날짜·시간 강제 변경
- EditMode 통과와 데이터 확인은 "자동 테스트"로 따로 적는다. 화면에 보이는지에 대한 근거로 쓰지 않는다.

### PlayMode 데이터 읽기 방식
- 평소 반복 테스트는 Addressables를 원본 에셋에서 읽는 방식으로 돌려 재빌드 시간과 메모리를 아낀다.
- 커밋 직전, 빌드와 같은지 판단할 때, FEVM 검증 때는 빌드된 Addressables로 한 번 더 돌린다.
- 보고서에는 어느 방식으로 돌렸는지 적는다. 원본 방식에서만 통과한 결과를 빌드 동작으로 보고하지 않는다.
