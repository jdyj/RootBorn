# 게임 설계 원칙

기획·데이터 구조·화면·테스트를 정할 때 적용한다. 수치·콘텐츠·진행 순서를 바꾸는 결정은 사용자에게 묻는다(`rules/engine-migration.md`).

## 자유 경로 성장

학생 생활은 학교 수업 하나만 정답인 일직선이 아니다. 학교를 중간에 나가거나 마을 활동, 관계, 알바, 탐험, 제작, 도움, 독학, 휴식, 이벤트 선택으로도 특성·성향·기술·진로 힌트·관계·컨디션이 자라야 한다. 왜: 플레이어가 고른 길이 존중받아야 다시 하고 싶은 게임이 된다.

### 하지 않는다

- 성장이나 퀘스트 진행을 "학교 수업 완료" 하나에만 묶기.
- 활동·장소·퀘스트 id로 분기해 길을 막기(`if (routeId == "school")`, `switch (locationId)`).
- 정해진 순서로만 이동·수업·퀘스트를 해야 진행되는 구조.
- 학교 밖 활동을 곁다리 보상으로만 두고 핵심 성장·진로·관계에서 빼기.

### 한다

- 같은 핵심 성장 목표에는 가능하면 길을 두 개 이상 둔다.
  - 예: 성실함 — 수업, 도서관 독학, NPC 돕기, 반복 작업.
  - 예: 사교성 — 친구 대화, 마을 행사, 같이 하는 퀘스트, 가게·주민 돕기.
  - 예: 진로 힌트 — 학교 활동, 현장 실습, 마을 의뢰, 독학, 관계 이벤트.
- 길은 모두 데이터(`data/` JSON의 정의와 그 안의 조건·효과·결과 전략)로 표현한다(`rules/data-driven.md`).
- 퀘스트와 활동은 하나의 필수 순서가 아니라 조건에 따른 선택지, 대신할 목표, 여러 해결 방법을 받는다.
- 새 핵심 흐름의 테스트는 학교가 아닌 길 하나 이상으로도 성장·퀘스트·진로 힌트가 나아가는지 본다(예: Game `FreePathTests`, `SelfStudyAndClassTests`).

## 성능을 처음부터 같이 설계

새 시스템은 다 만든 뒤 고치는 것이 아니라 데이터 구조·화면·테스트를 정할 때 항목 수 증가, 세이브 크기, 화면 갱신 비용, 그림 읽기 비용을 같이 본다. 왜: 목록 화면과 저장 구조는 나중에 바꾸기 가장 비싸다.

### 하지 않는다

- 매 프레임 전체 항목을 훑거나 다시 정렬하기.
- 매 프레임 수첩·퀘스트·가방·마일스톤 상태를 다시 계산하기.
- 갱신할 때마다 목록 노드를 통째로 버리고 새로 만들기.
- 프레임 루프에서 문자열 이어 붙이기, LINQ로 쓰레기 만들기.
- 같은 그림·데이터를 갱신할 때마다 다시 읽기.
- 시험 데이터 5개에서만 통과하고 실제 수백 개(가구 1,500여 개 등)에서 끊기는 구조를 끝났다고 보고하기.

### 한다

- 가방, 도감, 수첩, 가구 팔레트처럼 느는 목록은 보이는 줄만 그리고(`UiScrollList`, 카드 격자), 거르기 결과를 기억하고, 바뀐 것만 고친다.
- 정의는 시작할 때 한 번 읽고 id 표로 찾는다(`GameDefinitions`). 매번 전체 목록을 훑지 않는다.
- 화면은 상태가 바뀌었다는 알림, 이어 하기 완료, 탭 바꾸기, 검색어 바꾸기처럼 분명한 때에만 필요한 부분을 고친다.
- 새 일의 완료 조건에 성능 위험 확인과 최소한의 측정(또는 측정 계획)을 넣는다.
- 완료 보고에 성능을 어디까지 확인했는지, 남은 병목 가능성, 나중에 할 일을 적는다.
