# Rumor Clue Discovery Loop Goal Prompt

아래 프롬프트를 goal 세션에 그대로 붙여 넣고 진행한다.

```text
ROOTBORN Unity 프로젝트에서 "퀘스트/월드 상태 변화가 직접 추천이 아니라 NPC 소문, 게시판 단서, 지도 힌트, 도감 미확인 항목, 장소 흔적으로 이어지고, 플레이어가 실제 이동/상호작용으로 직접 발견하는 소문·단서·발견 루프"를 설계/구현/검증해줘.

핵심 의도:
- 게임이 "다음 행동은 이것"이라고 직접 추천하지 않는다.
- 월드 변화와 퀘스트 결과는 플레이어가 스스로 추리하고 찾아갈 수 있는 소문/단서/흔적으로 남긴다.
- 단서는 NPC 대사, 게시판, 지도 흐릿한 표시, 도감 `???` 항목, 장소 오브젝트 흔적처럼 여러 경로로 노출될 수 있다.
- 플레이어가 단서를 보고 실제로 이동/상호작용해 발견하면 도감, 진로 힌트, 후속 퀘스트, 월드 변화 활용 요소로 이어진다.
- 새 소문/단서는 C# 코드 수정 없이 ScriptableObject 데이터 추가와 Registry 등록만으로 추가 가능해야 한다.

헌법 규칙:
- AGENTS.md와 `.claude/rules/*`를 따른다.
- `Assets/**/*.cs`를 외부 디스크 쓰기로 직접 수정하지 않는다. C# 신규/수정은 반드시 Unity MCP `script-update-or-create` 또는 Unity Editor 안전 경로를 사용한다.
- 모든 게임 엔티티는 100% ScriptableObject 데이터 기반이어야 한다.
- clueId, worldStateId, questId, npcId, locationId, boardId, mapHintId별 `if/switch` 분기, enum 기반 엔티티 분기, 단서별 C# 클래스 생성은 금지한다.
- 소문/단서 노출 위치, 노출 조건, 완료 조건, 결과, 반복/만료 정책은 SO 데이터와 전략 배열로 표현한다.
- 도감/진로 힌트/퀘스트/월드 활용 보상은 저장/로드 후 중복 적용되면 안 된다.
- TDD로 진행한다. 먼저 실패하는 테스트를 만들고 실패를 확인한 뒤 구현한다.
- 성능/최적화 동시 설계 원칙을 따른다.
- 기존 dirty 변경을 되돌리지 않는다.

권장 데이터 구조:
- `DiscoveryClueDefinition`
  - 단서 표시명, 설명, 관련 월드 상태, 관련 퀘스트, 관련 장소, 관련 NPC, 단서 강도, 공개/숨김 텍스트, UI 표시 정책, 완료 결과를 정의한다.
- `DiscoveryClueSourceBase[]`
  - NPC 대사, 게시판, 지도 힌트, 도감 미확인 항목, 장소 흔적, 하루 결과 요약 같은 노출 경로를 정의한다.
- `DiscoveryClueConditionBase[]`
  - 월드 상태 활성 여부, 퀘스트 상태, 관심 진로, 관계도, 시간대, NPC 위치, 장소 방문 여부, 도감 발견 여부를 일반 조건으로 평가한다.
- `DiscoveryClueCompletionBase[]`
  - 특정 장소 방문, 오브젝트 상호작용, NPC 대화, 지도 위치 확인, 도감 항목 발견, 활동 수행을 단서 완료 조건으로 평가한다.
- `DiscoveryClueOutcomeBase[]`
  - 도감 발견, 진로 힌트, 후속 퀘스트 후보, 월드 변화 활용 요소, 관계 변화, 하루 이벤트 후보를 일반 결과로 처리한다.
- `DiscoveryClueProgress`
  - saveSlot + player identity 기준으로 단서 노출 여부, 본 여부, 추적 여부, 완료 여부, 보상 수령 여부, 마지막 노출 날짜, 완료 날짜를 저장한다.
- `DiscoveryClueSummaryModel`
  - NPC 대화 UI, 게시판 UI, 지도 UI, 도감 UI, 월드 로그 UI에서 공통으로 사용하는 표시 모델이다.

초기 단서 예시:
- `도서관 오래된 지도 소문`
  - 조건: 도서관 자료실 개방
  - 노출: 사서 NPC 대사, 도감 `??? 오래된 기록`
  - 완료: 자료실 안쪽 상호작용 발견
  - 결과: 탐험·정보형 진로 힌트, 도감 `오래된 지도 조각`, 후속 조사 퀘스트 후보
- `공방에 사람이 모인다는 소문`
  - 조건: 공방 수리 작업대 등장
  - 노출: 상점 주인 대사, 게시판 소문
  - 완료: 공방 작업대 직접 사용
  - 결과: 기술·작업형 진로 힌트, 수리 연습 활동 발견
- `골목 바람 소리`
  - 조건: 숨은 길 개방
  - 노출: 광장 NPC 대사, 지도 흐릿한 표시, 장소 흔적
  - 완료: 골목 숨은 길 포탈 발견
  - 결과: 새 장소 발견, 도감 항목, 탐험형 후속 이벤트 후보
- `새 품목 입고 소문`
  - 조건: 상점 새 품목 Shared 월드 상태 활성화
  - 노출: 게시판, 상점 UI 미확인 품목 배지
  - 완료: 상점에서 새 품목 확인 또는 구매
  - 결과: 관계·서비스형 힌트, 배달 도움 활동 후보

UI 요구:
- NPC 대화 UI는 해당 NPC에게 현재 노출 가능한 단서를 대사/소문 선택지로 표시한다.
- 게시판 UI는 현재 공개 가능한 단서를 목록으로 표시하되, 정확한 정답 위치를 모두 알려주지 않는다.
- 지도 UI는 단서가 있는 장소를 정확한 목적지 마커가 아니라 흐릿한 범위/힌트 배지로 표시할 수 있다.
- 도감 UI는 아직 발견하지 못한 단서를 `???` 항목으로 표시하고, 일부 힌트만 보여준다.
- 장소에는 실제 흔적 오브젝트 또는 상호작용 프롬프트가 생겨야 한다.
- 월드 로그 UI에는 본 단서/완료한 단서/미완료 단서를 상태별로 표시한다.
- UI는 특정 clueId/worldStateId를 직접 알지 않고 `DiscoveryClueSummaryModel`을 렌더링한다.
- Modern UI Style2 공통 패널 규약을 따른다.
- 1920x1080 기준에서 단서명, 힌트 텍스트, 출처, 상태, 버튼 텍스트가 겹치거나 잘리지 않아야 한다.
- UI는 문서 목업만 만들고 끝내면 안 된다. PlayMode에서 실제로 열리고 클릭 가능해야 한다.

확장성 검증:
- 새 소문/단서는 C# 코드 수정 없이 ScriptableObject 데이터 추가와 Registry 등록만으로 추가 가능해야 한다.
- 테스트용 신규 `DiscoveryClueDefinition`을 1개 이상 추가하고, 기존 런타임 코드를 수정하지 않은 상태에서 노출/확인/발견/보상/저장/로드가 동작하는지 검증한다.
- 한 월드 상태 변화가 여러 단서를 만들 수 있어야 한다.
- 하나의 단서가 NPC 대사, 게시판, 지도, 도감, 장소 흔적 중 여러 source에 동시에 노출될 수 있어야 한다.
- 같은 단서 완료 결과가 도감, 진로 힌트, 후속 퀘스트, 월드 활용 요소 중 여러 결과를 열 수 있어야 한다.
- 같은 단서를 반복 확인해도 중복 보상, 중복 도감 발견, 중복 퀘스트 해금, 중복 진로 힌트가 발생하지 않아야 한다.
- 단서 만료/반복/일회성 정책이 필요하면 데이터로 정의한다.
- 최종 보고에는 "소문·단서 추가 확장성 검증 체크리스트"를 포함하고, SO만으로 추가한 테스트 단서의 실제 플레이 검증 결과를 기록한다.

최우선 실제 플레이 검증 원칙:
- 이 goal은 실제 유저가 플레이하듯 검증하지 않으면 완료로 인정하지 않는다.
- 최소 1개 이상의 PlayMode E2E는 저장 슬롯 UI에서 시작해 실제 키보드 이동, 실제 NPC/게시판/지도/도감/장소 상호작용, 실제 UI 버튼 선택, 단서 확인, 실제 장소 발견, 결과 확인, 저장/로드 재진입을 모두 거쳐야 한다.
- 테스트에서 DiscoveryClueProgress, WorldStateProgress, QuestLog, Inventory, SaveData 상태를 직접 세팅해서 성공 처리하면 실패다.
- 플레이어 Transform 직접 이동, 내부 메서드 직접 호출, 씬 강제 로드, 저장 데이터 직접 주입, UI 없이 도메인 API 직접 호출로 실제 플레이 경로를 대체하면 완료로 보고하지 않는다.
- 최종 보고 전에 "실제 플레이 방식 상호작용 검증 체크리스트"를 반드시 작성하고, 각 항목을 PASS/FAIL로 표시한다.

실제 플레이 방식 상호작용 검증 체크리스트:
- 저장 슬롯 UI에서 새 게임 또는 기존 슬롯을 실제 UI 경로로 시작했는가?
- 플레이어 이동이 Transform 직접 세팅이 아니라 키보드/입력 시스템 경로로 수행됐는가?
- NPC 대화, 게시판, 지도, 도감, 장소 흔적 중 최소 2개 source가 실제 Prompt/Input/Button 경로로 열렸는가?
- 단서가 직접 추천이 아니라 소문/흐릿한 힌트/미확인 항목/장소 흔적으로 노출됐는가?
- 플레이어가 실제 이동으로 단서 위치를 찾아가고 실제 상호작용으로 발견을 완료했는가?
- 발견 결과가 도감, 진로 힌트, 후속 퀘스트, 월드 변화 활용 요소 중 최소 1개 이상으로 이어졌는가?
- 저장 슬롯 UI 재진입 후 같은 슬롯을 로드했을 때 단서 본 여부, 완료 여부, 보상 수령 여부가 유지되는가?
- 같은 단서를 반복 확인해도 중복 보상/중복 발견/중복 퀘스트 해금이 발생하지 않는가?
- 테스트용 신규 단서가 SO만으로 추가되어 실제 플레이 경로에서 노출/발견/저장/로드됐는가?
- 체크리스트 항목 중 하나라도 FAIL이면 완료로 보고하지 않고 실패 단계와 남은 작업을 보고했는가?

싱글/멀티 정책:
- 싱글플레이에서 혼자 모든 단서 발견 루프를 완료할 수 있어야 한다.
- 멀티플레이 협동은 필수가 아니다.
- Shared 월드 변화로 열린 단서는 모든 클라이언트에 노출될 수 있다.
- 단서 본 여부, 완료 여부, 도감 발견, 진로 힌트, 후속 퀘스트 수락/보상 상태는 Personal이다.
- Client 1이 월드 변화를 열어 단서 source가 생기면 Client 2도 source를 볼 수 있지만, Client 2의 단서 완료/보상은 별도로 처리한다.
- 멀티플레이 직접 검증이 이번 범위에 포함되면 실제 클라이언트 2개 이상 또는 Host+Client를 띄워 Shared 단서 source와 Personal 발견 상태 분리를 확인한다.
- 멀티플레이 직접 검증이 범위 밖이면 최종 보고에 후속 NET 테스트 계획을 명시한다.

목표 플레이 흐름:
1. 저장 슬롯 UI로 새 게임 또는 기존 슬롯 로드 후 Town에 진입한다.
2. 실제 플레이로 퀘스트 또는 월드 상태 변화를 만든다.
3. 플레이어가 실제 이동으로 NPC, 게시판, 지도, 도감, 변화 장소 중 하나에 접근한다.
4. 실제 Prompt/Input/Button 경로로 단서 source를 확인한다.
5. 단서는 정확한 다음 행동 추천이 아니라 소문/힌트/흔적 형태로 표시된다.
6. 플레이어가 힌트를 바탕으로 실제 이동해 관련 장소를 찾는다.
7. 실제 상호작용으로 장소 흔적/오브젝트/NPC/포탈/활동 중 하나를 발견한다.
8. 발견 결과로 도감, 진로 힌트, 후속 퀘스트, 월드 변화 활용 요소 중 최소 1개 이상이 발생한다.
9. 월드 로그 또는 도감 UI에서 단서 상태가 `본 단서`, `완료한 단서`, `미완료 단서`로 표시된다.
10. 저장 슬롯 UI로 같은 슬롯을 다시 로드한다.
11. 재로드 후 단서 본 여부, 완료 여부, 보상 수령 여부가 유지되는지 확인한다.
12. 같은 단서를 반복 확인해 중복 보상/중복 해금/중복 발견이 발생하지 않는지 확인한다.
13. SO만으로 추가한 테스트 단서도 같은 흐름으로 노출/발견/저장/로드한다.

- DISCOVERY-CLUE-EDIT-001: DiscoveryClueDefinition/source/condition/completion/outcome 전략이 Registry 또는 지정 데이터 경로에서 로드된다.
- DISCOVERY-CLUE-EDIT-002: 새 테스트 단서가 C# 코드 수정 없이 SO 추가와 Registry 등록만으로 로드된다.
- DISCOVERY-CLUE-EDIT-003: 활성 월드 상태 또는 퀘스트 결과가 관련 단서를 노출 가능 상태로 만든다.
- DISCOVERY-CLUE-EDIT-004: 단서 노출 조건은 clueId/worldStateId/npcId/locationId별 if/switch 없이 전략 배열로 평가된다.
- DISCOVERY-CLUE-EDIT-005: 하나의 단서가 NPC/게시판/지도/도감/장소 흔적 중 2개 이상 source summary를 생성할 수 있다.
- DISCOVERY-CLUE-EDIT-006: 단서 완료 결과는 도감/진로 힌트/후속 퀘스트/월드 활용 요소를 전략 배열로 적용한다.
- DISCOVERY-CLUE-EDIT-007: 저장/로드 후 본 여부, 완료 여부, 보상 수령 여부가 복원된다.
- DISCOVERY-CLUE-EDIT-008: 같은 단서 완료 결과를 반복 적용해도 중복 보상/중복 도감/중복 퀘스트/중복 진로 힌트가 발생하지 않는다.
- DISCOVERY-CLUE-EDIT-009: UI summary 생성이 매 호출 Registry 전체 순회를 요구하지 않는 구조인지 검증한다.
```
