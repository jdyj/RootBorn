# Career Interest Quest Chain State Goal Prompt

아래 프롬프트를 goal 세션에 그대로 붙여 넣고 진행한다.

```text
ROOTBORN Unity 프로젝트에서 "관심 진로별 전용 퀘스트 체인을 추가하고, 체인 중간 이탈, 관심 진로 변경, 여러 체인 동시 보유, 진행 차단, 재개, 완료/실패/만료, 저장/로드 복원, 그리고 앞으로 퀘스트를 ScriptableObject 데이터만으로 쉽게 추가할 수 있는 확장성"을 설계/구현/검증해줘.

핵심 의도:
- 관심 진로를 선택하면 해당 진로에 맞는 짧은 전용 퀘스트 체인이 열린다.
- 퀘스트 체인은 하나의 선형 강제 루트가 아니라, 플레이어가 여러 체인을 동시에 보유하거나 중간에 멈추고 다른 루트로 이동할 수 있는 구조여야 한다.
- 체인이 중간에 끊기거나 관심 진로가 변경되어도 진행도는 사라지지 않고 명확한 상태로 관리되어야 한다.
- 새 퀘스트 체인은 C# 코드 수정 없이 ScriptableObject 데이터 추가와 Registry 등록만으로 붙일 수 있어야 한다.
- 실제 유저가 플레이하듯 저장 슬롯 UI, 이동, NPC/장소 상호작용, 퀘스트 UI, 하루 종료, 저장/로드를 거쳐 검증해야 한다.

체인 상태 정책:
- `Available`
  - 조건을 만족해서 시작 가능한 체인이다.
- `Active`
  - 현재 진행 중인 체인이다.
- `Tracked`
  - HUD/퀘스트 로그에서 우선 추적 중인 체인이다. 여러 체인을 보유해도 우선 추적 체인은 기본 1개다.
- `Paused`
  - 관심 진로 변경, 다른 체인 우선 추적, 플레이어 선택으로 잠시 멈춘 체인이다. 진행도는 유지된다.
- `Blocked`
  - NPC 부재, 장소 미발견, 관계 부족, 아이템 부족, 시간대 불일치 등으로 진행이 막힌 체인이다. UI에 막힌 이유와 재개 조건을 표시한다.
- `Completed`
  - 모든 단계가 완료된 체인이다. 재진행 불가가 기본이며, 예외는 데이터로 정의한다.
- `Failed`
  - 실패 조건을 만족한 체인이다. 재시도 가능 여부는 데이터로 정의한다.
- `Expired`
  - 시간 제한을 넘긴 체인이다. 만료 후 재시도/대체 체인 연결 여부는 데이터로 정의한다.

중간 이탈/동시 진행 정책:
- 관심 진로를 바꾸면 기존 관심 진로 체인은 삭제하지 않고 `Paused` 상태로 유지한다.
- 다시 같은 관심 진로로 돌아오면 중간 진행도부터 재개할 수 있어야 한다.
- 여러 체인을 동시에 보유할 수 있다.
- HUD에는 우선 추적 체인 1개를 기본 표시하고, 퀘스트 로그에서는 전체 체인을 상태별로 볼 수 있어야 한다.
- 같은 행동이 여러 퀘스트/체인 목표를 동시에 진행할 수 있다.
- 같은 행동으로 여러 체인이 진행되더라도 각 체인의 완료 상태와 보상은 독립적으로 멱등 처리한다.
- 보상 수령 가능한 퀘스트는 관심 진로를 바꿔도 수령 가능해야 한다.
- 다음 단계 자동 오픈은 현재 관심 진로, 체인 상태, 조건 전략에 따라 제한할 수 있어야 한다.

헌법 규칙:
- AGENTS.md와 `.claude/rules/*`를 따른다.
- `Assets/**/*.cs`를 외부 디스크 쓰기로 직접 수정하지 않는다. C# 신규/수정은 반드시 Unity MCP `script-update-or-create` 또는 Unity Editor 안전 경로를 사용한다.
- 모든 게임 엔티티는 100% ScriptableObject 데이터 기반이어야 한다.
- questId, chainId, careerId, candidateId, npcId, locationId, activityId, rewardId별 `if/switch` 분기, enum 기반 엔티티 분기, 퀘스트별 C# 클래스 생성은 금지한다.
- 퀘스트 체인, 단계, 목표, 조건, 보상, 다음 단계 연결, 차단/실패/만료 정책은 SO 데이터와 전략 배열로 표현한다.
- 보상/인벤토리/마일스톤/도감/진로 힌트/퀘스트 완료 상태는 저장/로드 후 중복 적용되면 안 된다.
- TDD로 진행한다. 먼저 실패하는 테스트를 만들고 실패를 확인한 뒤 구현한다.
- 성능/최적화 동시 설계 원칙을 따른다.
- 기존 dirty 변경을 되돌리지 않는다.

권장 데이터 구조:
- `QuestChainDefinition`
  - 체인 표시명, 설명, 관련 관심 진로, 관련 후보, 관련 장소/NPC, 단계 배열, 시작 조건, 재개 조건, 실패/만료 정책, UI 그룹, 우선순위를 정의한다.
- `QuestStepDefinition`
  - 단계 표시명, 설명, 목표 배열, 완료 조건, 다음 단계 연결, 차단 조건, 보상 배열, 결과 이벤트를 정의한다.
- `QuestObjectiveBase[]`
  - 활동 완료, NPC 대화, 장소 방문, 아이템 획득/소모, 관계 수치, 특성/기술, 도감 발견, 하루 이벤트 결과, 진로 관심 상태를 일반 목표로 평가한다.
- `QuestConditionBase[]`
  - 시작/진행/재개/차단/실패/만료 조건을 전략 배열로 평가한다.
- `QuestRewardBase[]`
  - 인벤토리, 특성/기술, 진로 힌트, 도감, 마일스톤, 관계, 상태 변화, 다음 체인 해금을 일반 보상으로 지급한다.
- `QuestChainTransitionBase[]`
  - 다음 단계, 분기 단계, 대체 체인, 실패 후 재시도, 만료 후 후속 이벤트 연결을 데이터로 정의한다.
- `QuestChainProgress`
  - saveSlot + player identity 기준으로 체인 상태, 현재 단계, 목표 진행 수치, 완료 단계, 보상 수령 여부, 차단 이유, 만료 날짜, 추적 여부를 저장한다.
- `QuestChainLogPanel`
  - 체인 목록, 상태 필터, 관심 진로 필터, 단계 상세, 목표 진행도, 보상 상태, 차단/재개 조건, 우선 추적 버튼을 표시한다.
- `QuestChainHudWidget`
  - 우선 추적 체인의 현재 단계와 다음 행동을 HUD에 표시한다.

퀘스트 추가 확장성 검증:
- 새 퀘스트 체인은 C# 코드 수정 없이 ScriptableObject 데이터 추가와 Registry 등록만으로 추가 가능해야 한다.
- 테스트용 신규 퀘스트 체인 SO를 1개 이상 추가하고, 기존 런타임 코드를 수정하지 않은 상태에서 수락/진행/차단/재개/완료/보상/저장/로드가 동작하는지 검증한다.
- 퀘스트 목표/조건/보상/다음 단계 연결은 전략 배열 기반이어야 하며 questId, chainId, careerId, npcId, locationId별 if/switch 분기는 금지한다.
- 한 퀘스트는 여러 목표를 가질 수 있어야 한다.
- 한 행동이 여러 퀘스트 체인 목표를 동시에 진행시킬 수 있어야 하며, 각 체인의 보상과 완료 상태는 독립적으로 멱등 처리되어야 한다.
- 시간 제한, NPC 조건, 장소 조건, 관계 조건, 아이템 조건, 관심 진로 조건을 새 전략 또는 기존 전략 SO 조합으로 추가할 수 있어야 한다.
- 보상도 인벤토리, 특성/기술, 진로 힌트, 도감, 마일스톤, 관계, 상태 변화 등을 전략 배열로 추가할 수 있어야 한다.
- 퀘스트 로그 UI는 체인이 늘어나는 상황을 고려해 관심 진로, 상태, 장소/NPC 기준 필터 또는 그룹 표시를 제공해야 한다.
- 최종 보고에는 "퀘스트 추가 확장성 검증 체크리스트"를 포함하고, SO만으로 추가한 테스트 퀘스트 체인의 실제 플레이 검증 결과를 기록한다.

최우선 실제 플레이 검증 원칙:
- 이 goal은 실제 유저가 플레이하듯 검증하지 않으면 완료로 인정하지 않는다.
- 최소 1개 이상의 PlayMode E2E는 저장 슬롯 UI에서 시작해 실제 키보드 이동, 실제 NPC/장소/활동 상호작용, 실제 UI 버튼 선택, 퀘스트 체인 수락, 체인 진행, 관심 진로 변경 또는 체인 일시정지, 하루 종료, 결과 UI 확인, 저장/로드 재진입을 모두 거쳐야 한다.
- 테스트에서 QuestChainProgress, QuestLog, CareerInterestProgress, Inventory, SaveData 상태를 직접 세팅해서 성공 처리하면 실패다.
- 플레이어 Transform 직접 이동, 내부 메서드 직접 호출, 씬 강제 로드, 저장 데이터 직접 주입, UI 없이 도메인 API 직접 호출로 실제 플레이 경로를 대체하면 완료로 보고하지 않는다.
- 최종 보고 전에 "실제 플레이 방식 상호작용 검증 체크리스트"를 반드시 작성하고, 각 항목을 PASS/FAIL로 표시한다.

실제 플레이 방식 상호작용 검증 체크리스트:
- 저장 슬롯 UI에서 새 게임 또는 기존 슬롯을 실제 UI 경로로 시작했는가?
- 플레이어 이동이 Transform 직접 세팅이 아니라 키보드/입력 시스템 경로로 수행됐는가?
- NPC, 장소, 활동, 이벤트, 퀘스트 로그 UI가 실제 Prompt/Input/Button 경로로 열리고 수행됐는가?
- 퀘스트 체인 수락/추적/일시정지/재개/완료가 실제 UI 버튼과 상호작용 경로로 발생했는가?
- 관심 진로 변경 또는 다른 체인 추적으로 기존 체인이 `Paused` 또는 적절한 상태로 전환되는지 확인했는가?
- `Blocked` 상태가 실제 조건 부족으로 발생하고 UI에 이유/재개 조건이 표시되는지 확인했는가?
- 하루 종료가 내부 `EndDay()` 직접 호출이 아니라 실제 하루 종료 지점/상호작용으로 실행됐는가?
- 저장 슬롯 UI 재진입 후 같은 슬롯을 로드했을 때 체인 상태, 현재 단계, 목표 진행도, 보상 수령 여부, 차단/재개 상태가 유지되는가?
- 같은 목표/보상/완료 요청을 반복해도 중복 진행, 중복 로그, 중복 보상이 발생하지 않는가?
- 체크리스트 항목 중 하나라도 FAIL이면 완료로 보고하지 않고 실패 단계와 남은 작업을 보고했는가?

목표 플레이 흐름:
1. 저장 슬롯 UI로 새 게임 또는 기존 슬롯 로드 후 Town에 진입한다.
2. 플레이어가 실제 이동으로 관심 진로 관련 장소 또는 NPC에 접근한다.
3. 실제 Prompt/Input/Button 경로로 활동, NPC 대화, 이벤트, 탐험 중 하나를 수행한다.
4. 관심 진로 또는 후보 조건을 만족해 퀘스트 체인이 `Available` 상태로 표시된다.
5. 플레이어가 실제 입력 또는 UI 버튼으로 퀘스트 로그를 연다.
```
