# Clue Interpretation Branch Goal Prompt

아래 프롬프트를 goal 세션에 그대로 붙여 넣고 진행한다.

```text
ROOTBORN Unity 프로젝트에서 "플레이어가 발견한 단서/흔적을 여러 NPC, 장소, 활동, 오브젝트 경로로 해석할 수 있고, 해석 선택에 따라 진로 힌트, 도감 확장, 후속 퀘스트, 관계, 월드 변화가 달라지는 단서 해석 분기 루프"를 설계/구현/검증해줘.

핵심 의도:
- 단서는 하나의 정답으로 고정되지 않는다.
- 플레이어는 같은 단서를 사서에게 물어보거나, 공방 작업대에서 분석하거나, 상점 주인에게 보여주거나, 장소에서 직접 조사할 수 있어야 한다.
- 해석 경로에 따라 다른 성장, 관계, 퀘스트, 도감 설명, 월드 변화가 열려야 한다.
- 새 해석 경로는 C# 코드 수정 없이 ScriptableObject 데이터 추가와 Registry 등록만으로 추가 가능해야 한다.
- 싱글플레이에서 모든 해석 루프를 혼자 완료할 수 있어야 한다.

헌법 규칙:
- AGENTS.md와 `.claude/rules/*`를 따른다.
- `Assets/**/*.cs`를 외부 디스크 쓰기로 직접 수정하지 않는다. C# 신규/수정은 반드시 Unity MCP `script-update-or-create` 또는 Unity Editor 안전 경로를 사용한다.
- 모든 게임 엔티티는 100% ScriptableObject 데이터 기반이어야 한다.
- clueId, interpretationId, npcId, locationId, objectId, activityId, questId, careerId별 `if/switch` 분기, enum 기반 엔티티 분기, 해석 경로별 C# 클래스 생성은 금지한다.
- 해석 source, 조건, 결과, 독점/비독점/순차 정책, 반복/소모 정책은 SO 데이터와 전략 배열로 표현한다.
- 도감/진로 힌트/퀘스트/관계/월드 변화/보상은 저장/로드 후 중복 적용되면 안 된다.
- TDD로 진행한다. 먼저 실패하는 테스트를 만들고 실패를 확인한 뒤 구현한다.
- 성능/최적화 동시 설계 원칙을 따른다.
- 기존 dirty 변경을 되돌리지 않는다.

권장 데이터 구조:
- `ClueInterpretationDefinition`
  - 어떤 `DiscoveryClueDefinition`에 연결되는 해석 경로인지 정의한다.
  - 표시명, 설명, 해석 방식, 공개/숨김 텍스트, 관련 NPC/장소/오브젝트/활동, 조건, 결과, 정책을 포함한다.
- `ClueInterpretationSourceBase[]`
  - NPC 대화, 장소 조사, 작업대/오브젝트 사용, 도서관 열람, 게시판 기록, 지도 확인 같은 해석 source를 정의한다.
- `ClueInterpretationConditionBase[]`
  - 단서 발견 여부, NPC 관계도, 관심 진로, 시간대, 장소 발견, 아이템 보유, 월드 상태, 퀘스트 상태를 일반 조건으로 평가한다.
- `ClueInterpretationOutcomeBase[]`
  - 진로 힌트, 도감 항목 확장, 후속 퀘스트, 관계 변화, 월드 상태 변화, 새 단서, 활동 해금을 일반 결과로 처리한다.
- `ClueInterpretationPolicyDefinition`
  - 독점, 비독점, 순차, 반복 가능, 1회성, 아이템 소모, 쿨다운 정책을 데이터로 정의한다.
- `ClueInterpretationProgress`
  - saveSlot + player identity 기준으로 해석 가능 여부, 선택한 해석 경로, 완료 여부, 보상 수령 여부, 열린/잠긴 해석 후보, 마지막 해석 날짜를 저장한다.
- `ClueInterpretationSummaryModel`
  - 단서 상세 UI, NPC 대화 UI, 장소/오브젝트 UI, 도감 UI에서 공통으로 사용하는 표시 모델이다.

해석 정책:
- `Exclusive`
  - 하나의 해석 경로를 완료하면 같은 그룹의 다른 해석 경로는 닫힌다.
  - UI에는 닫힌 이유와 선택 결과 요약을 표시한다.
- `NonExclusive`
  - 같은 단서의 여러 해석 경로를 모두 완료할 수 있다.
  - 각 해석 결과와 보상은 독립적으로 멱등 처리한다.
- `Sequential`
  - 특정 해석을 완료해야 다음 해석이 열린다.
  - 예: 사서에게 지도 설명을 들은 뒤 공방 작업대에서 복원 가능.
- `Repeatable`
  - 반복 해석 가능. 쿨다운/일일 제한/보상 제한은 데이터로 정의한다.

초기 예시:
- `오래된 지도 조각`
  - 사서에게 보여주기
    - 조건: 도서관 자료실 개방, 사서 관계 1 이상
    - 결과: 탐험·정보형 진로 힌트, 도감 설명 확장, 후속 조사 퀘스트 후보
  - 공방 작업대에서 복원하기
    - 조건: 공방 작업대 등장, 도구 보유 또는 기술·작업형 관심 진로
    - 결과: 지도 복원 활동, 기술형 힌트, 숨은 길 단서
  - 상점 주인에게 물어보기
    - 조건: 상점 방문, 상점 주인 관계 1 이상
    - 결과: 오래된 거래 기록 소문, 관계형 힌트, 상점 후속 이벤트
- `이상한 부품`
  - 공방 관리자에게 분석 요청
    - 결과: 기술형 힌트, 수리 퀘스트
  - 학교 선생님에게 질문
    - 결과: 학습형 힌트, 이론 조사 활동
  - 광장 NPC에게 보여주기
    - 결과: 소문 확산, 관계 이벤트, 새 단서

UI 요구:
- 단서 상세 UI는 발견한 단서 설명과 가능한 해석 후보 목록을 표시한다.
- 잠긴 해석 후보는 `???`와 부족 조건 일부만 표시한다.
- 완료한 해석 후보는 결과 요약과 다시 볼 수 있는 기록을 표시한다.
- NPC 대화 UI에는 "이 단서에 대해 묻기" 선택지를 제공하고, 해당 NPC가 해석 가능한 단서만 표시한다.
- 장소/오브젝트 UI에는 "단서 조사하기", "작업대에서 복원하기" 같은 실제 상호작용 선택지를 제공한다.
- 도감 UI는 해석 결과에 따라 단서 설명이 확장되어야 한다.
- 같은 단서라도 해석 경로에 따라 다른 도감 문단이 열릴 수 있어야 한다.
- UI는 특정 clueId/interpretationId를 직접 알지 않고 `ClueInterpretationSummaryModel`을 렌더링한다.
- Modern UI Style2 공통 패널 규약을 따른다.
- 1920x1080 기준에서 단서명, 해석명, 조건, 결과, 버튼 텍스트가 겹치거나 잘리지 않아야 한다.
- UI는 문서 목업만 만들고 끝내면 안 된다. PlayMode에서 실제로 열리고 클릭 가능해야 한다.

확장성 검증:
- 새 해석 경로는 C# 코드 수정 없이 ScriptableObject 데이터 추가와 Registry 등록만으로 추가 가능해야 한다.
- 테스트용 단서 1개에 해석 경로 3개 이상을 SO만으로 추가한다.
- 기존 런타임 코드를 수정하지 않은 상태에서 NPC 대화, 장소 조사, 오브젝트 상호작용 중 2개 이상의 해석 경로가 실제 플레이로 동작해야 한다.
- 하나의 단서에 여러 해석 경로를 연결할 수 있어야 한다.
- 하나의 해석 경로가 여러 조건과 여러 결과를 가질 수 있어야 한다.
- 독점/비독점/순차 정책 중 최소 2개 이상을 테스트 데이터로 검증한다.
- 같은 해석 결과를 반복 확인해도 중복 보상, 중복 도감 확장, 중복 퀘스트 해금, 중복 진로 힌트가 발생하지 않아야 한다.
- 최종 보고에는 "단서 해석 분기 확장성 검증 체크리스트"를 포함하고, SO만으로 추가한 테스트 해석 경로의 실제 플레이 검증 결과를 기록한다.

최우선 실제 플레이 검증 원칙:
- 이 goal은 실제 유저가 플레이하듯 검증하지 않으면 완료로 인정하지 않는다.
- 최소 1개 이상의 PlayMode E2E는 저장 슬롯 UI에서 시작해 실제 키보드 이동, 실제 NPC/장소/오브젝트/도감 UI 상호작용, 실제 UI 버튼 선택, 해석 경로 선택, 결과 확인, 저장/로드 재진입을 모두 거쳐야 한다.
- 테스트에서 ClueInterpretationProgress, DiscoveryClueProgress, WorldStateProgress, QuestLog, Inventory, SaveData 상태를 직접 세팅해서 성공 처리하면 실패다.
- 플레이어 Transform 직접 이동, 내부 메서드 직접 호출, 씬 강제 로드, 저장 데이터 직접 주입, UI 없이 도메인 API 직접 호출로 실제 플레이 경로를 대체하면 완료로 보고하지 않는다.
- 최종 보고 전에 "실제 플레이 방식 상호작용 검증 체크리스트"를 반드시 작성하고, 각 항목을 PASS/FAIL로 표시한다.

실제 플레이 방식 상호작용 검증 체크리스트:
- 저장 슬롯 UI에서 새 게임 또는 기존 슬롯을 실제 UI 경로로 시작했는가?
- 플레이어 이동이 Transform 직접 세팅이 아니라 키보드/입력 시스템 경로로 수행됐는가?
- 단서 발견이 실제 NPC/게시판/지도/도감/장소 흔적 경로로 발생했는가?
- NPC 대화, 장소 조사, 오브젝트 상호작용 중 2개 이상의 해석 경로를 실제 Prompt/Input/Button 경로로 확인했는가?
- 플레이어가 실제 UI에서 해석 경로를 선택하고 완료했는가?
- 해석 결과가 도감 확장, 진로 힌트, 후속 퀘스트, 관계 변화, 월드 상태 변화, 새 단서 중 최소 2개 이상으로 이어졌는가?
- 독점/비독점/순차 정책 중 최소 2개 이상이 실제 플레이 또는 PlayMode 경로로 검증됐는가?
- 저장 슬롯 UI 재진입 후 같은 슬롯을 로드했을 때 선택한 해석, 완료 여부, 보상 수령 여부, 도감 확장 상태가 유지되는가?
- 같은 해석을 반복 확인해도 중복 보상/중복 해금/중복 확장이 발생하지 않는가?
- 테스트용 신규 해석 경로가 SO만으로 추가되어 실제 플레이 경로에서 노출/선택/완료/저장/로드됐는가?
- 체크리스트 항목 중 하나라도 FAIL이면 완료로 보고하지 않고 실패 단계와 남은 작업을 보고했는가?

싱글/멀티 정책:
- 싱글플레이에서 혼자 모든 단서 해석 루프를 완료할 수 있어야 한다.
- 해석 선택, 보상, 도감 확장, 진로 힌트, 후속 퀘스트 수락/보상 상태는 기본 Personal이다.
- 단서 source가 Shared 월드 변화로 생긴 경우 source는 모든 클라이언트가 볼 수 있다.
- Client 1이 사서에게 해석했다고 해서 Client 2의 해석 선택이 강제로 닫히면 안 된다.
- 단, 해석 결과가 Shared 월드 상태를 활성화하는 경우 서버 권한으로 모든 클라이언트에 반영 가능하다.
- 멀티플레이 직접 검증이 이번 범위에 포함되면 실제 클라이언트 2개 이상 또는 Host+Client를 띄워 Shared source와 Personal 해석 선택 분리를 확인한다.
- 멀티플레이 직접 검증이 범위 밖이면 최종 보고에 후속 NET 테스트 계획을 명시한다.

목표 플레이 흐름:
1. 저장 슬롯 UI로 새 게임 또는 기존 슬롯 로드 후 Town에 진입한다.
2. 실제 플레이로 단서를 발견한다.
3. 단서 상세 UI 또는 도감 UI에서 해석 가능한 후보를 확인한다.
4. 플레이어가 실제 이동으로 해석 가능한 NPC에게 접근한다.
5. 실제 대화 UI에서 "이 단서에 대해 묻기" 선택지를 선택한다.
6. 다른 경로로 실제 이동해 장소 조사 또는 오브젝트 상호작용 해석 후보도 확인한다.
7. 플레이어가 하나의 해석 경로를 실제 UI 버튼으로 선택하고 완료한다.
8. 해석 결과로 도감 확장, 진로 힌트, 후속 퀘스트, 관계 변화, 월드 상태 변화, 새 단서 중 최소 2개 이상이 발생한다.
9. 단서 상세 UI와 도감 UI에서 완료한 해석 결과가 표시된다.
10. 독점/비독점/순차 정책 중 최소 2개 이상이 UI와 도메인 상태에 반영된다.
11. 저장 슬롯 UI로 같은 슬롯을 다시 로드한다.
12. 재로드 후 선택한 해석, 완료 여부, 보상 수령 여부, 도감 확장 상태가 유지되는지 확인한다.
13. 같은 해석을 반복 확인해 중복 보상/중복 해금/중복 확장이 발생하지 않는지 확인한다.
14. SO만으로 추가한 테스트 해석 경로도 같은 흐름으로 노출/선택/완료/저장/로드한다.

필수 저장 데이터:
- saveSlot
- player identity
- clue id
- interpretation id
- available interpretation ids
- selected interpretation ids
- completed interpretation ids
- locked interpretation ids and reason summaries
- policy group state
- reward claimed flags
- encyclopedia expansion ids
- career hint grant history
- follow-up quest ids
- related world state changes
- today interpretation summary

필수 EditMode 테스트:
- CLUE-INTERPRET-EDIT-001: ClueInterpretationDefinition/source/condition/outcome/policy 전략이 Registry 또는 지정 데이터 경로에서 로드된다.
- CLUE-INTERPRET-EDIT-002: 테스트용 단서 1개에 3개 이상 해석 경로가 C# 코드 수정 없이 SO 추가와 Registry 등록만으로 로드된다.
- CLUE-INTERPRET-EDIT-003: 해석 가능 조건은 clueId/npcId/locationId/objectId별 if/switch 없이 전략 배열로 평가된다.
- CLUE-INTERPRET-EDIT-004: NPC 대화, 장소 조사, 오브젝트 상호작용 source summary가 같은 단서에서 생성된다.
- CLUE-INTERPRET-EDIT-005: 해석 결과는 도감/진로 힌트/후속 퀘스트/관계/월드 상태/새 단서를 전략 배열로 적용한다.
- CLUE-INTERPRET-EDIT-006: Exclusive 정책이 완료된 해석 그룹의 다른 후보를 닫고 이유를 생성한다.
```
