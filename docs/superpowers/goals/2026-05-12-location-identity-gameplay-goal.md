# Location Identity Gameplay Goal Prompt

아래 프롬프트를 goal 세션에 그대로 붙여 넣고 진행한다.

```text
ROOTBORN Unity 프로젝트에서 "Town의 학교, 도서관, 일터/공장, 상점, 광장, 집, 골목/외곽이 각각 고유 활동, NPC 대사, 도감 항목, 마일스톤 힌트, 학교 밖 성장 루트를 가지며, 플레이어가 실제 이동으로 장소를 방문했을 때 장소마다 다른 선택과 보상이 느껴지는 장소 정체성 루프"를 설계/구현/검증해줘.

전제:
- `2026-05-12-town-locations-npc-foundation-goal.md`가 완료되어 주요 장소와 핵심 NPC가 SO 데이터 및 실제 Town 배치로 존재한다.
- 장소/NPC 발견 상태는 저장/로드되며 도감 또는 임시 발견 UI와 연결되어 있다.
- 학교 밖 성장 기반, 도움 행동, 독학, 알바, 탐험, 마일스톤, 도감 goal과 연결될 수 있는 데이터 경계가 존재한다.

이 goal은 장소/NPC를 새로 대량 추가하는 작업이 아니다. 이미 존재하는 장소와 NPC에 "장소별로 고유한 플레이 이유"를 부여하는 작업이다.

핵심 의도:
1. Town의 각 장소가 단순 배경이 아니라 고유 행동과 보상 구조를 가진 생활 공간이 되게 한다.
2. 플레이어가 학교만 따라가지 않고 장소를 선택해 성장 경로를 만들 수 있어야 한다.
3. 같은 하루라도 학교, 도서관, 일터, 광장, 집, 골목 중 어디를 가느냐에 따라 성장/관계/컨디션/진로 힌트가 다르게 움직여야 한다.
4. 장소 정체성은 ScriptableObject 데이터와 전략 배열로 표현하고, 후속 스케줄/이벤트/멀티플레이 확장을 막지 않아야 한다.

최우선 검증 원칙:
- 이 goal은 실제 유저가 플레이하듯 검증하지 않으면 완료로 인정하지 않는다.
- 최소 1개 이상의 PlayMode E2E는 저장 슬롯 UI, 실제 키보드 이동, 장소 방문, 장소별 상호작용, 결과 UI, 하루 종료, 저장/로드 재진입을 모두 거쳐야 한다.
- 최소 2개 이상의 서로 다른 장소에서 서로 다른 결과/선택/보상이 발생하는지 실제 플레이 경로로 확인해야 한다.
- 테스트에서 LocationIdentityProgress, StudentLifeProgress, Trait/Skill/Quest/Inventory/Relationship/Status 상태를 직접 세팅해서 성공 처리하면 실패다.
- 플레이어 Transform 직접 이동, 내부 메서드 직접 호출, 씬 강제 로드, 저장 데이터 직접 주입으로 실제 플레이 경로를 대체하면 완료로 보고하지 않는다.

절대 규칙:
- AGENTS.md와 `.claude/rules/*`를 따른다.
- `Assets/**/*.cs`는 디스크 직접 쓰기 금지. C# 신규/수정은 반드시 Unity MCP `script-update-or-create` 또는 Unity Editor 안전 경로를 사용한다.
- 모든 게임 엔티티는 100% ScriptableObject 데이터 기반이어야 한다.
- locationId, activityId, npcId, eventId, questId, traitId, statusId별 `if/switch` 분기, enum 기반 엔티티 분기, 장소별 C# 클래스 생성은 금지한다.
- 장소별 활동, 요구 조건, 보상, 대사, 도감 힌트, 마일스톤 힌트는 SO 데이터와 전략 배열로 표현한다.
- 학교 수업은 여러 장소 성장 루트 중 하나일 뿐 유일한 정답이 아니어야 한다.
- 성능·최적화 동시 설계 원칙을 따른다.
- TDD로 진행한다. 먼저 실패하는 테스트를 만들고 실패를 확인한 뒤 구현한다.
- 기존 dirty 변경 되돌리기 금지.

장소별 기획:

1. `학교`
   - 정체성: 공식 학습, 교사 피드백, 기본 진로 힌트.
   - 고유 활동:
     - 짧은 수업 참여
     - 교사에게 질문
     - 학교 게시판 확인
   - 성장 방향:
     - 성실함, 기초 학습 스킬, 진로 힌트
   - 비용/리스크:
     - 시간, 집중, 약간의 피로
   - 도감/마일스톤 연결:
     - 학교 장소 도감
     - 교사 NPC 도감
     - "나만의 학습 방식 찾기" 마일스톤 진행

2. `도서관`
   - 정체성: 독학, 지식 해금, 조용한 성장.
   - 고유 활동:
     - 쉬운 책 읽기
     - 어려운 책 읽기
     - 사서에게 추천 받기
   - 성장 방향:
     - 지식, 기초 학습 스킬, 집중 관리, 진로 힌트
   - 비용/리스크:
     - 집중 소모, 피로 증가. 어려운 책은 조건 부족 시 실패 또는 작은 보상.
   - 도감/마일스톤 연결:
     - 지식 도감 항목 해금
     - "나만의 학습 방식 찾기" 진행

3. `일터/공장/작업장`
   - 정체성: 알바, 돈, 책임감, 기술/직업 힌트.
   - 고유 활동:
     - 짧은 알바
     - 작업 돕기
     - 관리자에게 일거리 묻기
   - 성장 방향:
     - 돈/아이템, 책임감, 체력 또는 기술 계열 힌트, 관리자 관계
   - 비용/리스크:
     - 피로 증가, 시간 소모. 컨디션이 낮으면 보상 감소 또는 실패 가능.
   - 도감/마일스톤 연결:
     - 일터 장소 도감
     - 알바 활동 도감
     - "진로의 단서" 또는 경제 관련 마일스톤 진행

4. `상점`
   - 정체성: 경제, 아이템, 주민 의뢰, 소비/준비.
   - 고유 활동:
     - 물건 둘러보기
     - 상점 주인과 대화
     - 작은 심부름 수락
   - 성장 방향:
     - 아이템/자원 이해, 상점 주인 관계, 사교성, 퀘스트
   - 비용/리스크:
     - 돈 사용 또는 심부름 시간 소모
   - 도감/마일스톤 연결:
     - 아이템/자원 도감
     - 상점 NPC 도감
     - 도움 행동/알바/퀘스트 루트 진입

5. `광장`
   - 정체성: 주민 만남, 게시판, 도움 행동, 마을 소식.
   - 고유 활동:
     - 게시판 확인
     - 주민과 대화
     - 도움 요청 찾기
   - 성장 방향:
     - 관계, 사교성, 도움 행동, 퀘스트 시작, 장소 힌트
   - 비용/리스크:
     - 시간 소모. 선택에 따라 관계/컨디션 결과가 다름.
   - 도감/마일스톤 연결:
     - NPC 도감
     - 도움 행동 루트
     - "마을에 적응하기", "첫 관계 만들기" 진행

6. `집`
   - 정체성: 휴식, 하루 종료, 컨디션 회복, 목표/도감 확인.
   - 고유 활동:
     - 짧은 휴식
     - 하루 정리
     - 도감/마일스톤 확인
   - 성장 방향:
     - 피로 회복, 집중 회복, 컨디션 관리 지식
   - 비용/리스크:
     - 시간 소모. 성장 직접 보상은 작지만 다음 행동 효율을 높임.
   - 도감/마일스톤 연결:
     - "하루 균형 잡기" 진행
     - 도감/목표 UI 접근 지점

7. `골목/외곽`
   - 정체성: 탐험, 발견, 작은 이벤트, 숨은 진로/지식 단서.
   - 고유 활동:
     - 주변 살펴보기
     - 이상한 단서 조사
     - 숨은 장소 발견
   - 성장 방향:
     - 탐험 발견, 지식, 진로 힌트, 호기심 계열 성향
   - 비용/리스크:
     - 시간/피로 소모. 컨디션이 낮으면 이벤트 선택 제한 가능.
   - 도감/마일스톤 연결:
     - 장소/지식/진로 힌트 도감
     - "진로의 단서", 탐험 마일스톤 진행

권장 데이터 구조:
- `LocationIdentityDefinition`
  - 장소 참조, 정체성 설명, 고유 활동 배열, 관련 NPC 대사 세트, 도감 힌트, 마일스톤 힌트, 추천 방문 시간대를 정의한다.
- `LocationActivityDefinition`
  - 장소에서 수행할 수 있는 고유 행동을 정의한다.
  - 기존 `LifeActivityDefinition` 또는 `OutsideSchoolActivityDefinition`을 재사용할 수 있으면 새 타입을 만들지 말고 참조 구조로 둔다.
- `LocationActivityRequirementBase[]`
  - 시간대, 컨디션, 관계, 장소 방문 여부, 도감 해금 여부, 마일스톤 상태를 일반 전략으로 평가한다.
- `LocationActivityOutcomeBase[]`
  - 특성/성향, 스킬, 관계, 컨디션, 지식, 진로 힌트, 인벤토리, 퀘스트 이벤트, 마일스톤 진행을 일반 전략으로 적용한다.
- `LocationHintEntry`
  - 도감/마일스톤/퀘스트에 표시할 장소별 힌트를 데이터로 정의한다.
- `LocationIdentityPanel` 또는 기존 발견/도감 UI 연동
  - 플레이어가 장소에 들어왔을 때 가능한 활동과 장소 설명을 보여준다.
- `LocationActivityInteractor`
  - 장소별 활동을 실제 플레이 상호작용으로 실행한다.

기존 구조 재사용 원칙:
- `LocationDefinition`, `NpcDefinition`, `OutsideSchoolActivityDefinition`, `LifeActivityDefinition`, `MilestoneDefinition`, `EncyclopediaEntryDefinition`이 존재하면 우선 재사용한다.
- 장소별 정체성 때문에 장소별 C# 컴포넌트가 늘어나면 안 된다.
- UI는 장소별 하드코딩이 아니라 데이터에서 받은 activity/hint/entry 배열을 렌더링한다.
- 저장 데이터는 후속 장소가 늘어도 필드가 계속 추가되지 않도록 일반 로그/상태 배열을 사용한다.

목표 플레이 흐름:
1. 저장 슬롯 UI로 새 게임 또는 기존 슬롯을 로드해 Town에 진입한다.
2. 플레이어가 실제 이동으로 광장에 접근한다.
3. 광장에서 게시판/주민/도움 행동 같은 광장 고유 상호작용을 실제 입력으로 수행한다.
4. 결과로 관계, 도움 행동 로그, 퀘스트, 도감, 마일스톤 중 하나 이상이 변화한다.
5. 플레이어가 실제 이동으로 도서관 또는 일터/공장에 접근한다.
6. 해당 장소에서 독학 또는 알바/작업 돕기 같은 다른 성격의 상호작용을 실제 입력으로 수행한다.
7. 두 장소의 결과가 서로 다른 성장 방향으로 반영된다.
8. 장소별 가능 활동/힌트/피드백 UI가 실제 화면에 표시된다.
9. 플레이어가 실제 이동으로 하루 종료 지점에 접근해 하루를 종료한다.
10. 하루 결과 UI에 장소별 활동과 성장/관계/컨디션/도감/마일스톤 변화가 표시된다.
11. 저장 슬롯 UI로 같은 슬롯을 다시 로드해도 장소별 활동 결과와 해금 상태가 유지된다.
12. 같은 장소 활동 또는 같은 하루 결과를 재호출해도 중복 보상/중복 성장/중복 도감 해금이 발생하지 않는다.

자유 경로 검증 요구:
- 최소 2개 이상의 서로 다른 장소에서 성장 가능한 경로를 실제 플레이로 검증한다.
- 최소 1개 이상의 학교 밖 장소에서 학교 수업 없이 특성·성향·스킬·진로 힌트·관계·컨디션·퀘스트·도감·마일스톤 중 하나 이상이 진행되어야 한다.
- 학교 장소는 유일 정답이 아니라 다른 장소 루트와 나란히 존재해야 한다.

UI/목업 요구:
- 장소별 가능 활동 또는 힌트를 보여주는 1차 UI를 만든다.
- 문서 목업만으로 완료하지 않는다.
- 최소한 장소 이름, 장소 정체성 한 줄, 가능한 활동 1~3개, 선택/상호작용 버튼 또는 프롬프트가 화면에 보여야 한다.
- Modern UI Style2 공통 패널 규약을 따른다.
- 1920x1080 기준에서 장소 이름, 활동명, 설명, 버튼 텍스트가 겹치지 않아야 한다.

성능/최적화 요구:
- 장소별 활동 목록은 UI 열림/장소 진입/조건 변경 시점에만 갱신하고 매 프레임 재계산하지 않는다.
- 장소/활동/힌트 lookup은 Registry 전체 반복 순회 대신 캐시를 사용한다.
- 장소별 UI 항목은 pool 또는 재사용 구조를 우선한다.
- 장소 수와 활동 수가 늘어나도 매 프레임 거리 계산/전체 검색이 폭증하지 않도록 Collider/InteractionRouter 기반 탐지를 우선한다.
- 최종 보고에는 장소/활동 수 증가 시 성능 리스크와 후속 최적화 과제를 포함한다.

멀티플레이 확장 고려:
- 장소 정체성 데이터와 가능한 활동 정의는 공유 월드 데이터다.
- 장소 활동 결과, 도감 해금, 관계, 컨디션, 마일스톤 진행은 기본적으로 플레이어별 개인 상태다.
- 공유 월드 오브젝트 소모 또는 장소 이벤트는 별도 공유 상태로 분리한다.
- 멀티플레이에서는 서버 권한으로 장소 활동 요청을 검증하고 개인 상태 변화를 확정할 수 있어야 한다.
- NPC 위치/스케줄과 장소 활성 상태는 추후 서버 권한 공유 월드 상태로 승격 가능해야 한다.
- 이번 goal에서 멀티플레이 직접 검증이 범위 밖이면 최종 보고에 후속 검증 항목과 리스크를 명시한다.

필수 저장 대상:
- saveSlot
- player identity
- 장소별 수행한 활동 로그
```
