# Quest Driven World State Goal Prompt

아래 프롬프트를 goal 세션에 그대로 붙여 넣고 진행한다.

```text
ROOTBORN Unity 프로젝트에서 "퀘스트 체인 완료/분기/실패 결과가 장소, NPC, 상호작용, 상점, 이벤트 가능 여부 같은 월드 상태 변화로 이어지고, 이 변화가 저장/로드 후에도 유지되며, 새 월드 변화는 ScriptableObject 데이터만 추가해 확장 가능한 구조"를 설계/구현/검증해줘.

핵심 의도:
- 퀘스트 보상은 아이템/수치만이 아니라 마을에 실제 흔적을 남겨야 한다.
- 도서관 자료실 개방, 공방 작업대 등장, 상점 품목 추가, NPC 대사 변화, 숨은 길 개방, 하루 이벤트 가능 여부 같은 변화가 퀘스트 결과로 발생해야 한다.
- 월드 상태 변화는 UI와 로직에 하드코딩하지 않고 `WorldStateFlagDefinition` 같은 SO 데이터로 정의한다.
- 새 월드 상태 변화는 C# 코드 수정 없이 SO 추가와 Registry 등록만으로 추가 가능해야 한다.
- UI는 특정 flagId를 알지 않고, SO가 제공하는 표시명/설명/아이콘/관련 장소/NPC/다음 행동/범위 정보를 공통 카드로 렌더링해야 한다.
- 멀티플레이에서는 마을에 시각적/기능적으로 드러나는 변화는 기본 Shared로 처리하고, 개인 성장/보상/진행도는 Personal로 분리한다.
- 멀티플레이 검증은 필수다. 최소 2개 이상의 실제 클라이언트 또는 Host+Client를 띄워 각 클라이언트에서 직접 플레이 상호작용으로 Shared/Personal 동작을 확인해야 한다.
- 실제 유저가 플레이하듯 저장 슬롯 UI, 이동, NPC/장소 상호작용, 퀘스트 완료, 월드 변화 확인, 저장/로드 재확인을 거쳐 검증해야 한다.

헌법 규칙:
- AGENTS.md와 `.claude/rules/*`를 따른다.
- `Assets/**/*.cs`를 외부 디스크 쓰기로 직접 수정하지 않는다. C# 신규/수정은 반드시 Unity MCP `script-update-or-create` 또는 Unity Editor 안전 경로를 사용한다.
- 모든 게임 엔티티는 100% ScriptableObject 데이터 기반이어야 한다.
- flagId, questId, chainId, npcId, locationId, shopId, objectId, eventId별 `if/switch` 분기, enum 기반 엔티티 분기, 월드 변화별 C# 클래스 생성은 금지한다.
- 월드 상태 조건, 적용 효과, UI 표시 규칙, 저장 범위, 멀티플레이 범위는 SO 데이터와 전략 배열로 표현한다.
- 보상/인벤토리/마일스톤/도감/퀘스트/월드 상태 변화는 저장/로드 후 중복 적용되면 안 된다.
- TDD로 진행한다. 먼저 실패하는 테스트를 만들고 실패를 확인한 뒤 구현한다.
- 성능/최적화 동시 설계 원칙을 따른다.
- 기존 dirty 변경을 되돌리지 않는다.

권장 데이터 구조:
- `WorldStateFlagDefinition`
  - 표시명, 설명, 관련 장소, 관련 NPC, 관련 퀘스트 체인, 관련 관심 진로, 변화 타입, UI 표시 여부, 아이콘/배지, 다음 행동, 저장 범위, 우선순위를 정의한다.
- `WorldStateScopeDefinition`
  - 개인 상태, 공유 월드 상태, 세이브 슬롯 전체 상태 같은 범위를 데이터로 정의한다.
- `WorldStateConditionBase[]`
  - 플래그 활성 여부, 장소 개방 조건, NPC 대사 조건, 상점 품목 조건, 이벤트 가능 조건, 오브젝트 표시 조건을 일반 조건으로 평가한다.
- `WorldStateChangeRewardBase[]`
  - 퀘스트 완료/분기/실패/만료 결과로 월드 상태 플래그를 활성화/비활성화/갱신한다.
- `WorldStateEffectBase[]`
  - 오브젝트 표시/숨김, Collider/Portal 활성화, NPC 대사 세트 변경, 상점 품목 추가, 상호작용 추가, 이벤트 후보 추가를 데이터 전략으로 적용한다.
- `WorldStateProgress`
  - saveSlot + player identity 또는 shared scope 기준으로 활성 플래그, 활성 날짜, 원인 퀘스트/이벤트, 이미 표시한 알림 여부를 저장한다.
- `WorldStateSummaryModel`
  - UI가 사용하는 공통 표시 모델이다. UI는 flagId별 분기 없이 이 모델만 렌더링한다.
- `WorldStateChangeCard`
  - 하루 결과 UI, 지도/장소 UI, 월드 로그 UI에서 재사용하는 공통 카드다.

초기 월드 변화 예시:
- `도서관 자료실 개방`
  - 관련 장소: 도서관
  - 관련 NPC: 사서
  - 변화 타입: 장소 개방
  - 다음 행동: 도서관 뒤편 자료실 확인
- `공방 수리 작업대 등장`
  - 관련 장소: 공방
  - 관련 NPC: 작업 관리자
  - 변화 타입: 오브젝트/상호작용 추가
  - 다음 행동: 수리 작업대 사용
- `상점 새 품목 입고`
  - 관련 장소: 상점
  - 관련 NPC: 상점 주인
  - 변화 타입: 상점 품목 추가
  - 다음 행동: 상점에서 새 물건 확인
- `골목 숨은 길 개방`
  - 관련 장소: 골목 또는 마을 외곽
  - 변화 타입: 포탈/장소 개방
  - 다음 행동: 숨은 길 탐험
- `NPC 대사/스케줄 변화`
  - 관련 NPC: 퀘스트 대상 NPC
  - 변화 타입: 대사 세트 또는 스케줄 조건 변화
  - 다음 행동: 다른 시간대에 NPC 만나기

UI 확장성 방향:
- UI는 특정 월드 변화 이름이나 flagId를 직접 알면 안 된다.
- UI는 `WorldStateSummaryModel` 목록을 받아 공통 `WorldStateChangeCard`로 렌더링한다.
- 같은 월드 변화 데이터는 최소 2개 이상의 UI에서 재사용한다.
  - 하루 결과 UI: "오늘 마을에 생긴 변화" 요약
  - 지도/장소 UI: 장소별 개방/변화 배지
  - 월드 로그 UI 또는 도감: 지금까지 발생한 마을 변화 기록
- 필터 기준은 장소, NPC, 퀘스트 체인, 관심 진로, 변화 타입, 개인/공유 범위를 지원한다.
- `Blocked`, `Locked`, `New`, `Seen`, `Shared`, `Personal` 같은 UI 배지는 데이터에서 생성한다.
- 새 `WorldStateFlagDefinition`을 추가하면 UI 코드 수정 없이 하루 결과 UI와 월드 로그 UI 중 최소 2곳에 자동 반영되어야 한다.
- Modern UI Style2 공통 패널 규약을 따른다.
- 1920x1080 기준에서 변화명, 설명, 장소/NPC, 다음 행동, 버튼 텍스트가 겹치거나 잘리지 않아야 한다.
- UI는 문서 목업만 만들고 끝내면 안 된다. PlayMode에서 실제로 열리고 클릭 가능해야 한다.

확장성 검증:
- 새 월드 상태 변화는 C# 코드 수정 없이 ScriptableObject 데이터 추가와 Registry 등록만으로 추가 가능해야 한다.
- 테스트용 신규 `WorldStateFlagDefinition`을 1개 이상 추가하고, 기존 런타임 코드를 수정하지 않은 상태에서 퀘스트 보상으로 활성화, UI 표시, 저장/로드 복원까지 검증한다.
- 월드 상태 조건/효과/보상/표시 규칙은 전략 배열 기반이어야 하며 flagId, questId, locationId, npcId별 if/switch 분기는 금지한다.
- 같은 퀘스트 결과가 여러 월드 상태 플래그를 동시에 활성화할 수 있어야 한다.
- 같은 월드 상태 플래그가 여러 퀘스트/이벤트 결과에서 활성화될 수 있어야 하며, 중복 활성화/중복 알림/중복 보상이 발생하지 않아야 한다.
- 하나의 월드 상태 플래그가 장소, NPC, 상점, 이벤트, 도감 UI에 동시에 영향을 줄 수 있어야 한다.
- 최종 보고에는 "월드 상태 추가 확장성 검증 체크리스트"를 포함하고, SO만으로 추가한 테스트 플래그의 실제 플레이 검증 결과를 기록한다.

최우선 실제 플레이 검증 원칙:
- 이 goal은 실제 유저가 플레이하듯 검증하지 않으면 완료로 인정하지 않는다.
- 최소 1개 이상의 PlayMode E2E는 저장 슬롯 UI에서 시작해 실제 키보드 이동, 실제 NPC/장소/활동 상호작용, 실제 UI 버튼 선택, 퀘스트 체인 진행/완료, 월드 상태 변화 확인, 하루 종료, 결과 UI 확인, 저장/로드 재진입을 모두 거쳐야 한다.
- 최소 1개 이상의 멀티플레이 E2E는 실제 클라이언트 2개 이상 또는 Host+Client를 실행한 상태에서 진행해야 한다.
- 멀티플레이 E2E에서도 Client 1과 Client 2 모두 실제 저장 슬롯 UI, 실제 이동, 실제 NPC/장소/활동 상호작용, 실제 UI 확인 경로를 사용해야 한다.
- 테스트에서 WorldStateProgress, QuestChainProgress, QuestLog, Inventory, SaveData 상태를 직접 세팅해서 성공 처리하면 실패다.
- 플레이어 Transform 직접 이동, 내부 메서드 직접 호출, 씬 강제 로드, 저장 데이터 직접 주입, UI 없이 도메인 API 직접 호출로 실제 플레이 경로를 대체하면 완료로 보고하지 않는다.
- 최종 보고 전에 "실제 플레이 방식 상호작용 검증 체크리스트"를 반드시 작성하고, 각 항목을 PASS/FAIL로 표시한다.

실제 플레이 방식 상호작용 검증 체크리스트:
- 저장 슬롯 UI에서 새 게임 또는 기존 슬롯을 실제 UI 경로로 시작했는가?
- 플레이어 이동이 Transform 직접 세팅이 아니라 키보드/입력 시스템 경로로 수행됐는가?
- NPC, 장소, 활동, 이벤트, 퀘스트 로그 UI가 실제 Prompt/Input/Button 경로로 열리고 수행됐는가?
- 퀘스트 완료 또는 분기 결과가 실제 플레이 흐름으로 월드 상태 플래그를 활성화했는가?
- 활성화된 월드 상태가 실제 장소/NPC/상점/오브젝트/이벤트 중 최소 1곳에 반영됐는가?
- 하루 결과 UI 또는 월드 로그 UI에서 새 월드 변화가 공통 카드로 표시됐는가?
- 저장 슬롯 UI 재진입 후 같은 슬롯을 로드했을 때 월드 상태 플래그와 UI 표시 상태가 유지되는가?
- 같은 퀘스트 결과나 저장/로드 재호출로 중복 플래그 활성화, 중복 알림, 중복 보상이 발생하지 않는가?
- 테스트용 신규 플래그가 SO만으로 추가되어 실제 플레이 경로에서 활성화/표시/저장/로드됐는가?
- 실제 클라이언트 2개 이상 또는 Host+Client를 띄워 Client 1의 Shared 월드 변화가 Client 2 화면에도 반영되는지 확인했는가?
- Client 2도 직접 이동/상호작용/UI 확인으로 Shared 변화를 확인했는가?
- Shared 변화가 동기화되어도 보상 수령 여부, 개인 관계도, 관심 진로, 진로 힌트, 도감, 개인 퀘스트 단계, NPC 반응 본 여부가 각 클라이언트별 Personal 상태로 분리되는지 확인했는가?
- 두 클라이언트가 같은 Shared 상태를 동시에 또는 연속으로 활성화하려 해도 중복 오브젝트, 중복 알림, 중복 보상이 발생하지 않는지 확인했는가?
- 체크리스트 항목 중 하나라도 FAIL이면 완료로 보고하지 않고 실패 단계와 남은 작업을 보고했는가?

목표 플레이 흐름:
1. 저장 슬롯 UI로 새 게임 또는 기존 슬롯 로드 후 Town에 진입한다.
2. 플레이어가 실제 이동으로 퀘스트 체인 관련 NPC/장소에 접근한다.
3. 실제 Prompt/Input/Button 경로로 퀘스트 체인을 수락하거나 진행한다.
4. 실제 이동/상호작용으로 퀘스트 목표를 완료한다.
5. 퀘스트 완료/분기/실패 결과로 월드 상태 플래그가 활성화된다.
6. 하루 결과 UI에 "오늘 마을에 생긴 변화"가 공통 카드로 표시된다.
7. 플레이어가 실제 이동으로 변화가 발생한 장소에 가서 오브젝트/포탈/상호작용/NPC 대사/상점 품목/이벤트 가능 여부 중 최소 1개 변화를 확인한다.
8. 지도/장소 UI 또는 월드 로그 UI를 열어 같은 변화가 데이터 기반 카드로 표시되는지 확인한다.
9. 저장 슬롯 UI로 같은 슬롯을 다시 로드한다.
10. 재로드 후 월드 상태 플래그, 장소/NPC/상점/오브젝트 변화, UI 표시 상태가 유지되는지 확인한다.
11. 같은 퀘스트 완료 결과를 재확인하거나 같은 보상 요청을 반복해도 중복 변화/중복 알림/중복 보상이 발생하지 않는지 확인한다.
12. SO만으로 추가한 테스트 월드 상태 플래그도 같은 흐름으로 활성화/표시/저장/로드한다.

필수 저장 데이터:
- saveSlot
- player identity 또는 shared world scope
- active world state flag ids
- flag activated day/time
- source quest chain id
- source quest step id 또는 event id
- seen notification flags
- applied effect version
- personal/shared scope marker
- today world change summary

필수 EditMode 테스트:
- WORLD-STATE-EDIT-001: WorldStateFlagDefinition/조건/효과/보상 전략이 Registry 또는 지정 데이터 경로에서 로드된다.

멀티플레이 scope 정책:
- 월드에 시각적/기능적으로 드러나는 변화는 기본 Shared로 처리한다.
- 장소 개방, 오브젝트 등장, 상점 공용 품목, 포탈/길 개방, NPC 스케줄 변화, 공동 이벤트 결과는 Shared WorldStateFlag로 정의한다.
- Shared WorldStateFlag는 서버 권한으로만 활성화되며 모든 클라이언트에 동기화된다.
- 한 플레이어가 Shared 월드 변화를 발생시키면 같은 서버의 모든 플레이어가 그 변화를 실제 플레이 화면에서 확인할 수 있어야 한다.
- 단, 보상 수령 여부, 개인 관계도, 관심 진로, 진로 힌트, 도감 발견, 개인 퀘스트 단계, NPC 반응 본 여부는 Personal로 저장한다.
- Shared 변화가 발생했을 때 다른 플레이어에게는 "누군가 마을을 변화시켰다"는 공용 반응/후속 활동이 열릴 수 있어야 한다.
- 같은 Shared 상태를 여러 플레이어가 동시에 활성화하려 해도 서버에서 멱등 처리해 중복 오브젝트, 중복 알림, 중복 보상이 발생하지 않아야 한다.
- Client 1의 Personal 상태(보상 수령, 관계도, 관심 진로, 도감, 개인 퀘스트 단계, NPC 반응 본 여부)가 Client 2에게 노출되면 안 된다.
```
