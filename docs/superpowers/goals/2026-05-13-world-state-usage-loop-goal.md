# World State Usage Loop Goal Prompt

아래 프롬프트를 goal 세션에 그대로 붙여 넣고 진행한다.

```text
ROOTBORN Unity 프로젝트에서 "퀘스트로 발생한 Shared 월드 상태 변화가 싱글플레이에서도 혼자 완성 가능한 새 활동/상호작용/후속 퀘스트/도감/진로 힌트로 이어지고, 멀티플레이에서는 같은 변화를 다른 클라이언트도 볼 수 있지만 개인 활용 보상은 분리되는 월드 변화 활용 루프"를 설계/구현/검증해줘.

핵심 의도:
- 퀘스트로 마을이 바뀐 뒤 그 변화가 장식으로 끝나면 안 된다.
- 바뀐 장소, NPC, 오브젝트, 상점, 포탈은 실제 플레이에서 다시 사용할 수 있어야 한다.
- 월드 변화 활용은 새 활동, 후속 퀘스트, 도감 발견, 진로 힌트, 관계 변화, 하루 이벤트 후보로 이어져야 한다.
- 싱글플레이에서 혼자 모든 활용 루프를 완료할 수 있어야 한다.
- 멀티플레이 협동은 필수가 아니라 선택/가속 요소다.
- Shared 월드 변화는 모든 클라이언트가 볼 수 있지만, 활용 보상/도감/진로 힌트/개인 사용 횟수는 Personal로 분리한다.

헌법 규칙:
- AGENTS.md와 `.claude/rules/*`를 따른다.
- `Assets/**/*.cs`를 외부 디스크 쓰기로 직접 수정하지 않는다. C# 신규/수정은 반드시 Unity MCP `script-update-or-create` 또는 Unity Editor 안전 경로를 사용한다.
- 모든 게임 엔티티는 100% ScriptableObject 데이터 기반이어야 한다.
- flagId, usageId, objectId, locationId, npcId, shopId, portalId, activityId, questId별 `if/switch` 분기, enum 기반 엔티티 분기, 활용 요소별 C# 클래스 생성은 금지한다.
- 월드 변화 활용 조건, 결과, 반복 제한, 보상, UI 표시 규칙은 SO 데이터와 전략 배열로 표현한다.
- 보상/인벤토리/마일스톤/도감/퀘스트/진로 힌트/월드 활용 상태는 저장/로드 후 중복 적용되면 안 된다.
- TDD로 진행한다. 먼저 실패하는 테스트를 만들고 실패를 확인한 뒤 구현한다.
- 성능/최적화 동시 설계 원칙을 따른다.
- 기존 dirty 변경을 되돌리지 않는다.

권장 데이터 구조:
- `WorldStateUsageDefinition`
  - 어떤 WorldStateFlag가 활성화됐을 때 어떤 활용 요소가 열리는지 정의한다.
  - 관련 장소, NPC, 오브젝트, 상호작용, 상점 품목, 포탈, 활동, 후속 퀘스트, 도감 항목, 관심 진로 연결을 포함한다.
- `WorldStateUsageConditionBase[]`
  - 월드 상태 활성 여부, 장소 방문 여부, 관심 진로, 관계도, 시간대, 아이템 보유, 도감 발견 여부, 퀘스트 상태를 일반 조건으로 평가한다.
- `WorldStateUsageOutcomeBase[]`
  - 활동 해금, 후속 퀘스트 해금, 진로 힌트 지급, 도감 발견, 관계 변화, 하루 이벤트 후보 추가, 상태/특성/기술 변화, 아이템 지급을 일반 결과로 처리한다.
- `WorldStateUsageRepeatPolicyDefinition`
  - 1회성, 반복 가능, 하루 1회, 쿨다운, 사용 횟수 제한을 데이터로 정의한다.
- `WorldStateUsageProgress`
  - saveSlot + player identity 기준으로 사용 여부, 사용 횟수, 마지막 사용 날짜, 보상 수령 여부, 반복 제한 상태, 오늘 사용 요약을 저장한다.
- `WorldStateUsageSummaryModel`
  - 장소 UI, 월드 로그 UI, 하루 결과 UI, HUD에서 공통으로 사용할 표시 모델이다.

초기 활용 루프 예시:
- 공방 수리 작업대
  - 조건: `공방 수리 작업대 등장` Shared WorldStateFlag 활성화
  - 활용: 작업대 상호작용, `수리 연습`, `도구 정비`, `납품 준비` 활동
  - 결과: 기술·작업형 진로 힌트, 작업 관리자 후속 대화/퀘스트, 도감 `수리 작업대`
- 도서관 자료실
  - 조건: `도서관 자료실 개방` Shared WorldStateFlag 활성화
  - 활용: 자료실 포탈/상호작용, `심화 조사`, `기록 열람`, `지도 단서 찾기`
  - 결과: 학습형/탐험형 진로 힌트, 사서 후속 이벤트, 도감 `오래된 자료실`
- 상점 새 품목
  - 조건: `상점 새 품목 입고` Shared WorldStateFlag 활성화
  - 활용: 상점 UI 새 품목, `배달 도움`, `진열 정리`, `단골 응대`
  - 결과: 관계·서비스형 진로 힌트, 상점 주인 후속 퀘스트, 구매 가능 품목
- 숨은 길
  - 조건: `골목 숨은 길 개방` Shared WorldStateFlag 활성화
  - 활용: 포탈 이동, `주변 조사`, `단서 수집`, `지도 기록`
  - 결과: 탐험·정보형 진로 힌트, 도감 발견, 하루 이벤트 후보 추가

UI 요구:
- 장소 UI에는 "새로 열린 활동" 배지와 "이 변화로 가능해진 일" 목록을 표시한다.
- 새 오브젝트/포탈/상점 품목에는 실제 상호작용 프롬프트가 떠야 한다.
- 하루 결과 UI에는 오늘 활용한 월드 변화, 새로 열린 활동/퀘스트/도감/진로 힌트를 표시한다.
- 월드 로그 UI에는 이미 생긴 변화, 아직 활용하지 않은 변화, 활용 완료/반복 가능 상태를 표시한다.
- HUD에는 추적 중인 활용 요소가 있으면 현재 목표와 다음 행동을 작게 표시한다.
- UI는 특정 usageId/flagId를 직접 알지 않고 `WorldStateUsageSummaryModel`을 렌더링한다.
- Modern UI Style2 공통 패널 규약을 따른다.
- 1920x1080 기준에서 변화명, 활용 설명, 조건, 보상, 버튼 텍스트가 겹치거나 잘리지 않아야 한다.
- UI는 문서 목업만 만들고 끝내면 안 된다. PlayMode에서 실제로 열리고 클릭 가능해야 한다.

확장성 검증:
- 새 활용 루프는 C# 코드 수정 없이 ScriptableObject 데이터 추가와 Registry 등록만으로 추가 가능해야 한다.
- 테스트용 신규 `WorldStateUsageDefinition`을 1개 이상 추가하고, 기존 런타임 코드를 수정하지 않은 상태에서 상호작용/활동/후속 퀘스트/도감/저장/로드가 동작하는지 검증한다.
- 한 WorldStateFlag가 여러 활용 요소를 열 수 있어야 한다.
- 한 활용 요소가 여러 결과/보상/후속 콘텐츠를 열 수 있어야 한다.
- 같은 활용은 중복 보상 없이 멱등 처리한다.
- 반복 활동은 쿨다운/일일 제한/사용 횟수 제한을 데이터로 정의한다.
- 장소, NPC, 오브젝트, 상점, 포탈, 활동, 퀘스트, 도감 모두 같은 조건/결과 전략 구조를 사용한다.
- 최종 보고에는 "월드 변화 활용 확장성 검증 체크리스트"를 포함하고, SO만으로 추가한 테스트 활용 루프의 실제 플레이 검증 결과를 기록한다.

최우선 실제 플레이 검증 원칙:
- 이 goal은 실제 유저가 플레이하듯 검증하지 않으면 완료로 인정하지 않는다.
- 최소 1개 이상의 PlayMode E2E는 저장 슬롯 UI에서 시작해 실제 키보드 이동, 실제 NPC/장소/오브젝트/상점/포탈 상호작용, 실제 UI 버튼 선택, 활용 결과 확인, 하루 종료, 결과 UI 확인, 저장/로드 재진입을 모두 거쳐야 한다.
- 테스트에서 WorldStateUsageProgress, WorldStateProgress, QuestLog, Inventory, SaveData 상태를 직접 세팅해서 성공 처리하면 실패다.
- 플레이어 Transform 직접 이동, 내부 메서드 직접 호출, 씬 강제 로드, 저장 데이터 직접 주입, UI 없이 도메인 API 직접 호출로 실제 플레이 경로를 대체하면 완료로 보고하지 않는다.
- 최종 보고 전에 "실제 플레이 방식 상호작용 검증 체크리스트"를 반드시 작성하고, 각 항목을 PASS/FAIL로 표시한다.

실제 플레이 방식 상호작용 검증 체크리스트:
- 저장 슬롯 UI에서 새 게임 또는 기존 슬롯을 실제 UI 경로로 시작했는가?
- 플레이어 이동이 Transform 직접 세팅이 아니라 키보드/입력 시스템 경로로 수행됐는가?
- 새로 열린 오브젝트/포탈/상점 품목/장소 활동이 실제 Prompt/Input/Button 경로로 열리고 수행됐는가?
- 활용 결과가 실제 활동, 후속 퀘스트, 도감, 진로 힌트, 관계 변화, 하루 이벤트 후보 중 최소 2개 이상으로 이어졌는가?
- 하루 결과 UI 또는 월드 로그 UI에서 활용 결과가 공통 summary/card로 표시됐는가?
- 저장 슬롯 UI 재진입 후 같은 슬롯을 로드했을 때 활용 상태, 사용 횟수, 보상 수령 여부, 도감/퀘스트/진로 힌트 상태가 유지되는가?
- 같은 활용을 반복해도 중복 보상, 중복 도감 발견, 중복 퀘스트 해금, 중복 진로 힌트가 발생하지 않는가?
- 테스트용 신규 활용 루프가 SO만으로 추가되어 실제 플레이 경로에서 상호작용/표시/저장/로드됐는가?
- 체크리스트 항목 중 하나라도 FAIL이면 완료로 보고하지 않고 실패 단계와 남은 작업을 보고했는가?

싱글/멀티 정책:
- 싱글플레이에서 혼자 모든 활용 루프를 완료 가능해야 한다.
- 멀티플레이 협동은 필수가 아니라 선택/가속 요소다.
- Shared 월드 변화는 모든 클라이언트가 볼 수 있다.
- 활용 보상, 도감, 진로 힌트, 개인 사용 횟수, 후속 퀘스트 수락/보상 상태는 Personal이다.
- Client 1이 작업대를 열면 Client 2도 작업대를 볼 수 있지만, Client 2의 사용 보상/도감/진로 힌트는 별도로 처리한다.
- 멀티플레이 직접 검증이 이번 범위에 포함되면 실제 클라이언트 2개 이상 또는 Host+Client를 띄워 Shared 표시와 Personal 보상 분리를 확인한다.
- 멀티플레이 직접 검증이 범위 밖이면 최종 보고에 후속 NET 테스트 계획을 명시한다.

목표 플레이 흐름:
1. 저장 슬롯 UI로 새 게임 또는 기존 슬롯 로드 후 Town에 진입한다.
2. 실제 플레이로 퀘스트를 완료하거나 기존 월드 상태 플래그를 활성화한다.
3. 월드 변화가 발생한 장소로 실제 이동한다.
4. 새로 열린 오브젝트/포탈/상점 품목/장소 활동 프롬프트를 확인한다.
5. 실제 Input/Button 경로로 활용 요소를 실행한다.
6. 활용 결과로 새 활동, 후속 퀘스트, 도감, 진로 힌트, 관계 변화, 하루 이벤트 후보 중 최소 2개 이상이 발생한다.
7. 하루 결과 UI에서 오늘 활용한 월드 변화와 열린 결과를 확인한다.
8. 월드 로그 UI에서 활용 완료/반복 가능/미활용 상태를 확인한다.
9. 저장 슬롯 UI로 같은 슬롯을 다시 로드한다.
10. 재로드 후 활용 상태, 사용 횟수, 보상 수령 여부, 도감/퀘스트/진로 힌트 상태가 유지되는지 확인한다.
11. 같은 활용을 반복해 중복 보상/중복 해금/중복 발견이 발생하지 않는지 확인한다.
12. SO만으로 추가한 테스트 활용 루프도 같은 흐름으로 상호작용/표시/저장/로드한다.
```
