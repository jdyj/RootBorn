# 화면 옮기기 (프로젝트 4) — 설계

- 날짜: 2026-11-12 (main `3e4f1c559` 기준 조사)
- 상태: **초안, 사용자 승인 대기.**
- 작성 경위: 사용자가 설계를 시작하라고 했고, 앞선 설계들처럼 질문 없이 추천안으로 썼다. 이 문서의 선택은 모두 **작성자(Claude)의 판단**이다. 사용자가 뒤집을 만한 것은 11절에 모았다.
- 위치: `docs/superpowers/specs/2026-11-11-unity-removal-design.md` 6절 표의 프로젝트 4. 끝 기준은 그 표 그대로다: **메인 체인을 MonoGame 판에서 실제 입력으로 끝까지 완료.**

## 1. 무엇을 하는가

Unity 판의 화면 약 30개를 MonoGame 판으로 옮긴다. 화면의 구성, 크기, 순서, 문구는 Unity 판과 같게 한다. 새 화면이나 새 기능은 넣지 않는다.

이 프로젝트가 끝나면 MonoGame 판 하나로 새 게임을 시작해 메인 체인을 끝까지 플레이할 수 있다. 그때부터 MonoGame 판이 "플레이 가능한 판"이 된다.

## 2. 조사한 사실

**Unity 판 화면** (`Assets/Scripts/UI`, 110개 파일, 약 22,000줄)

- 화면은 프리팹 없이 코드로 만든다. 공통 기반 클래스는 없고, 화면마다 설치 코드가 씬의 Canvas를 찾아 붙는다.
- 기준 해상도 1920x1080. 패널은 가운데 기준 절대 픽셀로 놓고, HUD는 오른쪽 위 기준이다.
- 키로 여는 큰 패널 넷은 서로 하나만 열린다: 가방(I), 상태(C), 설정(Esc), 목표 수첩(Tab).
- 이동을 막는 화면(모달)과 막지 않는 화면이 섞여 있다. 가방·상태·설정·수첩·대화·일과는 이동을 막는 호출이 화면 쪽에 없다.
- 키보드로 버튼 사이를 옮겨 다니는 기능은 없다. 마우스 클릭 중심이다. 툴팁, 끌어다 놓기, 화면 전환 애니메이션도 없다.
- 글자 입력은 세 곳: 캐릭터 이름(12자), 가방 검색, 가구 검색.
- 화면은 게임 상태를 컴포넌트에서 직접 읽는다. 다만 목표 수첩은 이미 "모으는 쪽 → 표시 모델 → 화면"으로 나뉘어 있고, 하루 결과·장소 상태·탐색 등은 Core의 요약 모델을 받는다.
- 가장 큰 덩어리는 가구 배치다(패널 982줄 + 월드 위 미리보기 1,344줄 + 배치용 카메라).
- 메인 체인 테스트(`MainChainOpeningE2EScenarioTests`)가 거치는 화면: 슬롯 선택 → 하루 이벤트 → 대화 → 일과 → 하루 결과 → 장소 → 미니게임 → 가구 배치, 그리고 장래희망과 목표 수첩.

**MonoGame 판에 이미 있는 것**

- `Rootborn.Ui`(엔진 참조 없음): 배치, 포인터 판정, 클릭, 포커스 이동, 줄 단위로만 그리는 스크롤 목록, 글자 칸(한글 조합), 9조각 패널. 그리기 명령 목록만 낸다.
- `Rootborn.Host`: 창, 입력 장치 계층, 글자 그리기, 견본 화면, 월드 화면. 지금은 화면을 하나만 띄운다.
- 테스트: 화면 없이 도는 UI 테스트, 실제 창과 게임 루프를 한 프레임씩 돌리며 키·포인터 이벤트를 넣는 Host 테스트(`PlayerDriver`).
- 진행 중: `game/Rootborn.Game`의 `GameSession`(규칙을 게임 한 판으로 묶는 진입점과 조회), 월드 2차(세이브 슬롯, 캐릭터 겉모습, 낮밤, 상호작용 대상).

## 3. 구조

```
game/Rootborn.Screens/         화면들. 엔진 참조 없음. Rootborn.Ui, Rootborn.Game, Rootborn.Core만 참조
game/tests/Rootborn.Screens.Tests/   화면 없이 도는 화면 테스트
game/Rootborn.Host/            화면 쌓기, 키 배정, 월드와 화면 잇기, 그리기 (기존 프로젝트에 추가)
```

- **화면은 `GameSession`만 부른다.** 화면에 규칙 판단을 쓰지 않는다. 화면이 필요한 값이 없으면 `GameSession`의 조회에 더한다.
- **화면 하나는 세 부분이다.**
  1. 표시 모델: 화면이 그릴 값만 담은 순수 데이터(문구 키, 수치, 줄 목록, 버튼이 눌릴 수 있는지와 이유). `GameSession`에서 만든다.
  2. 화면 클래스: 표시 모델로 `UiNode` 나무를 만들고, 버튼이 눌리면 `GameSession` 명령을 부른 뒤 모델을 다시 받아 바뀐 부분만 고친다.
  3. 등록 한 줄: 어떤 키나 어떤 상호작용이 이 화면을 여는지.
- **문구**는 현지화 키로만 쓴다. `data/localization/ko.json`·`en.json`을 읽는 `GameText`를 `Rootborn.Screens`에 둔다. 키가 없으면 키를 그대로 보여 주고 테스트가 실패한다(Unity 판처럼 코드에 적은 한글로 대신하지 않는다).
- **그림**은 Host가 맡는다. 화면은 스킨 이름과 아이콘 id만 말한다. 패널 그림 좌표는 지금처럼 `UiSkins` 한 곳에 둔다.

### 3.1 화면 쌓기 (Host)

`ScreenStack` 하나가 지금 떠 있는 화면을 가진다.

- 층: 월드 → HUD(항상) → 패널(한 번에 하나) → 모달(위로 쌓임) → 알림.
- 모달이 떠 있으면 그 아래 층은 입력을 받지 않고, 캐릭터는 움직이지 않는다. Unity 판의 `UiGameplayInputLock`을 이것 하나로 대신한다.
- 키 배정은 표 하나에 둔다(I, C, Esc, Tab, E). 글자 칸에 포커스가 있으면 키 배정을 건너뛴다.
- 월드의 상호작용 이벤트(월드 2차가 만든다)를 받아 맞는 화면을 연다. 어떤 상호작용이 어떤 화면을 여는지는 상호작용 **종류**로 등록한다. 엔티티 id로 고르지 않는다.
- 새 화면 종류는 화면 클래스 하나와 등록 한 줄로 더한다.

### 3.2 다시 그리기와 성능

- 화면은 매 프레임 상태를 읽지 않는다. `GameSession`이 "무엇이 바뀌었는지"를 알리면 그 부분만 고친다.
- 긴 목록(가방, 도감, 수첩, 가구 팔레트)은 보이는 줄만 만든다. `UiScrollList`가 이미 그렇게 한다.
- 화면을 열 때마다 노드를 통째로 다시 만들지 않는다. 한 번 만들고 값만 바꾼다.
- 가구 1,503개 팔레트와 도감은 실제 데이터로 "열기와 스크롤이 한 프레임 안에 끝나는지"를 Host 테스트에서 잰다.

## 4. Unity 판과 같게 두는 것, 고치는 것

**같게 둔다:** 화면 목록, 패널 크기와 위치(1920x1080 기준 수치), 줄과 버튼의 순서, 문구 키, 여는 키와 상호작용, 글자 크기 단계, 도시형 몰딩 스킨, 목표 수첩이 목표성 UI를 소유하는 규칙.

**고친다 (구조):**
- 화면마다 따로 있던 설치 코드와 Canvas 찾기를 `ScreenStack` 등록으로 바꾼다.
- 화면이 컴포넌트를 직접 읽던 것을 표시 모델로 바꾼다.
- 스크롤 목록, 탭, 게이지처럼 화면마다 새로 짜던 것을 `Rootborn.Ui` 부품으로 모은다.

**고친다 (동작, 9절 목록에 기록):**
- 큰 패널(가방, 상태, 설정, 수첩)과 대화, 일과가 떠 있는 동안 캐릭터가 움직이지 않는다. Unity 판은 화면 쪽에서 막지 않았다.
- 키보드만으로도 버튼 사이를 옮기고 고를 수 있다(방향 키, Enter). 마우스 동작은 그대로다.

**옮기지 않는다:** 낮밤 디버그 버튼, 가구 팔레트의 개발용 시드 입력, 도구 해금 알림(도구를 게임이 쓰지 않는다), 모드 선택·참가 화면(프로젝트 5).

## 5. `Rootborn.Ui`에 더할 부품

지금 있는 것: 패널, 글자, 버튼, 칸, 스크롤 목록(세로), 글자 칸.
더할 것: 여러 줄 글자(줄바꿈), 그림(아이콘·스프라이트), 탭 줄, 게이지, 켬/끔, 미끄럼 막대, 가로 스크롤 카드 줄, 카드 격자(줄마다 여러 칸인 스크롤).

부품은 토대 묶음에서 한꺼번에 만든다. 화면 묶음을 맡은 세션이 새 부품이 필요하면 `Rootborn.Ui`를 고치지 않고 자기 화면 폴더에 먼저 두고 보고한다. 조정 담당이 합칠 때 `Rootborn.Ui`로 올린다(여러 세션이 같은 파일을 고치지 않게).

## 6. 묶음과 순서

묶음 하나가 세션 하나의 일이다. 0번이 main에 들어온 뒤에는 서로 겹치지 않는 묶음을 동시에 진행할 수 있다(화면마다 파일이 따로이고, 겹치는 곳은 등록 표의 한 줄뿐이다).

| # | 묶음 | 화면 | 메인 체인에 필요 |
|---|---|---|---|
| 0 | 토대 | `ScreenStack`, 키 배정, 월드 상호작용 잇기, `GameText`, 스킨, 5절 부품, Host가 `GameSession`으로 시작하도록 | 예 |
| 1 | 시작 | 슬롯 선택(새 게임·이어 하기), 캐릭터 생성(이름, 겉모습 미리보기) | 예 |

가구(7)는 가장 크고 월드와 맞물린다. 배치 판정은 Core `Placement`에 이미 있으므로, 옮길 것은 팔레트 화면, 미리보기 그리기, 카메라, 저장 시점이다.

## 7. 검증

근거의 종류를 나눠 적는다(`core-logic-and-play-evidence.md`).

1. **표시 모델 테스트**(자동 테스트): 실제 `data/`와 `GameSession`으로 모델을 만들어 값과 순서를 확인한다.
2. **화면 테스트**(자동 테스트, 창 없음): `UiTree`에 포인터·키를 넣어 버튼을 누르고, `GameSession` 상태와 화면 값이 바뀌는지 본다. 모든 문구 키가 `ko.json`·`en.json`에 있는지도 여기서 본다.
3. **Host 시나리오**(장치 이벤트 주입, OS 입력 계층 미확인): 실제 창과 게임 루프에서 `PlayerDriver`로 걷고, E를 누르고, 포인터로 누른다. 화면마다 스크린샷을 `output/host-screens-evidence/`에 남기고 직접 열어 본다. Unity 판의 같은 화면 증거와 나란히 놓고 구성·크기·순서를 비교한다.
4. **메인 체인**: `MainChainOpeningE2EScenarioTests`의 흐름을 Host 시나리오로 옮긴다. 순간이동, 내부 호출, 상태 강제 설정을 쓰지 않는다. 이것이 통과하면 프로젝트 4의 끝이다.
5. **사람의 확인**: 실제 키보드·마우스로 하는 플레이와 조작감은 사용자가 본다. 그 전에는 "실제 플레이로 확인"이라고 쓰지 않는다.

화면 묶음마다 끝 기준: 그 묶음의 화면이 2번과 3번을 통과하고, 스크린샷을 직접 열어 결함(겹친 글자, 잘린 패널, 빈 그림, 어긋난 줄)이 없다.

## 8. 하지 않는 것

- 화면 구성·문구·수치를 바꾸는 일, 새 화면, 툴팁, 화면 전환 애니메이션, 게임패드.
- 해상도별 따로 만든 배치. 1920x1080 기준 수치를 화면 배율로 맞춘다(지금 Host가 하는 방식).
- 소리. 다른 프로젝트에서 다룬다.
- 멀티플레이 화면과 Steam(프로젝트 5).
- 데이터 편집 화면.

## 10. 규칙 문서 정리

화면이 옮겨질 때마다 Unity 클래스 이름을 가리키는 규칙을 고친다: `objective-journal-ui.md`(수첩·추적 HUD의 새 클래스 이름), `ui-standards.md`(Canvas·Addressables 조항 삭제, 스킨과 패널 좌표 위치), `path-based/assets-ui.md`와 `assets-addressables.md`(Unity 전용이라 삭제 대상). 묶음 6이 끝날 때 `objective-journal-ui.md`를, 묶음 0이 끝날 때 나머지를 고친다.

## 11. 작성자가 정한 것 (사용자가 뒤집을 수 있다)

1. **화면은 Unity 판과 같은 구성으로 옮긴다.** 옮기는 김에 화면을 다시 디자인하지 않는다.
2. **패널·대화·일과가 떠 있으면 캐릭터가 멈춘다.** Unity 판에서는 가방을 연 채로 걸을 수 있었다. 원래대로 두길 원하면 화면별로 켜고 끌 수 있다.
3. **키보드로 버튼을 옮겨 고르는 기능을 넣는다.** UI 토대에 이미 있어서 비용이 거의 없다.
4. **현지화 키가 없으면 테스트가 실패한다.** Unity 판에는 키가 없을 때 코드에 적힌 한글·영어로 대신하는 곳이 여럿 있다. 그런 문구는 옮기면서 `ko.json`·`en.json`에 키로 넣는다(`data/localization`을 고치는 일이므로 변환기 출력과 어긋난다 — 그 문구들은 JSON에 직접 더하고 변환기 비교에서 뺀다).
5. **메인 체인에 필요한 화면부터 옮긴다.** 가방·상태·설정·도감·옷장은 그 뒤다.
6. **픽셀까지 같게 맞추지 않는다.** 구성·크기·순서가 같으면 된다. 글꼴이 달라 글자 폭이 다르기 때문이다.

## 12. 앞서 끝나야 하는 것과 결정 대기

- `game-session`(GameSession)과 `host-world-2`(상호작용 이벤트, 세이브 슬롯, 캐릭터 겉모습)가 main에 들어와야 묶음 0을 시작한다.
- 배포용 한글 글꼴: 정해지기 전에는 운영체제 글꼴로 진행한다. 글꼴이 정해지면 글자 폭이 바뀌므로 스크린샷을 다시 본다.
- 캐릭터 생성의 겉모습 미리보기는 `host-world-2`가 옮기는 캐릭터 그리기를 쓴다.

## 13. 확인하지 못한 것

- Unity 판 화면의 모든 줄을 읽지 않았다. 화면 목록과 크기는 클래스 머리와 여는 코드에서 얻었다. 묶음을 맡는 세션이 원본을 읽으며 빠진 화면이 있으면 보고한다.
- 대화가 이동을 막는지는 화면 코드에서만 봤다. 부르는 쪽에서 막고 있을 수 있다.
- 가구 팔레트 1,503개와 도감이 MonoGame 판에서 한 프레임 안에 열리는지는 재 보지 않았다.
