# 픽셀 키트 — 건물·타일·외벽·실내를 부품과 규칙으로 그리기

작성일: 2026-11-13
상태: **초안, 사용자 승인 전.** "사용자"라고 적은 것만 사용자가 말한 것이고 "작성자 판단"은 이 문서를 쓴 쪽이 정한 것이다.
앞 문서: `docs/superpowers/specs/2026-11-12-art-production-design.md`(확산 모델로 후보를 뽑아 고르는 설계). 이 문서는 그 문서의 **그림을 만드는 절반을 바꾼다**(12절).

## 1. 왜

사용자(2026-11-13):

- Strix Halo에서 뽑은 그림이 마음에 들지 않는다. 디테일이 떨어지고 원하는 대로 나오지 않는다("빵집이면 진열대에 빵도 조금 있었으면").
- **가장 중요한 것은 외곽선과 중간중간의 마감이 제대로 안 되어 있다는 것. 기본부터 되어 있어야 한다.**
- 도시 풍경의 건물, 타일, 건물 외벽, 건물 안의 상황을 디자인으로 얻고, 스킬로 만들어 편하게 쓰고 싶다.

원인(작성자 판단, 결과물을 직접 보고): 확산 모델은 큰 그림을 그린 뒤 게임 픽셀로 줄인다. 픽셀 단위 마감을 약속할 수 없고 세부 지시를 잘 따르지 않는다. 외곽선 정리 후처리를 다섯 번 고쳤지만 기본이 잡히지 않았다.

시험(2026-11-13, `output/art-spike-bakery/`, 버릴 코드): 빵집 외관·진열대·타일을 부품 데이터와 규칙으로 그려 Strix Halo 결과와 같은 배율로 나란히 보였다. 사용자: **"기본은 됐다."**

이어서 사용자: **"입체감만 좀 살아있으면 될거같긴해"**, **"부족한 점 잘 채워줘"**. 시험을 두 번 더 돌렸다: 입체감 규칙(`spike2.py`, 앞뒤 비교 `board_depth.png`), 부족한 점 채우기(`spike3.py`, `board_v3.png` — 빵 실루엣, 뒤로 물러나는 지붕, 벽 변화, 벽등·화분·입간판·계산대·벽 장식). 이 세 번의 시험에서 쓴 규칙이 6절의 바탕이다.

## 2. 한 줄 요약

**그림을 뽑지 않고 조립한다.** 부품(벽 재질, 창, 문, 지붕, 진열대, 빵)을 1:1 게임 픽셀 데이터로 두고, 마감(외곽선·명암·색)은 렌더러가 규칙으로 입히고, "빵집"은 부품을 어떻게 놓을지 적은 조립 명세다. 스킬은 "약국 외관 만들어 줘"를 명세 작성 → 렌더 → 직접 보고 고치기 → 게임 형식으로 내보내기로 잇는다.

그림은 처음부터 게임 픽셀 1:1로 그린다(32px 칸이면 32개의 점). 큰 그림을 줄이는 단계가 없다. 확대판은 보기용일 뿐이다.

## 3. 목표, 하지 않을 것, 실패

**목표**

1. 외곽선이 끊기거나 두께가 달라지는 그림, 팔레트 밖 색, 이어지지 않는 타일이 **구조적으로 나올 수 없다**(규칙이 그리고 검사가 막는다).
2. 지시한 내용이 그대로 나온다. "진열대 2층에 크루아상 셋"은 명세의 한 줄이다.
3. 새 건물·새 방을 얻는 일이 명세 한 덩어리를 쓰는 일이다. 부품은 다시 쓴다.
4. 수백 장이 한 게임의 그림으로 보인다(팔레트, 빛 방향, 외곽선 규칙이 한 곳).
5. 나온 그림이 코드 수정 없이 게임에 들어간다(PNG + 좌표표 + 데이터 줄).
6. Claude와 Codex 어느 쪽이든 스킬 하나로 같은 절차를 돈다.

**하지 않을 것**

- UI 스킨(스킬 `ui-nine-slice-skin`), 캐릭터와 착용품, 움직이는 그림.
- LDtk 맵을 자동으로 만드는 일. 방 명세는 **미리 보기 장면**까지 낸다(8절). 맵에 놓는 일은 따로 한다.
- 확산 모델 결과를 게임 픽셀로 쓰는 일. 필요하면 분위기 시안으로만 본다(11절).
- 새 LoRA 학습.

**이렇게 되면 실패다**

- 마감이 다시 사람(또는 후처리 땜질)에게 넘어가는 것.
- 건물마다 부품을 새로 그려 재사용이 없는 것(건물 수만큼 손이 드는 것).
- 품목마다 색과 비율이 달라 한 화면에서 어긋나는 것.
- 그림이 들어올 때마다 게임 코드를 고치는 것.
- 기계적으로 고르기만 해서 휑한 것(시험에서 드러난 약점, 6.3절).
- **건물의 옆면(옆벽, 지붕 옆 비탈)을 보이는 것.** 사용자(2026-11-13): "절대 하지마 최악중 최악이야". 건물은 정면 + 지붕만 그린다(6.4절).

## 4. 접근 — 견준 것과 고른 것

| 길 | 무엇 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **A. 부품 데이터 + 규칙 렌더(고름)** | 이 문서 | 마감 보장, 지시대로, 타일 문제 해결, 독자 그림, 재사용 | 유기적인 모양(음식·식물)은 손이 더 간다. 부품 그림의 질은 그리는 쪽(AI) 솜씨에 달렸다 |
| B. A + 확산 모델 시안 | 분위기 시안만 뽑고 픽셀은 A로 | 디자인 아이디어 폭 | 단계 하나 추가. A가 자리 잡은 뒤 붙일 수 있다 |
| C. 손그림 팩(LimeZu) 조립 | 있는 조각만 조립 | 마감 가장 확실 | 팩에 없는 것은 못 만든다. "전부 새로 만든다"는 결정과 어긋난다 |
| (버림) 확산 모델 + 후처리 계속 | 지금 파이프라인 | — | 다섯 번 고쳐도 기본이 안 됐다 |

사용자가 A의 시험을 보고 "기본은 됐다"고 했다. B는 A 뒤의 선택 사항으로 남긴다(11절).

## 5. 구성

```
art/kit/style.json        화풍 규칙 한 곳: 칸 크기, 팔레트(재질별 명암 단계), 빛 방향, 외곽선 규칙, 색 수 한도
art/kit/parts/*.json      점 부품: 픽셀 행 + 팔레트 키 (빵, 손잡이, 화분, 간판 그림 …)
art/kit/recipes/**.json   조립 명세: 건물 외관, 가구, 타일, 방 장면
Tools/pixel-kit/          렌더러·검사·내보내기 (Python + Pillow), 테스트
art/props/<세트>/, art/items/, art/world/, art/tiles/   내보낸 PNG (게임이 읽는 그림. 앞 문서 7.3절의 자리 + 타일)
output/pixel-kit/…        견본판·작업물 (git 무시)
.claude/skills/pixel-kit, .agents/skills/pixel-kit   스킬 (같은 SKILL.md)
```

**사용자 결정(2026-11-13): 이 PC에서 돌린다.** Strix Halo로 옮기지 않는다. 그리는 계산은 가볍다(시험 스크립트 한 번에 0.2~0.4초, GPU 없음). 도구는 Python과 Pillow만 쓰므로 저장소를 받은 곳 어디서든 같은 명령으로 돌지만, 원격 실행 절차는 만들지 않는다.

작성자 판단: 도구는 Python이다(`Tools/ui-nine-slice`와 같다. 게임 실행에는 끼지 않는다). 데이터는 JSON이다.

### 5.1 부품의 두 종류

| 종류 | 무엇 | 더하는 법 |
|---|---|---|
| **점 부품** | 작은 그림을 픽셀 행으로 적은 것. 글자 하나가 팔레트 키 하나 | `parts/`에 JSON 한 덩어리. 코드는 고치지 않는다 |
| **만드는 부품** | 크기·내용을 받아 그리는 것: 재질 채우기(벽돌, 판자, 타일), 창, 문, 지붕, 차양, 진열대(칸 채우기), 계산대 | 클래스 하나 + 등록 한 줄. 종류를 `if`로 닫지 않는다 |

만드는 부품은 다른 부품을 **칸(slot)**에 받는다. 진열대의 칸에 빵, 진열창 안에 진열대, 간판에 그림. 시험에서 빵 7종을 한 번 그려 세 곳에 썼다.

점 부품 예:

```jsonc
{ "id": "bread.croissant", "anchor": "bottom-center",
  "rows": [ "...LHL...", ".LLDLDLL.", "LCDLCLDCL", "CD.....DC" ],
  "keys": { "H": "bread.4", "L": "bread.3", "C": "bread.2", "D": "bread.1" } }
```

색은 hex가 아니라 **팔레트 키**(`재질.단계`)로 적는다. 팔레트를 바꾸면 모든 그림이 함께 바뀐다.

### 5.2 조립 명세

```jsonc
// art/kit/recipes/buildings/bakery.json
{ "id": "bakery.exterior.lv1", "kind": "building",
  "size": [5, 5],                                   // 칸
  "wall": { "material": "brick.red" },
  "roof": { "type": "slate", "color": "teal" },
  "sign": { "icons": ["bread.croissant", "bread.loaf", "bread.baguette"] },   // 글자 없음(다국어)
  "awning": { "pattern": "stripe", "colors": ["red", "cream"] },
  "openings": [
    { "part": "window.display", "at": [0.4, 2.7], "size": [2.6, 1.4],
      "slots": ["bread.loaf", "bread.croissant", "bread.donut", "bread.bun"] },
    { "part": "door.glass-wood", "at": [3.4, 2.7] } ],
  "props": [ { "part": "planter.box", "at": [0.5, 4.4] } ] }
```

```jsonc
// art/kit/recipes/furniture/bakery-shelf.json
{ "id": "bakery.shelf", "kind": "furniture", "cells": [2, 1], "art_cells": [2, 2],
  "part": "shelf.tiered", "material": "wood.warm",
  "tiers": [ ["bread.loaf", "bread.loaf", "bread.baguette"],
             ["bread.croissant", "bread.bun", "bread.croissant"],
             ["bread.donut", "bread.choco", "bread.sandwich"] ],
  "states": { "empty": { "tiers": [[], [], []] } } }     // 상태 = 같은 명세의 다른 값
```

- `id`는 한 번 정하면 바꾸지 않는다(파일 이름, 좌표표 칸 이름, 가구 정의 id가 여기서 나온다).
- `cells`(바닥에서 차지하는 칸)는 규칙이고 가구 정의의 `footprintCells`가 된다. `art_cells`는 그림 크기다.
- 상태가 여럿인 그림(빈 진열대, 시설 레벨, 낡음)은 같은 명세에서 값만 바꿔 낸다. 앞 문서의 "상태마다 따로 뽑으면 다른 물건이 된다"는 문제가 없어진다.

### 5.3 종류

| kind | 무엇 | 게임에 들어가는 모양 |
|---|---|---|
| `tile` | 바닥(실내·보도·길·풀), 실내 벽(32×64, 직선·모서리·끝), 외벽 재질 | LDtk 타일셋 시트 + 좌표표 |
| `building` | 건물 겉모습 한 채 | LDtk가 고르는 묶음 시트(뒤에 덧붙이기만) + 좌표표 |
| `furniture` | 실내 가구(칸 채우기 포함) | PNG + 좌표표 + 가구 정의 줄 |
| `prop` | 바깥 소품(벤치, 가로등, 화단, 입간판) | 묶음 시트 + 좌표표 |
| `item` | 손에 드는 물건·아이콘 | 시트 + 좌표표 + 아이템 그림 키 |
| `scene` | 방·거리 미리 보기(타일 + 벽 + 가구·건물 배치) | 견본 PNG만(게임에 안 들어간다) |

내보내는 모양(좌표표, 가구 정의 줄, `replaces`로 옛 가구 id 지키기, 묶음 시트는 덧붙이기만)은 앞 문서 7.3절 그대로다. 맵 쪽 약속은 `game/world/README.md`(층 이름, `ysort`·`art` 태그, 기준점은 발 위치).

## 6. 화풍 규칙 — 마감을 규칙이 맡는다

### 6.1 `style.json`이 정하는 것

- 32px 칸, 게임 픽셀 1:1, 투명 배경, 위에서 비스듬히 본 시점(건물은 정면 + 지붕).
- **팔레트**: 재질마다 명암 4~5단계(`wood.warm.0~4`, `brick.red.0~2` …). 그림은 팔레트 키만 쓴다.
- **빛**: 왼쪽 위. 윗모서리·왼모서리는 한 단계 밝게, 아랫모서리·오른모서리는 한 단계 어둡게.
- **입체감 규칙(사용자가 가장 바란 것)** — 부품이 "튀어나옴/들어감/얹힘"을 말하면 렌더러가 그늘을 입힌다. 그리는 쪽이 그늘을 손으로 칠하지 않는다.
  - 튀어나온 것(처마, 차양, 창턱, 선반, 간판) 아래에는 2~3단계로 옅어지는 그늘.
  - 들어간 것(창, 문, 진열대 안)에는 위·왼쪽 안쪽 그늘, 안쪽 왼벽은 어둡게 오른벽은 밝게.
  - 틀과 판은 두께(위·왼쪽 밝은 선, 아래·오른쪽 어두운 선). 윗면이 보이는 것(계산대, 선반, 계단)은 윗면과 앞면을 다른 단계로.
  - 지붕은 위로 갈수록 좁아지고(뒤로 물러남) 용마루 쪽이 밝다. 오른쪽 면은 한 단계 어둡다.
  - 얹힌 것(선반 위 빵, 바닥 위 가구, 땅 위 건물, 벽에 걸린 것)에는 닿는 자리 그림자. 장면에 놓을 때 입힌다.
- **외곽선**: 물체 바깥 1px, 맞닿은 안쪽 색을 어둡게 한 색(검정 아님). 렌더러가 마지막에 채운다. 사람이 그리지 않는다.
- **물체당 색 수 한도**(가구 24, 건물 40. 가구는 칸에 넣은 부품의 색까지 세므로 처음 정한 16이 조합을 막아 1단계에서 24로 올렸다. 건물도 창·간판에 넣은 빵의 색까지 세므로 처음 정한 32에서는 빵을 갈색 한 종류로만 고르고 계단을 크림색으로 바꿔야 해서 1단계에서 40으로 올렸다).

### 6.2 자동 검사(`lint`) — 통과하지 못하면 내보내지 않는다

| 검사 | 막는 것 |
|---|---|
| 외곽선 닫힘 | 끊긴 선, 두께 다른 선 |
| 팔레트 | 팔레트 밖 색, 색 수 초과 |
| 외톨이 점 | 이웃과 이어지지 않는 1px 얼룩 |
| 칸 맞춤 | 캔버스가 칸 배수가 아님, 그림이 `art_cells`를 넘침, 아래 가운데 정렬 어긋남 |
| 타일 이음 | 타일을 3×3으로 깔았을 때 이음매의 색 끊김(재질 주기가 칸과 안 맞음) |
| 칸 겹침 | 칸에 넣은 부품이 서로 겹치거나 틀(창살 등)에 잘림 — 시험에서 실제로 나왔다 |
| 좌표표 | `width`·`height`가 PNG 실제 크기와 다름 |

검사는 "쓸 수 있다"의 바닥일 뿐이다. 보기 좋은지는 견본판을 직접 열어 본다(9절).

### 6.3 휑하지 않게 — 시험에서 드러난 약점과 대책

| 약점(시험 결과) | 대책 |
|---|---|
| 지붕이 납작한 띠 | 지붕 부품에 깊이: 용마루, 기와 줄의 명암 변화, 옆면, 굴뚝·환기구 칸 |
| 벽돌·벽지가 기계적으로 고르다 | 재질에 **변화 규칙**: 정해진 씨앗으로 색 섞기, 금·얼룩·이끼 덧그림(decal) 칸. 씨앗이 같으면 같은 그림 |
| 그림자가 네모 덩어리로 삐져나온다(3~6번째 시험) | 그림자는 열마다 물체가 끝나는 곳에서 시작한다(6.6절). 검사: 그림자가 물체 폭 밖 네모로 남지 않는다, 떠 있는 몸통 밑이 비지 않는다 |
| 그림자·주변 소품이 없다 | 바닥 그림자 규칙(물체 아래 타원), 건물 명세의 `props` 칸(화분, 입간판, 조명, 간판등) |
| 빵이 8px 안팎이라 구별이 약하다 | 점 부품에 크기 단계(선반용 작은 것 / 아이콘용 큰 것)를 따로 그린다. 실루엣이 다르게 |
| 화풍(색·비율)은 작성자가 임의로 잡았다 | 1단계에서 사용자가 기준판을 승인한다(10절) |

### 6.4 외벽의 입체감 — 정면만, 돋을새김으로

사용자(2026-11-13): 세 번째 시험을 보고 "아직 건물 외벽의 입체감이 덜하다". 두 방법을 그려 나란히 보였다(`output/art-spike-bakery/board_wall.png`, `spike4.py`).

- **옆면을 보이는 방법은 쓰지 않는다(사용자 결정, 다시 제안하지 않는다).** 옆벽, 지붕 옆 비탈, 차양 옆면 모두.
- 외벽의 입체감은 **정면 벽에 얹는 돋을새김 부품**으로 낸다. 건물마다 골라 붙인다(작성자 판단: 전부 붙이면 답답하다 — 시험에서 귀돌이 굵어 좁은 벽이 답답했다).

| 부품 | 무엇 |
|---|---|
| 귀돌 | 양 모서리의 돌 블록 |
| 돌림띠 | 처마 밑(또는 층 사이)의 돌 띠와 이빨 장식, 아래 그늘 |
| 인방·쐐기돌 | 창과 문 위의 돌 |
| 내민 창 | 양옆 볼(왼쪽 밝게, 오른쪽 어둡게), 두꺼운 창턱, 까치발, 벽에 드리운 그림자 |
| 들인 문 | 벽 두께가 보이는 파인 자리(위·왼쪽 그늘, 오른쪽 빛), 앞으로 나온 계단 |
| 홈통·벽등·간판 | 벽에 붙어 그림자를 드리우는 것 |
| 벽돌 낱장 | 윗줄 밝게, 아랫줄 어둡게 |

돋을새김만으로는 부족했다. 사용자가 LimeZu 가게 건물을 같이 보자고 했고(`board_limezu.png`), **"limezu 정도의 입체감이면 돼"**, 비율을 고친 판(`spike5.py`, `board_ratio.png`)에 "둘 다 괜찮은데 조금 더 지붕 입체감이 있으면", 지붕을 더한 판(`spike6.py`, `board_roof.png`, `v6_flat.png`·`v6_pitched.png`)에 **"입체감은 이제 괜찮아"**라고 했다. 아래가 그 판의 규칙이고 건물 명세의 기본이다.

### 6.5 건물의 비율과 지붕 (사용자가 승인한 판 `v6_*`의 규칙)

LimeZu의 조각을 쓰지 않는다. 비율과 입체감을 내는 방법만 같다.

- **지붕이 건물 높이의 절반 이상이고 위에서 내려다보인다.** 건물의 깊이는 지붕 면적으로 읽힌다(시험: 가로 160px에 지붕 100px, 벽 84px).
- **정면 벽은 낮다**(시험: 2칸 반 안팎). 재질은 넓은 색 면이 기본이고 벽돌 같은 무늬는 낱장 몇 장만 — 무늬가 잘면 그늘이 묻힌다. 양 끝 벽기둥과 처마 밑 띠로 벽을 묶는다.
- **창은 받침과 함께 앞으로 꺾여 나온다**(양옆 볼: 왼쪽 밝게, 오른쪽 어둡게. 몸통이 벽에 그림자를 드리운다). **문은 두꺼운 틀 안으로 깊이 들어간다**(위·왼쪽에 짙은 그늘, 오른쪽 안벽은 빛). 앞에 계단.
- **간판은 처마 위로 솟아 지붕 가장자리와 겹친다**(앞뒤가 생긴다).
- **외곽선은 짙은 남색 계열**(맞닿은 색을 어둡게 하되 남색 쪽으로).
- **지붕은 두 가지 부품 중 건물마다 고른다.**
  - 평지붕: 난간 윗면(갓돌)과 **뒤 난간의 안쪽 벽**이 보이고, 네 모서리 기둥, 바닥은 뒤가 어둡고 앞이 밝다, 난간이 바닥에 깊은 그림자. 앞 난간은 윗면 + 앞면.
  - 기와지붕: 겹쳐 얹힌 기와(줄마다 위 줄의 그늘 + 밝은 끝단), **아래로 갈수록 줄과 기와가 커진다**, 솟은 용마루와 그 그늘, 뒤 비탈은 어두운 좁은 면, 박공널(왼쪽 밝게, 오른쪽 어둡게), 처마 두께.
- **지붕 위 물건(옥탑, 굴뚝, 실외기, 천창, 박공 지붕창)은 윗면 + 앞면으로 높이를 갖고, 높이만큼 긴 그림자를 오른쪽 아래로 떨어뜨린다.**
- 크기는 명세의 값이다. 시험 건물(5칸)은 LimeZu 가게(약 6.7칸)보다 작았다.

시험판에 남은 결함(정식으로 만들 때 규칙과 검사로 잡는다): 그림자가 물체 모양이 아닌 네모·계단 덩어리, 지붕 위 물건끼리 겹침, 그늘 띠의 경계가 세로줄로 보임, 벽이 낮아져 벽등이 차양에 붙음.

### 6.6 실내의 빛 — 단순하게 (사용자가 "이제 좀 괜찮네"라고 한 판 `v8`의 규칙)

경과: 세 번째 시험의 실내를 다시 보이자 사용자가 "그림자가 너무 어색한데 반사광 주광 이런거 공부해서 다시 만들어볼래"라고 했다. 빛의 구조(주광, 그늘에 주변광 색 섞기, 실루엣을 눕힌 긴 그림자, 반사광, 방 전체 밝기 변화)를 전부 넣은 판(`spike7.py`)은 어색했다. 사용자가 LimeZu 실내 소품을 보자고 했고(`board_limezu_interior.png`), LimeZu처럼 단순하게 다시 그린 판(`spike8.py`, `v8b_interior_x5.png`)에서 수레 밑 그림자 하나를 지적받아 고친 뒤 "이제 좀 괜찮네"를 받았다. **빛을 정교하게 흉내 내는 쪽은 틀린 방향이었다.** 6.1절의 그늘 규칙과 어긋나는 곳은 이 절이 먼저다.

- **면 나누기로 입체를 낸다.** 넓고 밝은 윗면 / 한 단계 어두운 앞면 / 튀어나온 것(윗판, 선반 판) 바로 밑에 짙은 줄 하나. 계산대는 윗면이 높이의 절반쯤이다.
- **그늘에 색을 섞지 않는다.** 면마다 팔레트의 정해진 단계를 쓴다. 방 전체에 밝기 변화를 깔지 않는다. 평평한 면에 그늘 띠를 넣지 않는다.
- **그림자는 물체 바로 밑의 짧은 띠 하나.** 옆으로 눕힌 긴 그림자를 쓰지 않는다.
  - **열마다 그 열에서 물체가 끝나는 곳 바로 아래에서 시작한다.** 다리·바퀴·발로 떠 있는 물체는 몸통 밑(다리 사이)이 가장 어둡고, 거기서 바닥 앞으로 2~3px 한 단계 옅은 띠가 이어지고, 양 끝은 한 단계 더 옅다. (사용자 지적: 수레 몸통 밑은 밝고 바퀴 앞에만 그림자가 있었다 — "말이 안 되잖아".)
  - 벽에 걸린 것은 바로 밑 1~2px. 벽과 바닥이 만나는 줄에 한 줄.
- **유리와 금속에는 사선 반사 줄**(밝은 대각선 몇 줄). 유리 안의 물건 위로도 지나간다.
- **외곽선은 짙은 남회색 한 가지**, 물체 안쪽의 칸 나눔도 같은 색 선. (외관은 6.5절의 남색 계열. 1단계에서 둘을 하나로 맞춘다 — 작성자 판단: 실내 쪽의 한 가지 색으로.)
- **진열하는 물건은 낱개가 아니라 쟁반·선반 단위의 무더기**로 놓는다(조금씩 겹쳐 촘촘히).
- 벽은 윗면(벽의 두께)이 보인다.
- 외관의 지붕 위 물건처럼 높이를 보여야 하는 곳의 그림자(6.5절)는 그대로 둔다. 다만 모양은 이 절의 "물체가 끝나는 곳에서 시작"을 따른다.

`v8` 판에 남은 결함(정식으로 만들 때 잡는다): 진열대·수레의 빈 칸(칸 높이 계산), 계산대 쟁반의 빵이 겹쳐 뭉개짐, 금전 등록기가 작음, 수레 안쪽이 너무 어두움, LimeZu보다 채도가 높고 따뜻함(LimeZu는 회색·보라가 섞인 차분한 색), 화분이 화면 끝에 붙음.

## 7. 도구 명령 (`Tools/pixel-kit/kit.py`)

| 명령 | 하는 일 |
|---|---|
| `render <명세 id…>` | 명세를 그려 `output/pixel-kit/`에 1:1 PNG와 확대 견본판(기준판을 옆에 붙임)을 낸다 |
| `lint <명세 id…>` | 6.2 검사. 문제를 좌표와 함께 적는다 |
| `sheet <세트>` | 세트의 모든 명세를 번호와 함께 한 장에 모은다(사용자가 보는 판) |
| `scene <장면 id>` | 방·거리 미리 보기 |
| `export <명세 id…>` | 검사를 통과한 것만 게임이 읽는 모양으로 낸다. 묶음 시트는 덧붙이기만 한다 |
| `parts` | 부품 목록 판(어떤 부품이 있는지 한 장으로) — 명세를 쓸 때 본다 |

렌더는 결정적이다(같은 명세·같은 `style.json` → 같은 PNG). 시간과 난수를 쓰지 않고 변화는 명세의 씨앗에서만 온다.

## 8. 스킬 `pixel-kit`

`.claude/skills/pixel-kit/SKILL.md`와 `.agents/skills/pixel-kit/SKILL.md`에 같은 내용. 부르는 말: "○○ 건물/외관/타일/가구/방 만들어 줘", "빵집 진열대에 케이크 추가", "픽셀 키트".

순서(스킬이 적을 것):

1. **무엇을**: 요청을 명세 종류로 옮긴다. 게임 데이터와 이어지는 것(장소 id, 가구 id, 시설 레벨의 터 크기)은 `data/`에서 읽는다. 지어내지 않는다.
2. **있는 부품 보기**: `parts` 판을 열어 다시 쓸 부품을 고른다. 없는 것만 새로 만든다.
3. **명세 쓰기**(필요하면 새 점 부품). 새 "만드는 부품"이 필요하면 클래스 하나 + 등록 한 줄 + 테스트.
4. **렌더 → 검사 → 직접 보기 → 고치기**를 되풀이한다. 견본판을 직접 열어 기준판과 나란히 보고 결함을 찾는다. 검사 통과만으로 끝났다고 하지 않는다.
5. **장면에 놓아 보기**: 가구는 방 장면에, 건물은 거리 장면에 놓아 주변과 어울리는지 본다.
6. **사용자에게 판 보이기**: 판 경로(드라이브 문자부터)와 스스로 찾은 부족한 점을 같이 보고한다. 사용자가 고칠 곳을 말하면 명세를 고친다.
7. **승인 뒤 내보내기**: `export` → `dotnet test game/tests/Rootborn.Data.Tests` → 게임에서 스크린샷(스킬 `host-play-test`).

하지 않는다: 견본판을 안 열고 보고하기, 검사를 끄거나 예외를 두기, hex 색을 명세에 직접 적기, 묶음 시트의 이미 있는 자리를 바꾸기, 간판에 글자 그리기, 기획(새 가구·아이템 정의, 차지 칸)을 묻지 않고 정하기.

## 9. 확인하는 법

- **도구 코드**: 렌더러·검사·내보내기는 고정 파일로 테스트한다(`pytest Tools/pixel-kit`). 실패 테스트 먼저. 검사마다 "잡아야 할 결함이 든 그림"과 "깨끗한 그림" 고정 파일을 둔다. 렌더 결과를 통째 픽셀로 고정하는 테스트는 두지 않는다(화풍을 고칠 때마다 깨진다) — 구조(크기, 외곽선 닫힘, 칸 자리)를 본다.
- **그림**: 견본판을 직접 열어 기준판과 같은 배율로 나란히 본다. 보고에 판 경로를 붙인다.
- **게임**: `export` 뒤 Data 테스트(좌표표·정의 읽기), 가구 배치 화면과 맵을 띄운 스크린샷을 직접 본다. 화면 테스트는 그림의 픽셀에 기대지 않는다.
- 근거 종류는 `.claude/rules/core-logic-and-play-evidence.md`. 견본판은 "직접 본 화면"이 아니라 도구가 낸 그림이다. 게임 안에서 보인다는 말은 게임 스크린샷에만 쓴다.

## 10. 순서

| 단계 | 하는 일 | 끝났다는 기준 |
|---|---|---|
| 1. 바탕 + 빵집 다시 | `style.json`, 점 부품·만드는 부품의 틀, `render`·`lint`·`sheet`·`scene`, 스킬 초안. 시험의 빵집을 제대로 다시(6.3절 대책 포함): 외관, 진열대(찬 것·빈 것), 계산대, 빵 12종, 실내 벽·바닥, 보도 | **사용자가 판을 승인 → 화풍 기준판.** 검사 전부 통과 |
| 2. 게임에 한 번 넣기 | `export`. 빵집 가구를 가구 배치 화면에, 타일·외관을 시험 LDtk 레벨에 | 코드 수정 없이 게임 스크린샷에 보인다 |
| 3. 타일·외벽 세트 | 바닥(나무, 타일, 장판, 콘크리트), 실내 벽(직선·모서리·끝), 보도·길·풀·경계석, 외벽 재질(벽돌, 미장, 판자, 콘크리트, 유리) | 3×3 이음 검사 통과, 장면 판 승인 |
| 4. 건물 | 장소 10곳 + 시설 12개(진로 4 × 레벨 3, 터 4×2·5×3·6×4칸) + 일반 집·상가 | 건물 묶음 시트가 LDtk에서 놓인다 |
| 5. 실내 세트 | 세트별(식당 → 집 → 의원 → 훈련장 → …) 가구와 방 장면 | 세트마다 승인 |
| 6. 직업 소품·아이콘 | 음식, 도구, 의료품 등 | 세트마다 승인 |

품목 목록은 앞 문서 5.3절(장소 10곳, 장래희망 8종 기준 세트 표)을 그대로 쓴다. 빵집은 시험 대상이었고, 게임의 장소 목록에 맞춘 첫 세트는 식당이다(1단계의 부품은 식당에 그대로 쓰인다).

## 11. 알려진 한계와 위험

- **부품 그림의 질은 그리는 쪽 솜씨에 달렸다.** 각진 물체(건물, 가구, 타일)는 시험에서 확인했다. 음식·식물·천처럼 유기적인 모양은 확인이 약하다(빵 7종뿐). 1단계에서 식물·음식을 더 그려 보고, 안 되는 종류는 그때 대안을 정한다(사람이 그린 CC0 조각을 점 부품으로 옮기기, 또는 B).
- **디테일의 천장.** 32px 칸에서 넣을 수 있는 양은 정해져 있다. 손그림 팩의 숙련된 그림만큼 나온다는 보장은 없다. 기준판 승인이 그 판단이다.
- **B(확산 모델 시안)는 미룬다.** 붙인다면 Strix Halo에서 분위기 그림만 뽑아 명세를 쓸 때 참고로 열어 본다. 게임 픽셀로는 쓰지 않는다.
- **묶음 시트 자리.** 이미 맵에 놓인 그림의 자리가 바뀌면 맵이 깨진다. `export`는 덧붙이기만 하고, 자리 표를 저장소에 둔다.
- **옛 그림과 섞이는 기간.** 새 세트가 다 찰 때까지 LimeZu 그림과 한 화면에 섞인다. 맵을 새로 그릴 때 세트 단위로 바꾼다.

## 12. 앞 문서(2026-11-12 그림 찍어내기)와의 관계

| 앞 문서의 것 | 이 문서에서 |
|---|---|
| 카탈로그(품목 목록, `id`·`cells`·`art_cells`·`states`·`replaces`) | 조립 명세가 대신한다(값 이름은 그대로) |
| 확산 모델 후보 생성·순위·거절 줄(`plan`·`run`·`rank`·`review`) | **쓰지 않는다** |
| 내보내는 모양(7.3절), 옛 가구 1,503개 다루기(12절 2번), 품목 목록(5.3절), 총기류 표현(12절 7번) | 그대로 |
| "타일은 보류" | 3단계에서 만든다 |
| 0단계 시험(건물 LoRA 등) | 하지 않는다 |

작성자 판단: 앞 문서와 그 구현 계획(`docs/superpowers/plans/2026-11-12-art-production-stage0-1.md`)은 이 문서가 승인되면 "대체됨"으로 표시하고, 그대로인 절(5.3, 7.3, 12절 2·7번)은 이 문서로 옮긴 뒤 지운다.

## 13. 정해야 할 것 (추천안으로 진행하고, 사용자가 다르게 정하면 고친다)

1. **화풍(색, 비율, 외곽선 굵기)**: 시험의 따뜻한 톤으로 1단계를 만들고 기준판에서 승인받는다.
2. **앞 문서를 대체하는가**: 추천 — 대체(12절).
3. **Strix Halo의 쓰임**: 추천 — 그림 생성에는 쓰지 않는다. 시안(B)은 필요해지면 다시 묻는다. 학습해 둔 LoRA는 지우지 않는다.
4. **방 장면을 LDtk 레벨로도 낼 것인가**: 추천 — 지금은 미리 보기만. 맵을 새로 그릴 때 다시 정한다.
5. **아이콘 크기**: 추천 — 32×32 캔버스(앞 문서 12절 5번과 같다).
6. **간판에 글자를 넣는가**: 추천 — 넣지 않는다(다국어). 그림 간판만.

## 14. 만드는 사람에게 맡긴 것

- `style.json`·부품·명세의 값 이름, 팔레트의 실제 색, 그늘 높이, 색 수 한도의 최종값.
- 만드는 부품의 목록과 나눔(창·문 종류를 몇 개로 둘지).
- 견본판 배치와 배율, 묶음 시트의 자리 표 모양.
- 변화 규칙(씨앗 → 색 섞기·덧그림)의 구체적인 방법.

## 15. 검토에서 나온 질문과 답 (2026-11-13, 이 문서만 읽고 만들 수 있는지 다른 눈으로 읽힘)

아래는 모두 작성자 판단이다. 사용자가 다르게 정하면 고친다.

1. **타일을 내보내는 모양**: `art/tiles/<세트>.png` 32px 격자 시트 + 좌표표. 자리는 덧붙이기만 한다. 32×64 실내 벽은 시트에서 위아래 두 칸이다. 직선·모서리·끝은 LDtk에서 사람이 고른다(자동 규칙을 전제하지 않는다). 이음 검사는 "같은 타일끼리 3×3"과 "세트 안에서 이웃하도록 표시한 짝"을 본다.
2. **2단계의 시험 LDtk 레벨**: 만드는 사람이 테스트 고정 파일로 작은 `.ldtk` 하나를 쓴다(타일 층 하나 + `art` 태그 엔티티 층 하나). 기존 LDtk 프로젝트와 `game/world/maps.json`은 건드리지 않는다. 게임에 띄우는 길(`--maps`로 시험용 맵 목록을 주는 방법 등)은 계획 때 `game/README.md` 인자 표에서 확인한다. "LDtk 맵을 자동으로 만들지 않는다"는 실제 게임 맵 이야기다.
3. **시설 겉모습 12개**: MonoGame 판은 지금 `FacilityVisualDefinition`을 그리지 않는다(`Rootborn.Data/Builders/NotRules.cs`에만 있다). 4단계는 그림과 묶음 시트까지 만든다. 레벨에 따라 시설 겉모습을 바꿔 그리는 일은 게임 쪽 작업이라 이 설계 밖이고, 4단계를 시작할 때 사용자에게 따로 알린다.
4. **건물 명세의 크기**: 5.2절 예시의 `size`를 둘로 나눈다 — `site`(터, 칸. 시설은 데이터의 터 크기)와 `pixels`(그림 크기, 게임 픽셀). 부품 자리 `at`은 그림 왼쪽 위 기준 **정수 픽셀**이다(소수 칸을 쓰지 않는다). 문 자리에서 입구 칸을 계산해 견본판에 표시하되, 데이터의 충돌·입구 칸은 고치지 않는다.
5. **2단계에 무엇을 게임에 넣는가**: 빵집 가구를 `data/`에 넣지 않는다(게임 장소가 아니고, 가구 id는 세이브에 남는다). 2단계는 이미 있는 가구 두세 개를 `replaces`로 그림만 바꿔 확인한다(id·규칙·세이브 그대로). 새 가구 정의(이름, 분류, 놓는 면, 막는지)는 세트마다 목록으로 사용자에게 보이고 정해진 것만 명세의 `game` 덩어리에 적는다.
6. **상태(`states`)**: 기본 상태만 가구 정의에 연결한다. 다른 상태는 같은 PNG·좌표표에 `<id>@<상태>` 칸으로 함께 내 둔다. 게임이 상태를 쓰게 되는 것은 따로 정할 기획이다.
7. **경로와 배포**: 내보내는 자리는 5절(위에서 고침). 배포 빌드(`Tools/publish`)가 `art/`를 담는지는 2단계에서 확인하고, 빠져 있으면 배포 설정을 고친다(게임 코드는 아니다).
