# ROOTBORN을 Unity 밖으로 옮기기 — 설계 초안

- 날짜: 2026-11-11 (main `097d76b9d` 기준 조사)
- 상태: **사용자 승인(2026-11-11).** 전체 방향과 순서를 정한 문서다. 프로젝트 0(스파이크)은 끝났고, 프로젝트 1부터는 각자 설계 문서를 따로 쓰고 승인받은 뒤 만든다.
- 작성 경위: 사용자가 질문 단계를 건너뛰고 조사와 초안을 요청했다. 그래서 이 문서의 선택은 대부분 **작성자(Claude)의 판단**이고, 사용자가 정한 것은 1절에 따로 적었다. 마지막 절에 사용자가 정해야 할 것을 모았다.

## 1. 사용자가 정한 것

- 목표는 "Unity는 화면만 맡기기"가 아니다. 게임이 Unity 없이 다른 엔진이나 자체 프로그램에서 돌아가야 한다.
- **MonoGame으로 간다 (2026-11-11 결정).** 초안의 추천은 Godot이었으나 사용자가 MonoGame/FNA 계열로 바꿨다. 이유: UI 토대를 통째로 만들어야 하지만, 그만큼 UI에 버그가 있어도 직접 고칠 수 있다. FNA와 MonoGame 둘 다 스파이크로 시험한 뒤 사용자가 MonoGame을 골랐다(작성자 의견은 근소하게 FNA였다).
- 여러 독립 프로젝트로 쪼개지면 순서를 정하고 하나씩 따로 브레인스토밍한다.
- 걷어내려는 이유 중 하나: Unity 에디터 테스트가 수 분, 메모리 4~10GB를 쓴다.
- 사용자의 미커밋 변경과 세이브를 건드리지 않는다. 항상 한국어.

눈여겨볼 사실:

- 규칙 쪽 MonoBehaviour는 적다(Quests 0/46, DiscoveryClues 0/31, Careers 0/18, StudentLife 12/163). 진행 상태는 이미 순수 클래스 + 얇은 컴포넌트 래퍼 구조다.
- **전략 SO가 로직을 담는다.** 예: `DayEndRuleBase : ScriptableObject`의 `abstract Apply(StudentLifeProgress)`. 이런 SO 클래스가 약 110개다. 옮길 때 가장 큰 일은 이것을 "순수 클래스 + 데이터 파일"로 바꾸는 것이다.
- 규칙 코드는 `UnityEngine.Random`을 쓰지 않고, `Time.*`도 GameClock·플레이어·조명 쪽에만 있다. `Managers.` 전역 접근은 7개 파일에만 있다.
- `Rootborn.Game`에는 `using Unity.Netcode`가 없다. 네트워크 의존은 Network 폴더와 UI 4개 파일뿐이다.
- 세이브는 `System.IO` + `JsonUtility`이고 저장 경로는 한 곳에서 정한다. 데이터 모델은 순수 `[Serializable]` 클래스다.
- 캐릭터 애니메이션은 코드로 프레임을 넘긴다(`CharacterPartAnimator`). Timeline 사용처는 0건이다.

### 2.3 씬과 맵

- 원본은 LDtk 3개(`Assets/LDtk/Town/town.ldtk`, `Interiors/interiors.ldtk`, `House/house.ldtk`)다. 그러나 씬은 LDtk를 실행 중에 읽지 않고 Tilemap을 씬 YAML에 직접 저장한다(Town 29층, 5MB). 충돌과 실내 출구는 메뉴로 LDtk에서 구워 넣는다.
- NPC, 포탈, 상호작용 지점은 대부분 실행 중에 Installer 코드가 데이터에서 만든다.
- **위험:** 저장된 씬이 LDtk 원본과 어긋나 있을 수 있다. 씬에서 직접 손댄 타일이 있으면 LDtk만 읽어서는 같은 화면이 나오지 않는다.

### 2.4 테스트와 검증

- EditMode .cs 415개 중 163개가 `AssetDatabase`, 205개가 `ScriptableObject.CreateInstance`, 56개가 `EditorSceneManager`를 쓴다. 즉 상당수가 "Unity 에셋 와이어링 검사"와 "씬 구조 검사"이고, 새 환경에서는 대상 자체가 사라지거나 데이터 검증으로 바뀐다.
- PlayMode E2E는 `PlayerFlowE2EDriver`(963줄)가 가상 키보드·마우스 장치 이벤트로 걷기, 클릭, 휠, 문 통과, 미니게임 완주, 스크린샷을 한다. 테스트 본문은 드라이버 호출 위주지만 GameObject 이름 문자열로 대상을 찾는다.
- FEVM 기준선(Scripts/fevm/README.md): EditMode 2,090건 중 2,029 통과, PlayMode 166건 중 164 통과.

### 2.5 멀티플레이

- 세션 4종(Single, Host, Client, DedicatedServer), 서버 권한.
- 동기화 대상은 적다: 캐릭터 외형, 월드 시간, 퀘스트·생활 활동 알림. 플레이어 위치 동기화는 스크립트에서 찾지 못했다(메모리 기록에는 "남의 캐릭터는 걷지 않는다"가 있다).
- Steam: `SteamNetworkingTransport`가 NGO용 커스텀 트랜스포트다. 로비는 `SteamMatchmaking` 친구 전용, 참가는 초대나 실행 인자.

### 결정: MonoGame — 사용자 결정

초안은 UI·한글 글꼴·IME를 받아 쓸 수 있다는 이유로 Godot을 추천했다. 사용자는 MonoGame/FNA 계열을 골랐다. 직접 만든 UI는 구조를 전부 알고 있어 버그를 끝까지 따라가 고칠 수 있고, 엔진에 다시 묶이지 않으며, 빌드와 테스트가 `dotnet` 명령만으로 끝난다. 대가는 아래 "직접 만드는 것"이다.

MonoGame과 FNA는 같은 XNA API를 구현한 별개 라이브러리다. 같은 스파이크를 둘 다로 돌려 비교했고(6절 "스파이크 결과"), 둘 다 통과 기준을 모두 넘었으며 화면은 픽셀 단위로 같았다. 사용자가 MonoGame을 골랐다.

| | MonoGame 3.8.6.1 (선택) | FNA |
|---|---|---|
| 받는 방법 | NuGet 한 줄, 네이티브 라이브러리 자동 | 소스 복제 + 일일 빌드 라이브러리를 로그인해 받음 |
| Linux(FEVM) 실행 | 추가 설정 없음 | 렌더러 강제와 라이브러리 경로 필요 |
| 실행 프로그램 메모리 | 206MB(Windows) | 283MB(Windows) |
| 조합 중 글자 | 공개 API 없음. SDL2 직접 호출로 해결 | 공개 API |
| 테스트에서 한 프레임씩 돌리며 입력 넣기 | 내부 메서드를 리플렉션으로 호출 | 공개 API |
| 라이브러리 직접 수정 | 소스를 따로 받아 빌드해 교체 | 프로젝트 안 소스를 바로 고침. 원본은 AI가 쓴 코드를 받지 않음 |
| 사용자·자료 | 많음 | 적음 |

MonoGame을 쓰면서 안고 가는 것:

- **테스트 토대가 MonoGame 내부에 기댄다.** `RunOneFrame`이 입력 이벤트를 읽지 않아 내부 메서드 `SdlRunLoop`를 리플렉션으로 부른다. 그래서 MonoGame 버전을 정확히 고정하고(3.8.6.1), 올릴 때는 이 호출과 한글 조합 입력을 확인하는 테스트를 먼저 돌린다. 이 호출은 한 곳(테스트용 프레임 진행기)에만 둔다.
- **한글 조합 입력은 SDL2 직접 호출에 기댄다.** 이것도 한 곳(Host의 글자 입력 계층)에만 둔다.
- 코드는 XNA API 범위 안에서 쓴다. 위 두 곳을 빼면 FNA로 바꿀 수 있는 상태를 유지한다.

## 4. 목표 구조

```
Rootborn.Core        순수 C#. 규칙, 진행 상태, 세이브 모델, 월드 시뮬레이션(위치·격자 충돌·문·상호작용 판정)
Rootborn.Data        데이터 파일(JSON) 읽기, 스키마, 검증
Rootborn.Net         메시지 정의와 세션 규칙. 전송은 인터페이스 뒤(Steam 소켓 / UDP)
Rootborn.Ui          UI 토대. 배치·포커스·포인터 판정은 순수 로직, 그리기는 인터페이스 뒤
Rootborn.Host        실행 프로그램. 그리기, 입력, 소리, 창. MonoGame 참조는 여기만
data/                JSON 데이터, 스프라이트 좌표표, 현지화, LDtk 원본
```

원칙:

- **Core는 엔진을 모른다.** 지금의 `noEngineReferences` 원칙을 전체 규칙으로 넓힌다.
- **걷기와 충돌도 Core에 둔다.** 탑다운 격자 충돌은 단순하다. 위치·충돌·문·상호작용 범위를 Core가 계산하면 "걸어가서 문을 통과해 NPC와 대화"를 엔진 없이 `dotnet test`로 돌릴 수 있고, 화면 담당은 결과를 그리기만 한다.
- **화면 담당은 얇게.** Host는 Core의 상태를 읽어 그리고, 입력을 Core의 명령으로 넘긴다. 규칙 판단을 Host에 쓰지 않는다.
- **데이터는 프레임워크 형식에 넣지 않는다.** JSON과 PNG가 원본이고 변환 단계를 두지 않는다.
- **MonoGame 참조는 Host에만 둔다.** Core, Data, Net, Ui의 로직 부분은 MonoGame 타입을 쓰지 않는다. CI가 참조를 검사한다. 화면은 지금처럼 코드로 조립한다.
- **게임 루프를 직접 쥔다.** 시간은 Host가 Core에 넘겨 주는 값으로만 흐른다. 테스트는 같은 루프를 창 없이, 또는 창을 띄워 한 프레임씩 돌린다.
- 엔티티 데이터 드리븐 원칙(ID 분기 금지), 보상 트랜잭션 원칙, Objective Journal 소유권, Style2/도시형 몰딩 패널 규약은 그대로 유지한다.

## 5. 데이터 옮기기

### 형식

- 엔티티 하나가 JSON 객체 하나. 도메인별 파일 묶음(`data/quests/*.json` 등).
- 참조는 guid가 아니라 **`id` 문자열**로 한다.
- 전략 배열은 별도 파일이 아니라 **엔티티 안에 넣고 `type` 필드로 구분**한다. 예: `"rewards": [{ "type": "furnitureUnlock", "furnitureId": "..." }]`. 여러 엔티티가 같은 전략을 공유하던 곳은 id 참조를 허용한다.
- 가구 1,503개는 가구 JSON으로 옮기고, Tile 껍데기 1,548개는 버린다. 가구는 스프라이트를 직접 가리킨다.
- 스프라이트 슬라이스는 PNG 옆 좌표표(`<이름>.atlas.json`)로 뽑는다.
- 현지화는 `ko.json`/`en.json` 키 파일로 둔다. 카탈로그 "앞 593줄 고정" 같은 제약은 형식이 바뀌면서 다시 정한다.

### 변환 방법

- **Unity 없이 도는 변환기**(C# 콘솔)를 만든다. Unity YAML과 `.meta`는 텍스트라서 직접 읽을 수 있다. 수 초에 끝나고 몇 번이든 다시 돌릴 수 있다.
- 변환기는 실패를 숨기지 않는다. 풀리지 않는 guid, `_id` 없는 엔티티, 삭제된 이미지를 가리키는 참조는 목록으로 내고 종료 코드로 알린다(메모리 기록: 삭제된 이미지 guid를 참조하는 YAML이 남아 있다).
- 전환 시점까지는 **Unity 에셋이 원본**이고 JSON은 변환 결과다. 커밋된 JSON이 변환 결과와 같은지 CI가 확인한다. 전환(프로젝트 7) 때 JSON이 원본이 된다.

### Unity 없이 편집

- 지금도 데이터는 대부분 에이전트와 생성기 스크립트가 만든다. 전환 뒤에는 JSON을 직접 고친다.
- JSON Schema를 함께 두어 편집기 자동완성과 오류 표시를 받는다.
- 검증 명령 하나(`dotnet run --project Tools/Rootborn.Data.Validate`)가 지금의 와이어링 EditMode 테스트를 대신한다: id 중복, 끊어진 참조, 없는 스프라이트, 없는 현지화 키, 등록 누락.
- 전용 데이터 편집 화면은 만들지 않는다. 필요해지면 그때 따로 다룬다.
- 맵은 지금처럼 LDtk에서 고친다. 새 환경은 LDtk를 직접 읽으므로 "칠하고 굽기" 단계가 없어진다.

뒤 프로젝트에 넘기는 사실:

- xdotool의 `key`는 누름과 뗌이 한 프레임에 들어가 놓친다. `keydown` → 대기 → `keyup`으로 쓴다.
- 스크린샷 해시 비교는 GPU 경로로만 한다. 소프트웨어 렌더링은 값 1 차이가 난다.

- Steam 네이티브 라이브러리는 NuGet 패키지에 없다. 독립 실행판에서 받은 파일을 저장소에 버전 고정해 둔다.
- 배포 가능한 한글 글꼴을 골라 넣어야 한다. 저장소에 TTF가 없다.
- 스파이크의 충돌 규칙은 임시였다. 실제 자동 판정과 칠한 Collision 층 규칙은 프로젝트 1·3에서 옮긴다.

### 옮기는 동안의 규칙

- Unity 코드와 `Assets/` 아래는 고치지 않는다. 참고용으로 읽기만 한다.
- MonoGame 판 화면이 Unity 판과 같은지는 같은 지점의 스크린샷을 나란히 놓고 본다. Unity 쪽 화면은 기준본 태그의 빌드나 기존 증거(`output/`)에서 얻는다.
- 맵 원본(LDtk)과 Unity 씬의 어긋남은 프로젝트 3 처음에 맵별로 대조해 확인한다. 어긋난 곳은 LDtk 원본을 고친다.
- 기존 세이브 파일은 새 판에서도 읽는다. 검증은 고정용 세이브로 하고 사용자 세이브는 쓰지 않는다.

## 9. 하지 않는 것

- Unity 판과 새 판을 한 프로세스에서 섞어 돌리지 않는다.
- 기성 UI 라이브러리와 콘텐츠 변환 파이프라인을 들이지 않는다.
- 범용 엔진이나 범용 UI 프레임워크를 만들지 않는다. 이 게임 화면에 필요한 것만 만든다.
- 옮기면서 게임 기획이나 화면 디자인을 바꾸지 않는다. 같은 게임을 옮긴다.
- 레거시 Farm과 `[Ignore(LegacyPremise.*)]`로 격리된 테스트는 옮기지 않는다.
- 전용 데이터 편집기, 웹 내보내기, 모바일은 다루지 않는다.

## 10. 실패로 보는 경우

- 새 판이 돌아가지만 규칙이 다시 Host나 화면 코드 안에 쓰여 있는 경우.
- UI 토대를 만드는 데 빠져 게임 화면 이전이 시작되지 않는 경우.
- 테스트는 통과하는데 실제 입력으로 플레이한 근거가 없는 경우.
- 옮기는 도중 Unity 판도 새 판도 끝까지 플레이할 수 없는 기간이 생기는 경우.
