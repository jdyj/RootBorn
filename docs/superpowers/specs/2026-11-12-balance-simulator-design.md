# 수치 균형 시뮬레이터 — 직업을 계속 돌렸을 때 돈이 얼마나 벌리는가

작성일: 2026-11-12
상태: **초안. 사용자가 "추천안대로 진행해"라고 했다.** 아래에서 "사용자"라고 적은 것만 사용자가 말한 것이고, "추천"이라고 적은 것은 이 문서를 쓴 쪽의 판단이다.

## 2. 한 줄 요약

**화면 없이 `GameSession` 명령만으로 "한 가지 전략만 되풀이하는 플레이어"를 여러 날 돌리고, 직업·전략별 수입을 표로 낸다.** 보상 계산식을 따로 베끼지 않고 실제 규칙을 부르므로, `data/`의 수치를 고치면 표가 바로 바뀐다.

지금 있는 `Rootborn.Simulation.Tests`(자동 플레이어)는 "플레이가 깨지지 않는가"를 본다. 이것은 "수치가 고른가"를 본다. 둘은 목적이 달라 따로 둔다.

## 4. 목표와 하지 않을 것

**목표**

1. 직업(시설)마다, 알바마다 "이것만 계속 하면" 하루에, 게임 시간당, 실제 시간당 얼마를 버는지 같은 표에서 견준다.
2. 시설을 올리는 데 며칠이 걸리고, 올린 값을 며칠 만에 되찾는지 본다.
3. `data/`를 고친 뒤 명령 한 번으로 표를 다시 낸다. 같은 데이터는 언제나 같은 표를 낸다.
4. 새 직업·새 알바는 데이터를 더하면 표에 저절로 나온다. 새 전략은 설정 파일에 한 덩어리를 더한다. 새 행동 종류만 클래스 하나와 등록 한 줄이다.
5. 정한 범위를 벗어나면 CI가 막는다(범위 값은 사용자가 첫 표를 본 뒤 정한다, 9절).

**하지 않을 것**

- 미니게임을 실제로 푸는 것. 점수는 가정으로 준다(6.2절). 실제로 푸는 것은 `Rootborn.Simulation.Tests`가 한다.
- 화면, 걷기, 맵. 걷는 시간은 가정 값으로 시계만 돌린다.
- 가장 잘 버는 전략을 스스로 찾는 것(최적화). 사람이 적은 전략을 돌려 견줄 뿐이다.
- 같이 하기(공유 지갑). 혼자 하기만 본다.
- 수치를 고치는 것. 시뮬레이터는 재기만 한다. 수치를 바꾸는 결정은 사용자가 한다.

**이렇게 되면 실패다**

- 시뮬레이터가 보상 식이나 비용을 따로 베껴 갖고 있어서, 규칙을 고쳐도 표가 그대로인 것.
- 시뮬레이터 코드가 직업·알바·시설 id를 아는 것(`rules/data-driven.md`).
- 표의 숫자를 "실제 플레이로 확인"처럼 보고하는 것. 이것은 가정을 넣은 계산이다(`rules/core-logic-and-play-evidence.md`의 "자동 테스트").
- 돌릴 때마다 숫자가 달라지는 것.
- 평소 테스트 실행이 눈에 띄게 느려지는 것.

## 5. 어디에 두나

추천: 새 테스트 프로젝트 `game/tests/Rootborn.Balance.Tests`. 참조는 `Rootborn.Game`, `Rootborn.Data`(화면·월드·MonoGame 참조 없음). `game/Rootborn.sln`에 더한다.

- 왜 따로: 여러 날을 도는 긴 실행, 자기 출력 폴더, 자기 설정 파일이 있다. Game 테스트에 섞으면 흐름 테스트와 균형 보고가 한 곳에 엉긴다.
- 왜 테스트 프로젝트: 실제 `data/` 읽기와 게임 시작 도우미(Game 테스트의 `TestWorld`)가 이미 테스트 쪽에 있고, CI `dotnet-tests`가 `game/tests`의 프로젝트를 저절로 돈다. 배포물에 들어가지 않는다.
- `TestWorld`와 `DayBalanceTests`의 걷기·미니게임 시간 보내기·가정 읽기는 **베끼지 않고 함께 쓴다**(파일 연결이든 공용 파일로 빼든 만드는 쪽이 정한다). `DayBalanceTests`의 동작과 건수는 그대로여야 한다.

파일:

```

  Run/                      한 판 돌리기, 하루 돌리기, 기록
  Actions/                  행동 종류(클래스 하나씩) + 등록 한 곳
```

`money-balance.json`은 `day-balance.json`처럼 배포와 데이터 지문에 들어가지 않는다(Data 테스트 `DataFingerprintScopeTests`가 지키는 범위를 확인한다).

```
                                              │
                                              └──▶ 범위 검사(정해진 것만)
```

### 6.1 대상 — 데이터에서 저절로

- 시설 전략은 `GameDefinitions.All<Facility>()`의 시설마다 한 판씩 돈다. 알바 전략은 알바 정의마다 한 판씩 돈다. 코드와 설정 파일에 id를 적지 않는다.
- 설정 파일의 전략은 대상의 **종류**만 말한다(`"each": "facility"`, `"each": "part-time-work"`). 종류는 등록 한 줄로 더한다.

### 6.2 플레이어 가정

- **점수 단계**(추천, 설정 파일에서 바꾼다): 낮음 60(겨우 성공), 보통 80, 만점 100. 한 판은 한 단계로 끝까지 간다. 알바는 성공·실패만 있으므로 세 단계 모두 성공으로 돈다.
- 점수를 정하는 것은 "점수 모델" 한 종류다. 첫 판은 **고정 점수**만 만든다. 흩어진 점수(씨앗으로 정해지는 분포)나 "몇 번에 한 번 실패"는 필요해지면 종류를 더한다.
- **걷는 시간, 미니게임을 하는 시간**: `day-balance.json`의 값을 쓴다(활동마다 30분, 제한 시간 합의 0.5). 미니게임 동안 실제 초만큼 시계를 돌린 뒤 정산한다(`DayBalanceTests`와 같다).
- **자는 때**(추천): **취침 시각까지 끝나는 행동만 시작한다.** 걷는 시간을 보낸 뒤 그 행동의 길이를 더해 취침 시각을 넘으면 시작하지 않고 잔다. 왜: 넘겨 끝나는 일을 날마다 하면 밤 체력 감소와 줄어든 회복이 30일 동안 쌓여, 수입 표에 "지쳐서 멈춤"이 섞인다. `DayBalanceTests`는 "취침 시각 전에 시작하면 된다"로 하루만 보는데, 그 검사는 그대로 둔다. 이 값은 설정 파일의 한 칸으로 두어 "취침 시각 전에 시작"으로도 돌릴 수 있게 한다. 밤을 새워 더 버는 전략은 첫 판에 넣지 않는다.
- **자동 넘기기**: 쓰면 미니게임 실제 시간이 0이 되고 **점수가 100으로 고정된다**(Core `AdultCareerService`). 그래서 낮음·보통 판은 자동 넘기기가 되는 날부터 수입이 만점으로 뛴다 — 이것은 규칙대로이고 표에 그대로 나와야 한다. 조건은 시설 레벨 2 이상과 그 일의 숙련 100(성공 5번)이고, 숙련은 일마다 따로 쌓인다. 전략이 어떻게 쓰는지는 6.3절.
- **가방이 차면**: 통화가 아닌 보상(상점 일의 나무 등)으로 가방이 차서 명령이 거절되면 버리거나 팔지 않는다. 그날 멈춘 이유에 "가방 참"을 적고, 요약에 처음 막힌 날을 적는다. 왜: 버리기·팔기를 지어 넣으면 규칙에 없는 수입이 생긴다. 막히는 것 자체가 균형에서 볼 사실이다.

### 6.3 전략 — 행동의 차례

전략은 "차례대로 시도할 행동 목록"이다. 하루 동안 맨 앞부터 되는 것을 하나 하고 다시 처음부터 본다. 아무것도 안 되면 잔다. 예(모양은 만드는 쪽이 다듬는다):

```json
{ "id": "facility-work-and-upgrade", "each": "facility", "start": "adult",
  "autoSkip": true,
  "do": ["upgrade-facility", "best-facility-work"] }
```

첫 판의 행동 종류(추천):

| 종류 | 하는 일 |
|---|---|
| `upgrade-facility` | 올릴 수 있으면 올린다(`CanUpgradeFacility`가 된다고 할 때만) |
| `best-facility-work` | 지금 시설 레벨에서 할 수 있는 일 중 레벨이 가장 높은 것 하나를 미니게임으로 한다(`FacilityStatus`의 조회로 고른다) |
| `auto-skip-facility-work` | 자동 넘기기가 되는 일(`CanAutoSkip`) 중 레벨이 가장 높은 것을 넘긴다. 없으면 안 된 것으로 치고 다음 행동으로 간다 |
| `part-time-work` | 대상 알바를 한다 |
| `any-part-time-work` | 할 수 있는 알바를 돌아가며 한다 |

첫 판의 전략(추천):

| 전략 | 대상 | 본다 |
|---|---|---|
| 알바 하나만 | 알바마다 | 알바끼리, 알바와 시설 일의 차이 |
| 알바 돌아가며 | 한 판 | 학생 때 하루 수입의 위쪽 |
| 시설 일만(안 올림) | 시설마다 | 레벨 1에 머물 때 |
| 시설 일 + 되는 대로 올림, 자동 넘기기 안 씀 | 시설마다 | 레벨 3까지 걸리는 날, 되찾는 날 |
| 시설 일 + 되는 대로 올림, 자동 넘기기 먼저(`upgrade-facility`, `auto-skip-facility-work`, `best-facility-work` 차례) | 시설마다 | 실제 시간당 수입이 어떻게 달라지나 |

자동 넘기기 먼저 전략은 넘길 수 있는 일이 있으면 그것만 하므로, 올린 뒤에는 숙련이 찬 낮은 레벨 일을 넘기고 새 레벨 일의 숙련은 쌓지 않는다. 낮은 점수 판에서는 이쪽이 더 번다(레벨 2에서 60점: 넘긴 레벨 1 일 45 대 직접 한 레벨 2 일 36). "새 일의 숙련을 채운 뒤 넘기기"는 필요해지면 전략을 하나 더한다. 어느 쪽이 더 버는지는 시뮬레이터가 계산하지 않는다(보상 식을 베끼지 않는다) — 전략을 나란히 돌려 표에서 본다.

### 6.4 시작 상태

- 알바 전략: 새 게임 첫날부터.
- 시설 전략(`"start": "adult"`): 그 시설을 고른 성인 첫날부터. 거기까지는 **준비 단계**다. Game 테스트 `AdultCareerTests`의 준비(`SaveEdits.MakeChefCandidateReady`)는 요리 id를 직접 적은 요리 전용이라 그대로 쓸 수 없다. 시설 정의에서 진로와 후보를 끌어내는(`Facility`의 진로·후보 조회) 일반 준비를 새로 쓴 뒤 `ChooseFacility`를 부른다. 준비 때문에 시작 날이 4일째 이후가 되고 요일·체력·지갑이 새 게임과 다를 수 있다 — 그대로 받고, 판의 첫 줄에 시작 날·요일·지갑을 적는다. 수입은 시작 지갑을 뺀 값으로 센다.
- 학생 첫날부터 성인까지 이어서 도는 판은 3단계다(10절).

### 6.5 기록

날마다 한 줄:

| 칸 | 뜻 |
|---|---|
| 판 | 전략 id, 대상 id, 점수 단계 |
| 날 | 며칠째, 평일·주말 |
| 지갑 | 그날 끝의 용돈 |
| 번 것·쓴 것 | 그날 지갑이 늘어난 합, 줄어든 합(시설 올리기) |
| 다른 보상 | 통화가 아닌 보상 아이템의 개수(아이템 id별. 시설 재료 등) |
| 한 일 | 행동 수, 행동 id별 횟수 |
| 일한 게임 시간 | 분(걷기 포함·제외 둘 다) |
| 실제 시간 | 그날 깨어 보낸 실제 초, 그중 미니게임에 쓴 초 |
| 시설 | 레벨, 그날 올렸는지 |
| 남은 체력·집중, 멈춘 이유 | `DayBalanceTests`와 같은 뜻 |

통화가 무엇인지는 `game/economy.json`의 `currencyItem`에서 읽는다. 아이템 id를 코드에 적지 않는다.

판마다 요약 한 줄: 하루 평균 수입, 게임 시간당 수입, **실제 분당 수입**(걷기를 넣은 것과 미니게임 시간만 센 것 둘 다 — 자동 넘기기만 하는 날은 뒤쪽 분모가 0이라 빈칸), 가방이 차서 처음 막힌 날, N일 뒤 지갑, 레벨 2·3에 닿은 날, 올린 값을 되찾은 날(올린 뒤 늘어난 하루 수입으로 나눈 날 수), 하루 평균 행동 수, 자동 넘기기가 처음 된 날.

돈 말고 같이 적는 것(추천, 사용자의 "등"): 다른 보상 아이템, 하루 끝 체력·집중. 특성·기술·평판이 자라는 양은 첫 판에 넣지 않는다 — 필요하면 칸을 더한다.

### 6.6 내는 것

- `output/balance/<실행 이름>/days.csv`, `summary.csv`, `report.md`(사람이 읽는 한글 표: 전략별로 대상을 나란히, 가장 많이 버는 것과 가장 적게 버는 것의 비).
- `report.md` 맨 위에 쓴 가정(점수 단계, 걷는 시간, 미니게임 몫, 날 수)과 "가정을 넣은 계산이다, 실제 플레이가 아니다"를 적는다.
- 출력 폴더는 저장소의 `output/` 아래가 기본이고 환경 변수로 바꾼다(`ROOTBORN_BALANCE_OUT`, `game/README.md` 표에 적는다). 날 수는 `ROOTBORN_BALANCE_DAYS`(기본 추천 30).
- 표를 저장소에 커밋해 두지는 않는다(데이터를 고칠 때마다 다시 내야 해서). 필요하면 나중에 정한다.

### 6.7 테스트와 실행

- **빠른 검사**(평소·CI): 짧은 날 수로 모든 전략이 한 번씩 끝까지 돈다 — 예외 없음, 날마다 기록 한 줄, 같은 입력으로 두 번 돌리면 같은 결과, 지갑 변화 = 번 것 − 쓴 것, 준비 단계의 돈이 섞이지 않음. 전체 10초 안쪽을 목표로 한다.
- **전체 보고**(손으로, `[Explicit]`): 기본 날 수로 모든 판을 돌려 파일을 쓴다. 실행 명령을 `game/README.md`의 "손으로만 도는 테스트"에 적는다.
- **범위 검사**: `money-balance.json`의 `bands`에 적힌 것만 본다(9절). 비어 있으면 아무것도 막지 않는다.
- 시뮬레이터 자체의 테스트는 실패 테스트 먼저 쓴다. 기록 계산(되찾는 날 등)은 실제 데이터가 아닌 작은 손 계산 예로 고정한다.
- 저장: 판마다 저장소 하나를 쓴다. 디스크 임시 폴더가 느리면 메모리 저장소를 쓴다(만드는 쪽이 재서 정한다). 사용자 세이브 폴더는 쓰지 않는다.
- 근거 종류: 전부 "자동 테스트". 화면이나 실제 플레이의 근거가 아니다.

## 7. 규칙과 맞는지

- 엔티티 id로 분기하지 않는다: 대상은 정의 목록에서, 통화는 설정에서 읽는다. CI `check-no-entity-id-branching.sh`는 `game/tests`를 빼지만, 여기서는 테스트 코드라도 id를 적지 않는다(새 직업이 저절로 나오게).
- 규칙은 Core에만: 시뮬레이터는 `GameSession` 명령·조회만 부른다. 필요한 조회가 없으면 `GameSession`에 조회를 더한다(규칙을 테스트 쪽에 다시 쓰지 않는다).
- 종류를 enum·switch로 닫지 않는다: 행동 종류, 대상 종류, 점수 모델은 클래스 하나 + 등록 한 줄.
- 환경 의존 값: 출력 폴더와 날 수는 환경 변수, 기본은 저장소 안.
- 게임 코드와 `data/`는 고치지 않는다(조회를 더하는 것은 빼고).

## 8. 성능

- 한 판 = `GameSession` 하나 × 날 수. 하루에 명령 십여 개다. 첫 판 규모(알바 9 + 알바 돌아가며 1 + 시설 4 × 3 전략) × 점수 3단계 × 30일 ≈ 2,000일이다.
- 느려질 수 있는 곳: 날마다 하는 저장(하루 사본 포함), 판마다 정의 읽기. 정의는 한 번 읽어 함께 쓴다(`TestWorld.Definitions`처럼). 저장이 병목이면 메모리 저장소로 바꾼다.
- 완료 조건: 빠른 검사 10초 안쪽, 전체 보고 1분 안쪽을 재서 보고에 적는다. 넘으면 무엇이 느린지 적는다.

## 9. 범위 검사 — 값은 사용자가 정한다

범위는 기획 결정이다. 첫 표가 나온 뒤 사용자가 정한다. 그 전에는 `bands`를 비워 둔다. 표를 보고 정할 만한 것(예시일 뿐이다):

- 시설끼리 하루 수입의 가장 큰 것 ÷ 가장 작은 것이 몇 배 이내인가.
- 시설끼리 **실제 분당 수입**이 몇 배 이내인가(지금 값으로는 미니게임 길이 때문에 크게 벌어질 것으로 본다).
- 시설 일 하루 수입 ÷ 알바 하루 수입이 어느 범위인가.
- 레벨 2·3에 닿는 날이 어느 범위인가.

검사 종류도 클래스 하나 + 등록 한 줄로 더한다. 실패 문구에는 어느 판이 얼마였는지가 나온다.

## 10. 단계

1. **1단계(이 문서의 범위)**: 프로젝트, 한 판 돌리기, 6.3절의 전략, 기록, 파일 내기, 빠른 검사, 첫 표.
2. **2단계**: 사용자가 첫 표를 보고 정한 범위 검사. 값 환산표 — 가구 값(`data/interiors`의 `price`)과 시설 올리는 값을 "며칠 치 수입인가"로 바꿔 보인다.
3. **3단계**(필요해지면): 학생 첫날부터 성인까지 이어서 도는 판, 흩어진 점수, 밤샘 전략, 특성·기술 성장 칸, 직업 사이 자유도 설계(`2026-11-12-cross-career-freedom-design.md`)의 공간 보정이 들어온 뒤의 전략.

## 13. 2단계 — 모든 경우 훑기 (2026-11-13 사용자 지시)

사용자(2026-11-13):

- 자는 때도, 밤새는 게 효율이 좋은지 언제 자는 게 효율이 좋은지 시뮬레이션이 있었으면 좋겠다.
- 대신 정한 것이 딱 한 가지 경우만 해 놨다. 필요한 것은 모든 가지의 경우를 하는 것이다.

그래서 1단계에서 값 하나로 정했던 가정(6.2절, 12절)을 전부 **축**으로 바꾸고, 축의 모든 값을 곱해 돌린다. 9절의 범위 검사와 가격 환산표는 3단계로 민다. 아래 값 목록은 추천이고 `money-balance.json`에서 더하고 뺀다.

### 13.1 축

| 축 | 값(추천) | 기준 값(표를 읽기 쉽게 하는 표시일 뿐) |
|---|---|---|
| **자는 때** | `finish-by` 20:00, 21:00, 22:00, 23:00, 00:00, 01:00, 02:00, 03:00, 04:00, 05:00, 06:00(그 시각까지 끝나는 행동만 시작하고 잔다) / `start-before` 22:00, 00:00, 02:00(그 시각 전이면 시작하고, 끝나면 잔다) / `never`(자지 않는다 — 07:00에 날이 넘어간다) / `stay-up-every` 2, 3, 7(N일에 하루만 밤새고 나머지 날은 22:00까지 끝내고 잔다) | `finish-by` 22:00 |
| **미니게임 점수** | 고정 50(실패), 60, 70, 80, 90, 100 / `fail-every` 2, 4(N번에 한 번 실패 점수 50, 나머지 80) | 80 |
| **알바 성공** | 모두 성공 / `fail-every` 2, 4 | 모두 성공 |
| **걷는 시간(분)** | 0, 15, 30, 60 | 30(`day-balance.json`) |
| **미니게임을 하는 몫** | 0.25, 0.5, 1.0 | 0.5(`day-balance.json`) |
| **전략** | 1단계의 다섯 + 시설 일을 레벨마다 하나만 하기(올리되 그 레벨 일만) + 올린 뒤 새 일의 숙련을 채우고 나서 자동 넘기기 | — |
| **날 수** | 한 판을 100일 돌리고 7일·30일·100일 시점의 값을 낸다 | 30일 |

- 자는 때의 규칙(Core `TimeRules`, `StudentLifeProgress`): 취침 시각 22:00 뒤 깨어 있는 1시간마다 체력 1을 잃고, 늦게 잔 1시간마다 회복이 2씩 준다. 체력이 0이면 지쳐서 아무것도 시작하지 못하고, 자야 풀린다. 자지 않으면 07:00에 회복 없이 날이 넘어간다. 시뮬레이터는 이 규칙을 다시 쓰지 않고 `GameSession`의 `Sleep`, `AdvanceTime`, `IsExhausted`만 쓴다.
- 지쳤거나 할 것이 없는데 아직 잘 때가 아니면: `never`는 날이 넘어갈 때까지 시계만 돌린다. 다른 잠 규칙은 그때 잔다(지쳐서 일찍 잠 — 멈춘 이유에 적는다).
- 사용자 결정(2026-11-12, `StayingUpTests`): 밤샘이 자는 것보다 이득이면 안 된다. 그것은 성장 기준이었다. 이 표는 **돈 기준**으로 같은 것을 본다 — 이득으로 나오면 고치지 않고 표에 그대로 보인다.
- 종류(잠 규칙, 점수 모델, 성공 모델)는 클래스 하나 + 등록 한 줄이다. 값 목록은 설정 파일에 있다.

### 13.2 돌리는 법과 크기

- 모든 축의 곱을 돌린다(시설 전략은 자는 때 × 점수 × 걷기 × 몫 × 전략 × 시설, 알바 전략은 자는 때 × 성공 × 걷기 × 몫 × 전략 × 알바). 추천 값이면 수만 판 × 100일이다. 판끼리 독립이라 병렬로 돌린다(결과 순서는 설정 순서로 고정 — 같은 입력은 같은 파일). Strix Halo(32코어)에서 몇 분 안쪽을 목표로 하고 재서 적는다.
- 너무 커서 다 못 돌리면 줄이기 전에 그 사실과 줄이는 방법을 보고한다.
- 날마다의 줄(`days.csv`)은 훑기에서는 쓰지 않는다(수백만 줄). 판마다 시점별 요약만 쓴다.

### 13.3 내는 것 (`output/balance/sweep/`)

- `sweep.csv`: 판(모든 축의 값) × 시점(7·30·100일)마다 한 줄 — 하루 수입, 실제 분당 수입(둘), 레벨 2·3 날, 쓴 값만큼 버는 날, 자동 넘기기 첫날, 지쳐서 멈춘 날 수, 밤에 잃은 체력 합, 가방 찬 첫날, 하루 평균 행동 수.
- `sweep-report.md`(한글): 맨 위에 가정과 "가정을 넣은 계산이다. 실제 플레이가 아니다."
  1. **자는 때 표**: 전략마다, 줄은 잠 규칙, 칸은 하루 수입(7·30·100일)·하루 행동 수·지쳐서 멈춘 날 수. 다른 축은 기준 값. 가장 많이 버는 잠 규칙에 표시.
  2. **축마다 표**: 그 축만 바꾸고 다른 축은 기준 값일 때 전략별 하루 수입.
  3. **가장 많이·적게 버는 조합** 위·아래 20개(모든 축).
  4. 직업(시설)끼리의 비가 가장 크게 벌어지는 조합.
- 1단계의 `report.md`·`days.csv`·`summary.csv`(기준 값 한 가지)는 그대로 둔다.

### 13.4 이 문서를 쓴 쪽이 정한 것(2단계)

- 축의 값 목록(13.1절 표) — 사용자가 더하고 뺀다.
- `stay-up-every`의 나머지 날은 22:00까지 끝내고 잔다.
- 실패 점수는 50, `fail-every`의 성공 점수는 80.
- 100일 한 판에서 7·30·100일 시점을 읽는다(따로 세 번 돌리지 않는다).
- 가방이 찼을 때 버리기, 학생 첫날부터 성인까지 이어 도는 판은 이번에도 넣지 않는다(버리는 명령·긴 준비가 필요하다) — 결정 대기 문서에 적는다.
- 직업 간 자유도가 들어간 main이 아니라 이 브랜치의 데이터로 돈다. main을 합치면 표가 저절로 바뀐다.
