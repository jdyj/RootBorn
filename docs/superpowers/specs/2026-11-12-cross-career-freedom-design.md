# 직업 사이가 이어지는 자유도 — 기술, 공간, 꾸미기 설계

작성일: 2026-11-12
상태: **초안. 사용자가 질문을 건너뛰고 추천안으로 진행하라고 했다.** 아래에서 "사용자"라고 적은 것만 사용자가 말한 것이고, "추천"이라고 적은 것은 이 문서를 쓴 쪽의 판단이다. 구현 전에 12절(정해야 할 것)을 확인받는다.

## 1. 사용자가 바란 것

사용자(2026-11-12):

- 게임에 자유도가 높았으면 한다.
- 요리사는 요리를 할수록 숙련도가 올라 요리가 잘된다. 거기서 그치지 않고 식당 인테리어도 필요하다.
- 싱글플레이에서는 기본 템플릿을 제공할 수도 있지만, 요리사가 인테리어를 배워 자기 식당을 직접 가꿀 수도 있으면 좋겠다.
- 이렇게 직업끼리 유기적으로 이어지게 한다. 인테리어는 대다수 직업과 관련이 있을 수 있다. 확장하기 쉽게 설계한다.

## 2. 한 줄 요약

**직업은 "기술 묶음을 쓰는 자리"이고, 기술은 누구나 배운다. 모든 일터는 꾸밀 수 있는 공간이고, 공간의 성질이 그 일터의 일에 이득을 준다.** 요리사가 인테리어를 배우는 것은 특별한 기능이 아니라 이 세 가지가 만나서 저절로 생기는 일이다.

## 3. 지금 있는 것 (코드에서 확인)

| 있는 것 | 어디 | 이 설계에서 |
|---|---|---|
| 기술 값(`AddSkill`/`GetSkillValue`, id 문자열) | Core `StudentLifeProgress` | 그대로 쓴다. 기술 정의는 지금 `skill.basic-study` 하나뿐이다 |
| 일마다 숙련(`Mastery`), 성공 횟수 | Core `AdultCareerProgress` | 그대로 둔다(일 하나를 얼마나 익혔는지). 기술과 구별한다 |
| 시설 레벨 1~3, 레벨별 보상 비율 | Core `Facility`, `FacilityLevel` | 그대로 둔다. 공간 보정이 그 위에 곱해진다 |
| 조건 종류를 클래스 하나로 더하는 구조 | `IFacilityTransitionRequirement`, `IAutoSkipRequirement`, 활동의 조건·효과 | 같은 방식으로 새 종류를 더한다 |
| 면 id로 나뉜 가구 배치, 걸어갈 길 검사 | Core `HouseFurnitureLayout`, `HousePlacementModel`, `FurniturePlacementSaveData.SurfaceId` | **집 전용이 아니다.** 일터에도 그대로 쓴다 |
| 가구 1,503개(분류: Bedroom, Kitchen, Bathroom …), 해금 토큰, 용돈 구매 | `data/interiors/FurnitureDefinition.json`, `FurnitureUnlockProgress` | 그대로 쓴다. 성질은 덧붙이는 데이터로 준다(6절) |
| 맵 성질로 화면을 고르는 구조(`MapFeatures`) | Screens `ScreenStack.EnterMap` | 일터 맵이 "가구를 놓는 면이 있다"를 가지면 가구 배치 화면이 그대로 열린다 |
| 방 요청(요청 id, 한 번만) | Core `Room/RoomRequests` | 3단계(다른 플레이어에게 의뢰)의 바탕 |

없는 것: 직업과 무관하게 자라는 기술 목록, 일터 안을 꾸미는 일, 꾸민 결과가 일에 주는 영향, 직업 사이의 주고받기.

## 4. 목표와 하지 않을 것

**목표**

1. 한 직업을 가진 채 다른 직업의 기술을 배워 자기 일에 쓸 수 있다(요리사 + 인테리어).
2. 배우지 않아도 막히지 않는다. 템플릿을 사거나 남에게 맡기는 길이 있다.
3. 새 직업, 새 기술, 새 공간 성질, 새 직업 간 연결을 **데이터만 더해** 넣을 수 있다. 새 "종류"만 클래스 하나와 등록 한 줄이다.
4. 기존 세이브가 그대로 읽힌다. 기존 네 직업의 진행과 엔딩 조건이 바뀌지 않는다.

**하지 않을 것**

- 직업을 여러 개 동시에 갖는 것(시설 여러 곳의 수장). 주 직업은 하나로 둔다. 추천.
- 손님이 걸어 다니는 경영 시뮬레이션. 공간은 수치로 일에 영향을 줄 뿐이다.
- 지금 그림에 맞춘 꾸미기 판정(그림은 전부 바뀔 예정이다).

**이렇게 되면 실패다**

- 인테리어를 안 배우면 식당이 손해를 보는 구조(벌점). 꾸미기는 **더 얻는 길**이지 필수 관문이 아니다.
- "요리사이면서 인테리어를 배웠으면"처럼 특정 직업 짝을 코드가 아는 것.
- 한 가지 정답 배치가 있어서 모두 같은 식당이 되는 것.

## 5. 세 기둥

```
 기술(누구나 배움) ──① 무엇을 놓을 수 있나, 같은 가구에서 얼마나 얻나──▶ 공간(일터마다 하나)
                                                                        │
                                              ② 놓인 것에서 성질 점수 계산 │
                                                                        ▼
 일(요리, 진료, 훈련 …) ◀──③ 그 일이 반기는 성질만큼 이득────────── 공간 성질(아늑함, 위생 …)
        │
        └──④ 일을 하면 그 일의 기술이 자란다
```

### 5.1 기술 — 직업에서 떼어 낸다

- 기술은 데이터다(`SkillDefinition`, 이미 있는 종류). 직업마다 기술을 한두 개 더한다: 요리, 인테리어, 응급 처치, 체력·규율. 이름과 개수는 12절.
- **직업은 기술을 가리킬 뿐 소유하지 않는다.** 시설의 일(`FacilityWork`)에 "성공하면 이 기술이 얼마 자란다"를 효과로 붙인다. 학생 때 활동·알바·연습은 이미 `SkillProgressEffect`로 기술을 올릴 수 있다.
- 기술 값은 지금처럼 `StudentLifeProgress`에 쌓이고 성인이 되어도 이어진다. 새 저장 칸이 필요 없다.
- 기술 단계: 기술 값의 구간을 데이터로 나눈 것(`SkillTier`: 기술 id, 최소 값, 단계 이름 키). 규칙은 "값 ≥ 최소 값"만 본다.
- 일의 숙련(`Mastery`)과의 차이: 숙련은 **그 일 하나**를 익힌 정도(건너뛰기 조건). 기술은 **여러 일과 공간에 두루** 쓰이는 힘. 둘 다 둔다.

### 5.2 공간 — 모든 일터는 꾸밀 수 있는 면이다

- 시설마다 배치 면 하나를 데이터로 준다(`WorkspaceDefinition`: 시설, 면 id, 레벨별 가구 한도, 받는 가구 묶음). 집에서 쓰는 `HouseFurnitureLayout`·`HousePlacementModel`을 그대로 쓴다. 칸(바닥, 고정, 문 앞)은 맵에서 온다.
- 가구가 어느 면에 놓일 수 있는지: 지금 가구는 `allowedSurfaceIds`에 면 id를 적는다. 1,503개에 시설 면 id를 하나씩 더하지 않도록, **면 쪽이 "이 면에 놓을 수 있는 가구의 면 id"를 받는다**(`accepts: ["house"]`). 가구 데이터는 그대로다. 추천.
- 시설 레벨은 **넓이와 한도**(놓을 수 있는 가구 수), 꾸미기는 그 안의 **질**을 맡는다. 서로 대신하지 못한다.
- 저장: 면마다 배치 파일 하나(집의 단계별 파일과 같은 모양, `FurniturePlacementLayoutSaveData`). 파일 이름은 `SaveFileNames`에 한 줄.

### 5.3 공간 성질 — 놓인 것이 일에 주는 것

- 성질은 데이터다(`SpaceQualityDefinition`: id, 이름 키, 아이콘 키). 예: 아늑함, 위생, 작업 동선, 안전, 집중. 목록은 12절.
- 가구가 성질을 얼마나 주는지는 가구 정의를 고치지 않고 **덧붙이는 표**로 준다(`FurnitureQualityRule`: 대상은 가구 분류 또는 가구 id, 성질 id, 점수). 분류 단위 기본값을 두고 필요한 가구만 따로 적는다. 왜: 가구 정의는 변환 결과이고 1,503개다. 그림을 바꿔도 이 표는 가구 id에만 기댄다.
- 공간 점수 계산은 Core의 순수 함수 하나다: (놓인 가구 목록, 성질 규칙, 계산 전략들) → 성질별 점수. 전략은 종류를 더할 수 있다.
  - 합산(가구 점수의 합), 같은 가구 되풀이 줄이기(같은 것만 채우는 것을 막는다), 묶음 보너스(예: 식탁 + 의자). 처음에는 합산과 되풀이 줄이기만 만든다. 추천.
  - **가구가 놓인 칸 위치에 기대는 판정(인접, 동선)은 1단계에서 하지 않는다.** 맵이 새로 그려질 예정이라 지금 정하면 다시 써야 한다.
- 기술이 끼어드는 자리(①): `IDecorationRule` 종류로 더한다.
  - **한도 늘리기**: 인테리어 기술 단계가 오르면 그 면의 가구 한도가 는다.
  - **점수 배율**: 같은 가구에서 얻는 성질 점수가 는다.
  - 자유 배치를 기술로 잠그지 않는다(사용자 결정, 12절 3). 누구나 가구를 놓을 수 있다.
- 일이 받는 이득(③): 일 정의에 효과 목록을 붙인다(`IWorkspaceBonus`). 종류마다 클래스 하나.
  - 보상 비율 더하기(성질 점수 구간 → 퍼센트). 시설 레벨의 `RewardPercent`에 더해진다.
  - 명성 더하기.
  - 미니게임 관대함(제한 시간, 실수 허용) — 기획서 8절 "성장 보너스"와 같은 통로다.
  - 이득에는 **위 한도**를 데이터로 둔다. 꾸미기만으로 수익이 끝없이 늘지 않게.
- 일마다 반기는 성질이 다르다. 식당 일은 아늑함·위생, 응급 시설은 위생·동선, 훈련 기지는 안전·동선, 스튜디오는 집중·아늑함. 이것이 "인테리어는 대다수 직업과 관련된다"의 구현이다 — 인테리어 기술 하나가 모든 일터의 성질 점수를 올린다.

### 5.4 꾸미는 세 가지 길 (자유 경로)

| 길 | 무엇 | 드는 것 | 얻는 것 |
|---|---|---|---|
| 템플릿 | 데이터로 준 배치 한 벌(`WorkspaceTemplate`: 면, 가구·칸·방향 목록, 값)을 적용 | 돈 | 무난한 성질 점수. 기술 필요 없음 |
| 맡기기 | 인테리어 일을 하는 쪽에 의뢰(2단계는 NPC, 3단계는 다른 플레이어) | 돈, 날짜 | 템플릿보다 높은 점수. 기술 필요 없음 |
| 직접 | 인테리어 기술을 배워 가구를 하나씩 놓는다 | 시간(기술을 올리는 데), 가구 값 | 가장 높은 한도와 배율, 원하는 모양 |

- 템플릿 적용과 의뢰 지급은 보상 규칙을 따른다: 미리 확인(돈, 가구 한도, 걸어갈 길), 하나라도 안 되면 무변경, 요청 id로 한 번만, 저장·다시 읽기 뒤에도 한 번만.
- 템플릿을 적용한 뒤 언제든 직접 고칠 수 있다. 템플릿은 시작점이다.
- 시설을 처음 맡을 때는 가장 싼 템플릿이 이미 적용돼 있다. 왜: 빈 방에서 시작해 손해를 보는 일이 없게(4절 실패 조건).

### 5.5 직업 사이의 연결 — 일반형은 "기여"

인테리어만 특별하게 만들지 않는다. 한 기술이 다른 일터에 주는 것은 모두 같은 모양이다: **기여가 대상 공간의 성질 점수 원천이 된다.**

- 공간 점수의 원천을 인터페이스로 둔다(`ISpaceQualitySource`): 가구(1단계), 기여(2단계).
- 기여(`ContributionDefinition`): 어느 기술이, 어떤 성질을, 얼마 동안, 얼마나 주는지. 예(내용은 12절에서 정한다):
  - 인테리어 → 꾸미기 의뢰(가구 배치)
  - 요리 → 단체 급식: 대상 일터의 사기 성질을 며칠 올린다
  - 응급 처치 → 위생·안전 점검: 위생 성질
  - 군인 → 안전 훈련: 안전 성질
- 플레이어가 자기 주 직업의 기술로 **다른 시설의 의뢰**를 받는 것도 같은 데이터다(의뢰 = 기여를 해 주고 돈·명성을 받는 일). 그래서 성인기에도 다른 직업의 일터에 드나들 이유가 생긴다.
- 새 직업이 들어오면: 기술 정의, 시설, 일, 그 일이 반기는 성질, (있으면) 그 기술이 주는 기여를 데이터로 더한다. 코드는 그대로다.

## 6. 데이터

새 종류(모두 `type`, `id`, 다른 엔티티는 `ref`로 가리킨다). 만들기 함수는 `game/Rootborn.Data/Builders`에 영역 하나(`WorkspaceBuilders`)로 더한다.

| 종류 | 필드(요지) | 단계 |
|---|---|---|
| `SkillDefinition`(있음) | 더할 것 없음. 정의만 는다 | 1 |
| `SkillTierDefinition` | 기술, 최소 값, 이름 키 | 1 |
| `SkillProgressWorkEffect` | 기술, 늘어나는 값. 일의 성공 효과 | 1 |
| `SpaceQualityDefinition` | 이름 키, 아이콘 키 | 1 |
| `FurnitureQualityRule` | 대상(분류 또는 가구), 성질, 점수 | 1 |
| `WorkspaceDefinition` | 시설, 면 id, 받는 면 id 목록, 레벨별 가구 한도, 꾸미기 규칙 목록 | 1 |
| 꾸미기 규칙들(`SkillTierCapacityRule`, `SkillTierScoreRule` …) | 기술 단계 → 한도·배율 | 1 |
| 일의 공간 이득들(`QualityRewardPercentBonus`, `QualityReputationBonus` …) | 성질, 점수 구간, 이득, 위 한도 | 1 |
| `WorkspaceTemplate` | 면, 배치 목록, 값(아이템·수량) | 1 |
| `ContributionDefinition`, `CommissionDefinition` | 기술, 성질, 기간, 값 | 2 |

데이터를 어디에 두는가: `data/`는 지금 변환기 결과라 손으로 고치지 않는다. 새 종류는 Unity 에셋에 원본이 없으므로 MonoGame 판이 직접 갖는 폴더에 둔다(문구의 `game/localization`과 같은 방식). 추천: `game/data/` 폴더를 정의 로더가 `data/` 뒤에 함께 읽게 한다. Unity를 지워 `data/`가 원본이 되면 합친다. 12절에서 확인.

기존 일 정의(`FacilityWorkDefinition`)에 효과를 붙이는 방법도 같은 문제다(변환 결과를 고칠 수 없다). 추천: 일을 고치지 않고 **바깥에서 일을 가리키는 연결 데이터**로 둔다(`WorkBonusBinding`: 일 ref, 효과 목록). 일 정의가 원본이 되면 일 안으로 옮길 수 있다.

## 7. 규칙이 사는 곳

- Core `Rootborn.Core.Workspaces`(새 영역): 성질 정의, 가구 성질 규칙, 공간 점수 계산, 꾸미기 규칙, 일의 공간 이득, 템플릿 적용 판정, 세이브 모양. 엔진·파일·JSON 참조 없음.
- Core `Careers`: `AdultCareerService`의 일 정산이 "공간 이득 조회"(`IWorkspaceBonusSource`, 값으로 받는다)를 받아 보상 비율·명성에 더한다. 조회가 없으면 지금과 똑같이 돈다(기존 테스트가 그대로 통과해야 한다).
- Game `GameSession`: 일터 배치 열기·저장, 템플릿 적용 명령, 공간 점수 조회, 일 정산에 공간 이득 넘기기. 규칙 판단은 하지 않는다.
- Screens: 가구 배치 화면은 그대로 쓰고(맵 성질로 열린다), 성질 점수 줄과 템플릿 고르기를 더한다. 시설 화면에 "이 일이 반기는 성질과 지금 이득"을 보인다. 화면 구성은 12절.
- 목표 수첩: "꾸미면 이득이 는다" 같은 안내는 새 HUD가 아니라 수첩의 모으는 쪽 하나로 낸다.

## 8. 저장

- 일터 배치: 면마다 `FurniturePlacementLayoutSaveData`(있는 모양) 파일 하나. 새 모양 없음.
- 적용한 템플릿·의뢰의 요청 id: 새 세이브 모양 `WorkspaceProgressSaveData`(Version 1, 면 id, 적용한 요청 id 목록, 2단계에서 진행 중인 기여). `SaveShapeCoverage`에 등록.
- 기존 세이브: 일터 배치 파일이 없으면 가장 싼 템플릿이 적용된 것으로 읽는다(무료, 한 번만). 기술 값이 없으면 0이다. 기존 필드는 고치지 않는다.
- 공간 점수는 저장하지 않는다. 배치에서 다시 계산한다.

## 9. 성능

- 공간 점수는 배치가 **확정될 때**와 읽을 때만 계산해 면마다 기억한다. 매 프레임·일 정산마다 가구를 훑지 않는다.
- 가구 성질 규칙은 시작할 때 가구 id → 성질 점수 표로 한 번 펼친다(분류 규칙을 1,503개에 미리 적용). 배치 중에는 표 조회만.
- 배치 화면에서 가구를 들고 움직이는 동안의 미리 보기 점수는 "지금 점수 + 이 가구의 차이"로 낸다. 전체를 다시 계산하지 않는다(되풀이 줄이기 전략이 이를 지킬 수 있게 가구별 개수만 기억한다).
- 측정: 가구 한도의 가장 큰 값만큼 놓은 면에서 점수 계산과 템플릿 적용 시간을 테스트로 잰다.

## 10. 단계

| 단계 | 내용 | 끝났다는 기준 |
|---|---|---|
| 1 | 기술 정의·단계, 일의 기술 성장, 일터 면, 성질, 점수 계산, 일의 공간 이득, 템플릿. **요리사 + 인테리어 한 줄로 끝까지** | 요리사로 식당에 걸어 들어가 가구를 놓으면 성질 점수가 오르고, 요리 일의 보상이 는다. 인테리어 기술을 올리면 한도가 는다. 다른 세 시설은 데이터만 더해 같은 것이 된다 |
| 2 | 기여와 의뢰(NPC). 다른 시설의 일을 받아 주고, 내 시설을 맡긴다 | 인테리어를 안 배운 요리사가 의뢰로 템플릿보다 높은 점수를 얻는다 |
| 3 | 멀티플레이: 다른 플레이어에게 맡기기(방 요청) | 멀티플레이 바탕이 Host에 이어진 뒤에 따로 설계한다 |

단계 1만 구현 계획을 쓴다. 2·3은 1이 끝난 뒤 다시 설계한다(쓰이지 않는 확장점을 미리 만들지 않는다 — 1단계에서 만드는 인터페이스는 `ISpaceQualitySource` 하나뿐이고 구현은 가구 하나다).

## 11. 테스트

- Core: 점수 계산(합산, 되풀이 줄이기, 규칙 없는 가구는 0), 기술 단계별 한도·배율, 이득의 위 한도, 템플릿 적용의 다섯 경우(정상, 돈 부족, 일부 적용 없음, 같은 요청 두 번, 저장·다시 읽기 뒤 다시 요청), 공간 이득 조회가 없을 때 일 정산이 지금과 같음.
- Data: 새 종류 등록, 실제 데이터 읽기, 새 세이브 모양, 일터 배치 파일이 없는 옛 세이브 고정 파일.
- Game: 시나리오 `WORKSPACE-001`(꾸미면 일 보상이 는다), `WORKSPACE-002`(템플릿은 한 번만), `SKILL-001`(주 직업이 아닌 기술을 올려 자기 일터에 쓴다 — 요리사 + 인테리어). 학교 밖 길: 인테리어 기술을 수업 없이 올리는 길 하나 이상(내 방 꾸미기, 스튜디오 알바, 독학).
- Screens: 점수 줄·템플릿 목록의 구성과 동작, 모든 언어의 문구 키, 긴 문구.
- Host: 식당에 걸어 들어가 가구를 놓고 일을 해 보상이 는 것까지 장치 이벤트 주입으로 한 번. 스크린샷을 직접 본다.
- 엔티티 id 분기 없음(CI). 테스트는 특정 그림·맵 좌표에 기대지 않는다.

## 12. 정해야 할 것 (기획 — 사용자가 정한다)

추천안을 적었다. 그대로 가도 되는지, 바꿀 것이 있는지 확인받는다.

1. **주 직업은 하나, 기술은 무엇이든.** 추천. 시설을 여러 곳 맡는 것은 하지 않는다.
2. **꾸미기는 더 얻는 길이지 필수가 아니다.** 추천. 엔딩 조건(시설 레벨 3)은 그대로이고 꾸미기를 요구하지 않는다.
3. **자유 배치에 기술 조건을 두지 않는다. 사용자 결정(2026-11-12).** 누구나 가구를 놓을 수 있고, 인테리어 기술은 놓을 수 있는 수와 점수 배율만 올린다. "자유 배치 열기" 규칙은 만들지 않는다.
4. **기술 목록.** 추천: 직업마다 하나(요리, 인테리어, 응급 처치, 체력·규율)로 시작한다.
5. **공간 성질 목록과 일마다 반기는 성질.** 추천: 아늑함, 위생, 동선, 안전, 집중 다섯. 5.3의 짝.
6. **수치 전부**(가구 한도, 성질 점수, 이득 퍼센트와 위 한도, 템플릿 값, 기술 단계 구간). 수치는 사용자가 정한다. 구현은 시험용 수치로 하고, 실제 수치는 표로 제안해 확인받는다.
7. **학생 때 인테리어 기술을 올리는 길.** 내 방 꾸미기가 인테리어 기술을 올리게 할지(기획서 3절에 "Interior 유년기 활동: 내 방 가구 배치"가 이미 있다). 추천: 올린다.
8. **새 데이터의 자리.** 추천: `game/data/`(6절).
9. **2단계의 기여 내용**(급식, 점검, 안전 훈련). 1단계가 끝난 뒤 정한다.

## 13. 구현하는 쪽에 맡기는 것

- 클래스·필드 이름, 점수 계산 전략의 내부 모양, 표 펼치기 방식.
- 가구 배치 화면에 점수 줄을 넣는 배치(그 화면의 배치 한 곳에서).
- `WorkBonusBinding` 대신 더 단순한 연결 방법이 있으면 그것(6절의 제약만 지키면 된다).

## 14. Unity 판과 달라지는 것

Unity 판에 없던 새 기능이다. 기존 동작은 바뀌지 않는다: 공간 이득 조회가 없으면 일 정산 결과가 지금과 같다. 달라지는 한 가지 — 시설을 맡으면 기본 템플릿이 적용된 일터 배치가 생긴다(옛 세이브는 처음 읽을 때 한 번).
