# 월드 이동 축 테스트 주도 복구 설계

## 목표

현재 프로젝트에서 사용자가 실제 플레이 기준으로 체감하는 핵심 결함은 다음과 같다.

- 캐릭터 기본 이동이 신뢰할 수 없다.
- 카메라 추적과 화면 이동이 안정적으로 보장되지 않는다.
- 씬이 나뉘어 있어도 실제 맵 이동 여정이 완결되지 않는다.
- 이동/전환 중 HUD 및 오버레이가 일관되게 유지된다고 보기 어렵다.

이번 설계의 목적은 이 문제를 “기능 추가 요청”이 아니라 “테스트로 잠긴 복구 목표”로 재정의하는 것이다. 산출물은 두 가지다.

- 사람 검토용 설계 문서
- 다음 세션에서 반복 실행 가능한 goal 문서

이번 단계의 최종 목표는 장기적으로 전체 테스트 스위트까지 확장 가능한 구조를 마련하되, 1차 goal은 `이동 축 전용 스위트`를 설계하고 구현하여 통과시키는 것이다.

## 1차 완료 조건

1차 goal은 다음 조건을 모두 만족할 때 완료로 본다.

- `MOV`, `CAM`, `MAP`, `UI` prefix를 사용하는 명명된 테스트 시나리오가 존재한다.
- 시나리오별 기대 행동, 대상 씬, 테스트 계층(EditMode/PlayMode)이 문서에 명시된다.
- 이동 축 전용 스위트가 실패 테스트부터 시작해 구현 후 안정적으로 통과한다.
- 관련 기존 회귀 테스트가 함께 통과한다.
- 남은 미구현 항목, 임시 skip, 애매한 수동 판단 지점이 문서에 남지 않는다.
- 다음 단계에서 전체 테스트 스위트로 확장하는 규칙이 문서에 정의된다.

## 문제 정의

기존 테스트는 일부 포털 전환과 씬 오브젝트 존재를 확인하지만, 다음 사용자 체감 결함을 완전하게 막지 못한다.

- 입력 기반 이동이 실제로 동작하는지
- 대각 이동 속도가 비정상적이지 않은지
- 충돌체를 뚫고 지나가지 않는지
- 카메라가 플레이어를 놓치지 않는지
- 씬 전환 후 카메라 타깃과 플레이어 참조가 유지되는지
- 포털 이동 후 스폰 위치가 정확한지
- 전환 과정에서 플레이어가 중복 생성되지 않는지
- HUD와 오버레이가 전환 후에도 유효한지
- 대화 UI가 이동을 영구적으로 잠그지 않는지

## 범위

### 1차 포함 범위

- 플레이어 이동
- 카메라 추적
- 포털 기반 씬 이동
- 전환 후 스폰 위치
- 이동/전환 관련 HUD 및 오버레이 생존성
- 위 항목에 영향을 받는 기존 EditMode/PlayMode 회귀

### 1차 제외 범위

- 전체 네트워크 세션 동기화 완성
- 전 세대/농사/도구/상호작용 스위트 전면 재작성
- 미사용 씬 전부에 대한 월드 품질 보장
- 시네머신 도입 같은 구조 대체

## 접근 방식 비교

### 접근 1. 문서 후 이동 축 전용 스위트부터 잠그기

문서에서 시나리오와 goal 루프를 고정한 뒤, `이동/카메라/맵전환/UI` 축의 실패 테스트를 먼저 추가하고 최소 구현으로 통과시킨다.

장점:

- 현재 체감 문제에 가장 직접적이다.
- 헌법의 TDD 의무와 잘 맞는다.
- 2차 확장 시 같은 패턴을 전체 스위트에 재사용할 수 있다.

단점:

- 초기에는 이동 축 외 영역을 동시에 정리하지 않는다.

### 접근 2. 처음부터 전체 테스트 스위트 운영 규약까지 완성하기

장기 운영 규칙을 먼저 전부 정리하고 이동 축은 그 첫 배치로 포함한다.

장점:

- 장기 운영 문서 완결성이 높다.

단점:

- 현재 고장 난 이동 경험을 복구하는 집중력이 흐려질 수 있다.

### 접근 3. 수동 QA 중심으로 재정의 후 자동화 이관

체감 문제를 수동 체크리스트로 먼저 굳히고 나중에 자동화한다.

장점:

- 사용자 불만을 문장으로 빠르게 정리하기 쉽다.

단점:

- 헌법의 자동화/TDD 우선 원칙과 가장 덜 맞는다.

## 채택안

이번 작업은 **접근 1. 문서 후 이동 축 전용 스위트부터 잠그기**를 채택한다.

이유는 다음과 같다.

- 현재 저장소에 이미 이동 축 관련 코드와 테스트 골격이 존재한다.
- 사용자가 요구한 것은 “이론상 구현 흔적”이 아니라 “실제로 동작하고 테스트로 잠긴 상태”다.
- 이동 축은 사용자 첫 체감 품질이며, 전체 테스트 스위트 확장의 출발점이 된다.

## 시나리오 카탈로그

### MOV

- `MOV-001` 입력 벡터가 주어지면 플레이어가 예상 방향으로 이동한다.
- `MOV-002` 대각 입력은 정규화되어 축 이동보다 빨라지지 않는다.
- `MOV-003` 충돌체가 있는 경우 Rigidbody2D 기반 이동이 벽을 관통하지 않는다.
- `MOV-004` 입력이 0이면 이동이 멈추고 마지막 facing/idle 상태가 안정적으로 유지된다.

### CAM

- `CAM-001` 카메라가 플레이어를 일정 시간 내 추적한다.
- `CAM-002` 씬 전환 후에도 카메라가 새 씬의 플레이어를 계속 추적한다.
- `CAM-003` 포털 이동 직후 플레이어가 화면 밖으로 사라지지 않는다.

### MAP

- `MAP-001` `Farm -> Town` 포털 이동이 성공한다.
- `MAP-002` `Town -> House` 포털 이동이 성공한다.
- `MAP-003` `House -> Town` 또는 `Town -> Farm` 복귀 이동이 성공한다.
- `MAP-004` 각 이동 후 `SpawnId` 위치 재배치가 정확하다.
- `MAP-005` 씬 전환 중 플레이어 인스턴스가 중복 생성되지 않는다.

### UI

- `UI-001` HUD 필수 요소가 씬 진입 후 null/미표시 상태가 아니다.
- `UI-002` Dialogue/Overlay가 열린 뒤 닫히면 이동 가능 상태가 복구된다.
- `UI-003` 씬 전환 후 HUD 참조가 깨지지 않는다.

## 테스트 계층 설계

### EditMode에서 잠글 것

- 이동 입력 정규화나 순수 이동 규칙
- 전환 요청 데이터 해석
- `SpawnId` 선택 규칙
- UI 상태 전환의 순수 로직

### PlayMode에서 잠글 것

- 실제 씬 기반 이동
- 카메라 추적
- 포털 진입과 씬 전환
- 전환 후 플레이어 재배치
- HUD/오버레이 생존성
- 플레이어 중복 생성 여부

원칙은 다음과 같다.

- 실제 플레이 체감과 연결되는 요구는 PlayMode 우선이다.
- 가짜 씬/가짜 오브젝트로 충분한 규칙만 EditMode에서 잠근다.
- `Farm`, `Town`, `House` 실제 씬을 우선 사용한다.

## goal 문서 구조

실행용 goal 문서는 아래 섹션을 가진다.

- 목표
- 비목표
- 절대 헌법
- 1차 시나리오 카탈로그
- 반복 루프
- 테스트 실행 순서
- 실패 분류 규칙
- 종료 조건
- 최종 보고 형식

이 문서는 에이전트가 매 반복마다 동일한 기준으로 행동하도록 만드는 운영 계약서 역할을 한다.

## 반복 루프 설계

각 반복은 다음 순서를 반드시 따른다.

1. 현재 실패 테스트와 미구현 시나리오를 식별한다.
2. 가장 작은 단위의 실패 테스트를 추가하거나 기존 실패를 고정한다.
3. 테스트를 실행해 실제 실패를 확인한다.
4. 최소 구현으로 해당 실패만 해결한다.
5. 이동 축 전용 스위트와 관련 회귀 테스트를 다시 실행한다.
6. 남은 실패를 원인군별로 분류한다.
7. 아직 실패가 남아 있으면 다음 루프로 넘어간다.
8. 모든 통과 조건이 충족될 때만 종료한다.

## 종료 조건

- `MOV/CAM/MAP/UI` 1차 카탈로그가 모두 테스트로 존재한다.
- 이동 축 전용 스위트가 전부 통과한다.
- 관련 기존 회귀 테스트가 통과한다.
- skip, FIXME, 미정 상태 없이 결과가 정리된다.
- 어떤 테스트를 실행했고 무엇이 통과했는지 결과가 남는다.

## 장기 확장 규칙

1차 goal이 끝나면 동일한 구조를 전체 테스트 스위트로 확장한다.

- 이동 축을 통과 기준 템플릿으로 삼는다.
- 각 코어 루프 영역별로 prefix와 완료 조건을 명시한다.
- 신규 기능은 전체 스위트 확장 전에 해당 축 시나리오부터 등록한다.

## 리스크와 대응

- 기존 테스트 이름이 보장 범위를 충분히 드러내지 않을 수 있다.
  - 대응: 시나리오 ID 기준으로 재명명하거나 명시적 케이스로 분해한다.
- 실제 입력 장치 의존 테스트는 배치 실행에서 불안정할 수 있다.
  - 대응: 가능한 입력 시뮬레이션 또는 명시적 상태 주입으로 테스트를 설계한다.
- 씬 전환 중 참조 유지 문제가 Player, Camera, HUD에서 다르게 나타날 수 있다.
  - 대응: 원인군을 이동, 카메라, 포털, UI로 분리해 한 루프에 한 군만 수정한다.

## 최종 판단

이번 설계는 “이동이 안 된다”는 사용자 불만을 실행 가능한 테스트 체계로 바꾸는 데 초점을 둔다. 구현보다 먼저 기준을 잠그고, 그 기준을 goal 문서로 운영화하여 이후 세션에서도 같은 방식으로 반복 가능하게 만드는 것이 핵심이다.
